# 一、引言：为什么 RLVR 受到关注

## 1.1 后训练的重心正在从“像人”转向“会做题”

大语言模型的训练通常分为三个阶段：预训练、监督微调（SFT）和对齐 / 强化学习后训练。预训练让模型获得语言能力和世界知识；SFT 让模型学会按指令组织输出；RLHF 让模型的回答更符合人类偏好。这条路线在聊天、写作、知识问答上非常有效，但在数学推理、代码生成、形式化证明这类任务上，它有一个长期存在的短板：**“回答得像”与“回答得对”并不是同一件事。**

2024 年之后，情况发生了变化。以数学和代码为主要训练任务的一批工作表明，如果奖励信号可以由程序自动判定，强化学习就能在大规模采样中持续筛出“真正做对”的轨迹，并显著提升模型在推理任务上的表现。DeepSeek-R1 使用 GRPO 和基于规则的奖励（答案正确性加格式）训练推理能力；Tülu 3 则明确把这类方法称为 RLVR，并在数学可验证任务上用 PPO 做强化学习。术语和实现各不相同，但共同点是：**奖励不再来自人类偏好或奖励模型，而来自一个可以自动运行的验证器。**

这就是 RLVR 受到关注的原因。它把后训练的目标从“让模型更像人类喜欢的回答”部分转向“让模型通过可检查的正确性标准”。对于数学题，检查最终答案是否等价；对于代码题，运行单元测试；对于 JSON 输出，校验 Schema；对于工具调用，检查环境终态是否满足任务目标。只要验证器足够可靠，模型就可以在没有人工逐条打分的情况下，通过大量采样和策略优化自我提升。

但 RLVR 不是“有验证器就能变强”的简单公式。验证器的覆盖范围、误判率、抗攻击能力，奖励的稀疏程度，以及强化学习本身的稳定性，都会决定最终效果。本文会把这些工程细节展开讲清楚，而不是停留在“可验证奖励很客观”这一层。

## 1.2 SFT 的局限：只学示范，不学纠错

SFT 的目标是最小化示范答案上的 token 级交叉熵：

```text
L_SFT = -Σ log πθ(y_t | x, y_<t)
```

其中 `x` 是输入，`y` 是人工或强模型给出的示范回答。这个目标有三个结构性限制。

第一，**标准 SFT 只有正例，没有负例。** 模型学到的是“在这个上下文里，下一个 token 应该是什么”，而不是“哪种解法会失败、失败在哪里”。如果示范数据里没有覆盖某类错误，模型在推理时犯了同类错误，SFT 不会提供任何直接的纠正信号。

第二，**SFT 优化的是 token 级似然，不是序列级正确性。** 一道数学题的解答可以有 500 个 token，其中 499 个 token 都很流畅，只有最后一步算错。从交叉熵看，这个回答的损失可能很低；从任务看，它是完全错误的。SFT 没有机制把“最终答案错了”这个信息回传到中间步骤。

第三，**SFT 存在暴露偏差（exposure bias）。** 训练时模型看到的是示范答案的前缀，推理时看到的是自己生成的前缀。一旦模型在早期走偏，它没有在训练中见过“走偏之后如何恢复”的样本，错误会沿着自己的分布继续累积。

此外，SFT 依赖高质量示范数据。数学和代码的详细解题过程标注成本高，标注者本身也可能出错；用强模型蒸馏虽然能降低标注成本，但会把强模型的错误和风格一并复制过来。更微妙的是，SFT 很容易让模型学会“解题的格式”——先写“分析”，再写“计算”，最后写“因此”——却没有学会真正的搜索、验证和回溯。这在评测中表现为：格式很漂亮，步骤很完整，答案经常不对。

SFT 仍然是必要的。它负责教会模型任务格式、输出约定、工具调用 Schema 和基本的推理范式，也是 RL 冷启动的常见起点。但它不适合作为提升复杂推理能力的唯一手段。

## 1.3 RLHF / RLAIF 的局限：奖励是代理，不是事实

RLHF 的典型流程是：收集人类对同一问题多个回答的偏好排序，训练一个奖励模型（Reward Model, RM），再用 PPO 等算法优化策略，使奖励模型给出的分数更高，同时用 KL 惩罚限制策略偏离参考模型。

这套方法解决的是“人类更喜欢哪种回答”的问题，而不是“哪种回答在事实上正确”的问题。它有三个关键局限。

**第一，奖励模型是一个代理（proxy）。** 我们真正想要的是“有用、真实、无害”，但 RM 只能从有限偏好数据中学习这个目标的近似。优化压力一旦足够大，策略就会寻找 RM 的漏洞。Gao 等人的实验表明，随着对奖励模型的优化加强，代理奖励会持续上升，而真实奖励可能先升后降，这就是奖励模型过优化（reward model overoptimization）。在 RLVR 语境下，这个问题换了一个形式出现：如果验证器有漏洞，策略同样会学会利用漏洞。

**第二，偏好数据是主观的，而且信息粒度粗。** 标注者通常只能判断“A 和 B 哪个更好”，很难指出“A 的第 3 步错了，应该用另一种方法”。对于数学和代码，一个表达流畅但答案错误的回答，可能在风格上更讨喜；一个正确但冗长的证明，可能因为“读起来费劲”被压低。偏好信号与事实正确性之间没有必然的一致性。

**第三，奖励模型本身可以被攻击。** 模型可能学会更长、更自信、更迎合用户的表达，而不是更正确的推理。LLM Judge 也有类似问题：位置偏差、长度偏差、自我偏好、对提示注入缺乏抵抗力。RLAIF 用 AI 反馈替代部分人工标注，确实降低了成本、提高了规模，但它继承的是裁判模型的偏差，而不是消除了偏差。

这并不意味着 RLHF 没有价值。对于 helpfulness、语气、安全边界、拒答策略这类难以用规则表达的目标，RLHF 仍然是最主要的手段。问题在于：**当你真正关心的是“答案对不对”时，让一个学习出来的偏好模型来充当裁判，是把可验证问题转化成了不可验证问题。**

## 1.4 可验证奖励的价值：把“对不对”交给程序

RLVR 的核心洞察是：对很多任务而言，**验证一个候选答案比生成一个正确答案容易得多，而且验证可以自动化。**

- 数学题：给定参考答案，检查两个表达式是否等价，或者把候选值代入原方程验证。
- 代码题：给定函数签名和测试用例，编译并运行，看输出是否匹配。
- 形式化证明：把证明交给 Lean、Coq、Isabelle 的内核检查，类型检查通过就是通过。
- 结构化输出：用 JSON Schema、类型系统、业务规则校验字段和取值。
- 工具调用：在模拟或真实环境中执行工具，检查最终状态是否满足任务目标。
- Agent 任务：检查数据库终态、文件内容、API 副作用或用户目标是否达成。

这些信号的共同点是：**它们不依赖“哪个回答更讨人喜欢”，而依赖“哪个回答满足一个可执行、可复现的判据”。** 这带来几个直接好处：

1. **客观性**：在强可验证任务上，同一个输入、同一个验证器版本，输出是确定的。
2. **自动化**：不需要人工逐条标注，验证可以随采样规模扩展。
3. **可复现**：验证器版本、测试用例、运行环境都可以固定，实验可以重放。
4. **低边际成本**：一次单元测试或一次符号检查的成本，通常远低于一次人工评分。
5. **适合在线 RL**：RL 需要大量探索样本，可验证奖励让“多采样、多筛选”在经济上可行。

但“验证比生成容易”也有边界。一般数学表达式的等价性判断在理论上不可判定，实际系统只能用符号化简、数值采样和超时兜底；自然语言证明的验证并不比生成容易；代码测试通过也不等于代码正确（Dijkstra 的老话：“测试只能证明有错，不能证明没错”）。所以 RLVR 的“可验证”是工程意义上的可验证，不是数学意义上的完备判定。

## 1.5 RLVR 的核心问题

把上面的讨论收束一下，RLVR 要回答四个问题：

1. **什么任务可以被验证？** 任务需要有一个可执行或可判定的正确性标准。标准可以是参考答案、测试用例、形式化规约、Schema、环境终态，或者一组业务规则。没有这样的标准，就不适合直接用 RLVR。
2. **如何设计 verifier？** 验证器要覆盖主要错误模式，误判率要低，结果要稳定，执行要安全，成本要可控。验证器不是“写个正则”那么简单，它是整个训练系统的奖励来源。
3. **如何把验证结果转化为奖励？** 是二值奖励、分级奖励，还是过程奖励？格式、长度、安全、KL 各占多少权重？奖励尺度如何影响 advantage 和策略更新？
4. **如何处理部分正确？** 答案对但推理错、推理对但答案错、多解问题、题目本身有歧义、验证器超时或报错，这些情况都需要明确策略，不能简单归零。

### 一个最小例子

假设题目是“解方程 `3x + 5 = 20`”，参考答案是 `5`。模型采样出两个回答：

```text
回答 A：3x = 15，所以 x = 5。最终答案：\boxed{5}
回答 B：3x = 20 - 5 = 16，所以 x = 16/3。最终答案：\boxed{16/3}
```

验证器可以分三步：

1. **抽取答案**：用正则找到最后一个 `\boxed{...}`，得到 `5` 和 `16/3`。
2. **归一化**：去掉空格、单位、货币符号，把分数和小数统一成有理数或符号表达式。
3. **等价判断**：把候选值代入原方程，或者用 SymPy 比较 `candidate - reference` 是否化简为 0。

```python
import re
from fractions import Fraction

def extract_boxed(text: str):
    matches = re.findall(r"\\boxed\{([^{}]+)\}", text)
    return matches[-1].strip() if matches else None

def verify_linear(answer: str, reference: str) -> float:
    candidate = extract_boxed(answer)
    if candidate is None:
        return 0.0
    try:
        # 示意：真实系统应使用符号计算，而不是直接 eval
        return 1.0 if Fraction(candidate) == Fraction(reference) else 0.0
    except (ValueError, ZeroDivisionError):
        return 0.0
```

在这个例子里，回答 A 得到 1.0，回答 B 得到 0.0。这个奖励会和其他采样一起进入策略优化：产生 A 的轨迹概率被提高，产生 B 的轨迹概率被降低。真实的数学验证器会比这复杂得多，后文会展开。

再看一个结构化输出的例子。假设任务要求模型输出一个用户对象，Schema 规定 `name` 是字符串、`age` 是整数、`tags` 是字符串数组，并且 `age >= 0`：

```python
import json
import jsonschema

SCHEMA = {
    "type": "object",
    "required": ["name", "age", "tags"],
    "additionalProperties": False,
    "properties": {
        "name": {"type": "string", "minLength": 1},
        "age": {"type": "integer", "minimum": 0},
        "tags": {"type": "array", "items": {"type": "string"}},
    },
}

def verify_user_json(text: str) -> float:
    try:
        obj = json.loads(text)
        jsonschema.validate(obj, SCHEMA)
        return 1.0
    except (json.JSONDecodeError, jsonschema.ValidationError):
        return 0.0
```

这个例子说明：可验证奖励不限于“标准答案”。只要正确性可以被规则、Schema 或下游系统检查，就可以构造 RLVR 信号。也正因如此，RLVR 的适用范围比“数学和代码”更广，后面会专门讲结构化输出、SQL、工具调用和 Agent 任务。

# 二、什么是 RLVR

## 2.1 定义

> **RLVR（Reinforcement Learning with Verifiable Rewards）** 是一种用于大语言模型后训练的强化学习方法。它通过对模型输出进行自动验证，生成可客观判定的奖励信号，并利用这些奖励信号优化模型，使模型在数学推理、代码生成、形式化任务、工具使用等可验证任务上获得更好的表现。

这个定义里有三个关键词：

- **强化学习**：模型不是被动模仿示范，而是在自己的输出分布上采样、获得奖励、更新策略。
- **可验证奖励**：奖励来自规则、程序执行、单元测试、符号检查器、格式校验器或外部环境反馈，而不是人类偏好或纯学习出来的奖励模型。
- **后训练**：RLVR 通常发生在预训练和 SFT 之后，作为提升特定能力的阶段，而不是从零训练模型。

需要强调：**RLVR 不是某一个算法。** 它描述的是一类“奖励通道”的性质。具体优化可以用 PPO、GRPO、REINFORCE，也可以用拒绝采样微调（rejection sampling fine-tuning）这类更简单的离线方法。不同实现的差别很大，但只要奖励来自可验证信号，就可以归入 RLVR 家族。

## 2.2 强化学习的基本要素

把语言生成放进强化学习框架，有几种建模方式。最常见的是**序列级 bandit 视角**：把整个回答看成一个动作，奖励只在回答结束时给出；另一种是**token 级 MDP 视角**：每生成一个 token 是一个动作，状态是 prompt 加已生成的前缀，奖励可以在中间或结束时给出。

| RL 概念 | 在 RLVR 中的对应物 | 说明 |
| --- | --- | --- |
| Policy（策略） | 语言模型 `πθ` | 给定上下文，输出下一个 token 的概率分布 |
| State（状态） | prompt 加已生成前缀 | 序列级视角下可以简化为 prompt |
| Action（动作） | token 或完整回答 | token 级 MDP 与序列级 bandit 的区别 |
| Trajectory（轨迹） | 完整输出序列及其 logprob | 包含推理过程、最终答案、工具调用记录 |
| Reward（奖励） | 验证器给出的标量 | 可以是二值、分级或过程奖励 |
| Optimization Objective（优化目标） | 期望奖励减去 KL 惩罚 | 在提升奖励的同时限制策略漂移 |

**Policy** 是模型本身。它接收上下文，输出下一个 token 的分布。在 RLVR 中，策略通常从 SFT 模型初始化，参考模型（reference policy）是 SFT 模型的冻结副本，用来计算 KL 惩罚。

**Action** 可以是一个 token，也可以是整个回答。这个区别影响 credit assignment：如果奖励只在最后给出，token 级策略梯度需要把同一个序列级奖励分配给所有 token；如果每个推理步骤都有奖励，信用分配会更细，但需要过程验证器。

**Reward** 是验证器输出的标量。最简单的形式是 0/1，复杂的形式可以包含格式、过程、长度、安全和 KL 等多个分量。奖励的设计直接决定模型学什么，后文会专门讨论。

**Optimization Objective** 通常写成：

```text
J(θ) = E_{x~D, y~πθ(·|x)} [ R(x, y) ] - β · KL(πθ(·|x) || π_ref(·|x))
```

第一项是期望奖励，第二项是 KL 正则。β 控制“允许模型偏离参考模型多远”。没有 KL，模型可能为了奖励牺牲语言质量、可读性或安全性；KL 太强，模型又学不动。这个权衡是 RLVR 训练稳定性的核心之一。

## 2.3 什么是 Verifiable Rewards

可验证奖励的来源可以分成几类：

- **规则**：正则表达式、JSON Schema、字段约束、单位检查、格式约定。
- **程序执行**：编译、单元测试、集成测试、SQL 查询、API 调用。
- **符号检查**：CAS（计算机代数系统）、定理证明器、类型检查器、SMT Solver。
- **环境反馈**：模拟器状态、数据库终态、文件系统变化、工具返回值。
- **形式化规约**：前置条件、后置条件、不变式、权限策略。

它与人工偏好奖励的区别，不只是“谁来判断”，而是**奖励的语义**不同：

| 维度 | 偏好奖励 | 可验证奖励 |
| --- | --- | --- |
| 判断对象 | 哪个回答更符合人类喜好 | 回答是否满足某个判据 |
| 信号来源 | 标注者、奖励模型、LLM Judge | 规则、程序、符号系统、环境 |
| 可复现性 | 依赖标注者、模型版本、上下文 | 在固定版本和环境下可复现 |
| 扩展成本 | 人工或推理成本随规模线性增长 | 边际成本较低，可并行 |
| 主要风险 | 主观偏差、奖励模型过优化 | 验证器漏洞、覆盖不足、被策略利用 |
| 适用任务 | 风格、helpfulness、安全偏好 | 数学、代码、形式化、结构化、工具调用 |

为什么可验证奖励更适合推理任务？因为推理任务的目标通常是“找到一个满足约束的解”，而不是“写一段讨人喜欢的文字”。解的正确性可以被独立检查，检查过程不需要理解模型的“表达风格”。这让奖励信号更接近任务本身，也让大规模在线采样变得可行。

从训练动力学看，可验证奖励还有两个作用。第一，它降低了奖励噪声：偏好模型会随数据、上下文和模型版本漂移，而一个固定版本的测试或符号检查给出的信号更稳定，策略梯度更接近“真实正确性”的方向。第二，它支撑了“多探索 + 可靠筛选”的循环：模型可以对同一道题采样很多次，验证器负责从大量候选里筛出正确路径，策略再强化这些路径。推理能力的提升，很大程度上来自这个循环，而不是某一次单独的策略更新。

但要注意：**可验证奖励不是“绝对正确”的同义词。** 验证器可能漏判、误判、超时、被攻击；测试用例可能覆盖不足；Schema 可能太松；LLM Judge 可能被说服。RLVR 的质量上限，很大程度上由验证器的质量决定。

## 2.4 RLVR 中的大语言模型角色

在 RLVR 中，LLM 同时扮演几个角色：

1. **Policy**：生成候选答案、推理过程、代码、工具调用序列。
2. **State encoder**：把 prompt、历史对话、工具返回结果编码成上下文。
3. **Action generator**：逐 token 生成输出，形成一条轨迹。
4. **Learning target**：通过策略梯度更新参数，使高奖励轨迹的概率上升。

Prompt 或问题相当于状态或上下文；生成的答案或推理轨迹相当于动作序列；Verifier 输出奖励；强化学习算法根据奖励和 logprob 更新模型参数。这个闭环可以写成：

```text
问题 x → 策略 πθ 采样 y ~ πθ(·|x) → Verifier V(x, y) → 奖励 r
      → 策略梯度更新 θ → 新策略 πθ'
```

需要澄清一个常见误解：**RLVR 不要求模型必须输出显式的思维链。** 只给最终答案、只用结果奖励，也可以做 RLVR。DeepSeek-R1-Zero 的实验表明，在只使用答案正确性和格式奖励的情况下，模型可能自发产生更长的推理过程；但“自发产生”是实验结果，不是理论保证。工程上更常见的做法是：用 SFT 冷启动教会模型基本的推理格式，再用 RLVR 优化正确性；是否显式奖励推理过程，取决于任务和验证器能力。

## 2.5 边界：RLVR 是一类方法，不是万能标签

为了避免概念泛化，本文对 RLVR 的使用有几个边界：

- **奖励必须主要来自可验证信号。** 如果奖励主要来自 LLM Judge 的主观打分，即使流程里有一些规则检查，也更接近 RLAIF，而不是严格意义上的 RLVR。
- **验证器可以是模型辅助的，但要有校准和兜底。** 例如用 LLM 做语义等价判断，同时用规则、符号检查或人工抽检约束它。这样的系统是“弱可验证”，需要额外说明。
- **RLVR 不保证提升所有能力。** 它优化的是验证器覆盖的目标。验证器没覆盖的能力（语言自然度、创造性、安全性）可能不变，甚至退化。
- **RLVR 的效果依赖任务分布。** 在训练分布内提升明显，不代表在分布外、竞赛级难题或开放式任务上同样有效。后文会讨论相关研究和评估方法。

# 三、RLVR 与 SFT、RLHF、RLAIF 的区别

## 3.1 四种方法对比

| 对比维度 | SFT | RLHF | RLAIF | RLVR |
| --- | --- | --- | --- | --- |
| 训练信号来源 | 人工或强模型示范的 token 级似然 | 人类偏好对，训练奖励模型 | AI 偏好或评分，训练奖励模型或直接优化 | 规则、程序执行、单元测试、符号检查、环境反馈 |
| 奖励是否客观 | 无显式奖励，目标是模仿示范 | 主观，依赖标注者和奖励模型 | 较便宜，但仍依赖裁判模型的偏差 | 强可验证任务上客观、可复现；弱验证任务上仍有噪声 |
| 是否需要人工偏好标注 | 需要示范数据 | 需要偏好数据 | 少量或不需要 | 通常不需要；需要题目、答案、测试或规则 |
| 是否需要奖励模型 | 不需要 | 需要 | 通常需要 | 通常不需要；复杂任务可用模型辅助验证 |
| 典型算法 | 交叉熵、指令微调 | PPO + RM + KL | RLAIF、PPO、DPO + AI 反馈 | PPO、GRPO、REINFORCE、拒绝采样微调 |
| 适合任务 | 格式、指令遵循、冷启动 | 风格、helpfulness、安全偏好 | 大规模偏好对齐、降低标注成本 | 数学、代码、形式化证明、结构化输出、工具调用 |
| 优点 | 稳定、简单、数据效率高 | 能优化难以规则化的偏好 | 成本低、可扩展 | 奖励客观、可自动化、适合在线探索 |
| 局限 | 只学正例、易模仿格式、推理提升有限 | 奖励模型可被优化、主观、成本高 | 继承裁判偏差、可能自偏好 | 只覆盖可验证任务、奖励稀疏、验证器可被攻击 |
| 工程复杂度 | 低 | 高 | 中高 | 高，涉及沙箱、验证服务、RL 训练和评估 |

## 3.2 如何理解四者的关系

这四种方法不是互相替代的关系，而是解决不同问题的工具：

- **SFT 适合让模型学会基本格式和任务范式。** 它告诉模型“这类题应该怎么组织答案”“工具调用应该输出什么结构”“代码应该放在什么位置”。没有 SFT，RL 的探索空间太大，采样效率很低。
- **RLHF 更适合对齐人类偏好。** 当目标是“回答更有帮助、更礼貌、更符合安全规范”，而这些标准难以写成规则时，偏好学习是合理选择。
- **RLAIF 用 AI 反馈降低人工成本。** 它适合偏好数据规模大、人工标注昂贵的场景，但需要接受裁判模型的偏差，并做校准和抽检。
- **RLVR 更适合可客观验证的推理与执行类任务。** 当正确性可以被程序检查时，直接优化正确性比优化“看起来正确”更可靠。

实际训练中常见的组合是：

```text
预训练 → SFT（冷启动、格式、工具 Schema）
      → RLVR（数学、代码、结构化输出、工具调用）
      → RLHF / RLAIF（语气、安全、helpfulness）
      → 评估、红队、回归测试
```

顺序不是固定的。有些团队会先做 RLHF 再做 RLVR，有些团队会把安全惩罚直接并入 RLVR 的奖励函数，还有些团队会用拒绝采样微调替代在线 RL。选择取决于任务、数据、算力和风险容忍度。

一个重要的工程判断是：**不要用 RLVR 去优化它验证不了的东西。** 如果团队关心的是“回答是否优雅”“是否符合品牌语气”，这些不应该被塞进数学验证器；应该用单独的偏好信号或规则约束。把多个目标混进一个奖励函数，最容易出现的结果是模型只优化最容易得分的部分。

# 四、RLVR 的基本训练流程

RLVR 的完整流程可以概括为：

```text
问题采样 → 模型生成多个候选答案 → Verifier 自动验证
        → 奖励计算 → 强化学习优化 → 策略更新 → 评估与回归测试
```

下面按阶段展开。需要说明的是，实际系统里这些阶段通常是异步、并行、反复迭代的，而不是严格的单向流水线。

## 4.1 数据准备

RLVR 的数据不只是“题目加答案”。一个可训练的样本通常包含：

- **prompt / problem**：给模型的输入，可能包含系统提示、工具定义、输出格式要求。
- **reference answer**：参考答案，供答案型验证器使用。
- **verification rule**：验证方式，例如“用 SymPy 判断等价”“运行隐藏测试”“校验 JSON Schema”。
- **test cases**：代码题的公开测试、隐藏测试、边界测试。
- **constraints**：时间限制、内存限制、允许的库、输出格式、安全策略。
- **metadata**：来源、难度、题型、语言、许可证、去重指纹。
- **split**：训练集、验证集、测试集，必须按来源或时间去重划分。

不同任务族的数据设计重点不同：

| 任务族 | 样本核心字段 | 主要验证方式 | 主要风险 |
| --- | --- | --- | --- |
| 数学 | 题目、参考答案、答案格式 | 符号等价、数值比较、代入检验 | 题目歧义、多解、答案格式不统一 |
| 代码 | 题面、函数签名、公开/隐藏测试 | 编译、单元测试、静态检查 | 过拟合公开测试、硬编码、沙箱逃逸 |
| 结构化输出 | 输入、Schema、业务规则 | Schema 校验、字段约束、下游 dry-run | Schema 太松、业务规则遗漏 |
| 形式化证明 | 定理陈述、证明脚本、环境版本 | 证明助手内核检查 | 环境依赖、版本漂移、证明风格单一 |
| 工具调用 | 任务、工具定义、期望状态 | 模拟环境或真实环境终态检查 | 模拟环境与真实环境不一致 |
| Agent 任务 | 目标、环境、成功判据 | 终态检查、轨迹约束、安全策略 | 长程信用分配、无效循环、权限越界 |

一个数学样本可以写成：

```json
{
  "id": "math-000123",
  "prompt": "解方程 3x + 5 = 20，并给出最终答案。",
  "reference": "5",
  "answer_format": "boxed",
  "verifier": {"type": "math_equiv", "version": "2026-01"},
  "difficulty": 2,
  "source": "internal",
  "tags": ["algebra", "linear-equation"],
  "split": "train"
}
```

一个代码样本可以写成：

```json
{
  "id": "code-000456",
  "prompt": "实现函数 two_sum(nums, target)，返回两个下标。",
  "function_signature": "def two_sum(nums: list[int], target: int) -> list[int]:",
  "public_tests": [
    {"input": [[2, 7, 11, 15], 9], "expected": [0, 1]}
  ],
  "hidden_tests_ref": "s3://rlvr-tests/code-000456/hidden.json",
  "constraints": {"time_limit_ms": 2000, "memory_mb": 256, "network": false},
  "difficulty": 3,
  "split": "train"
}
```

数据准备阶段要特别注意三件事：

1. **不要把隐藏测试放进 prompt。** 隐藏测试是评估信号，不是输入。模型能看到测试，就会针对测试优化，而不是解决问题。
2. **验证器规格要版本化。** 同一个样本在不同验证器版本下可能得到不同奖励。训练记录必须能追溯到验证器版本。
3. **要做污染检查。** 训练题不能与评测集重叠，尤其是公开 benchmark。代码题还要检查题面、测试用例和参考实现是否泄漏。

## 4.2 Rollout 采样

Rollout 是 RLVR 最消耗算力的环节之一。对每个问题，策略采样多个回答（group），通常 4 到 16 个，8 个是常见起点。采样参数一般会提高温度以增加探索，例如 temperature 0.8 到 1.0，top_p 0.95 左右，同时设置最大输出长度和停止序列。

一次 rollout 需要记录：

- **token 序列和 token ID**：用于计算 logprob 和梯度。
- **每个 token 的 logprob**：策略梯度需要。
- **回答文本**：传给验证器。
- **结束原因**：正常结束、达到最大长度、命中停止符、工具调用失败。
- **采样参数和模型版本**：用于复现。
- **验证器结果和奖励**：用于训练和审计。

为什么同一个问题要采样多个回答？有三个原因：

1. **估计基线**：GRPO 用组内平均奖励作为 baseline，减少方差。
2. **增加覆盖**：复杂题目的正确解可能只出现在少数采样中，多采样提高命中率。
3. **提供对比信号**：同一问题下，正确轨迹和错误轨迹的对比，比跨问题比较更能说明“哪种行为更好”。

Rollout 工程上要关注吞吐和稳定性。常见做法是用 vLLM、SGLang 等推理引擎做连续批处理、前缀缓存和异步采样；训练与推理分离部署，定期同步权重；对超长输出设置硬上限，避免单个样本拖垮整批。对于 GRPO，如果一组采样全部正确或全部错误，组内奖励方差为零，advantage 也接近零，这批数据对策略更新没有贡献。动态采样（只保留有区分度的组）可以提高有效样本比例，但会增加调度复杂度。

## 4.3 Verifier 验证

验证器通常按“从便宜到昂贵、从格式到语义”的顺序执行：

```text
格式检查 → 答案抽取 → 归一化 → 语义/执行检查 → 安全策略检查 → 结果聚合
```

以数学题为例：

1. 检查输出是否包含约定的答案标记，例如 `\boxed{...}`。
2. 抽取最后一个答案，处理嵌套括号和 LaTeX。
3. 归一化分数、小数、单位、根式、集合、区间。
4. 用符号计算判断等价；符号计算失败时用数值代入兜底。
5. 记录验证器状态：正确、错误、超时、解析失败、内部错误。

以代码题为例：

1. 解析代码，检查语法和函数签名。
2. 编译或导入，检查依赖。
3. 运行公开测试。
4. 运行隐藏测试。
5. 做静态检查和危险调用扫描。
6. 可选：性能测试、内存测试、并发测试。

验证结果建议使用**三态而不是二态**：`correct`、`incorrect`、`verifier_error`。把验证器超时、沙箱崩溃、测试环境缺依赖误判为“模型错误”，会把噪声写进奖励，长期训练会让模型学到错误的行为。工程上应该把 `verifier_error` 的样本隔离、重试或跳过，并单独监控其比例。

## 4.4 Reward 设计

奖励是验证结果到训练信号的映射。最简单的形式是二值奖励：

```text
R = 1 if correct else 0
```

更常见的形式是多个分量的加权组合：

```text
R = w_c · 1[correct]
  + w_f · 1[format_ok]
  + w_p · process_score
  - λ_len · max(0, length - L0) / L0
  - λ_safe · 1[unsafe]
  - β · KL(πθ || π_ref)
```

| 奖励项 | 作用 | 典型量级（示意） | 主要风险 |
| --- | --- | --- | --- |
| 正确性奖励 | 主信号，鼓励答案正确 | 0 或 1 | 稀疏；验证器误判会直接放大 |
| 格式奖励 | 鼓励遵循输出约定 | 0.05 到 0.1 | 模型只学格式，不学解题 |
| 过程奖励 | 鼓励合理中间步骤 | 0 到 1 | 需要过程验证器；可能被步骤模板欺骗 |
| 长度惩罚 | 抑制无意义的长推理 | 超过阈值后线性惩罚 | 误伤需要长推理的难题 |
| 安全惩罚 | 抑制危险代码、越权工具调用 | -0.5 到 -1 | 惩罚太强会让模型过度保守 |
| KL 惩罚 | 限制策略漂移 | 由 β 控制 | 太强学不动，太弱语言退化 |

奖励设计有几个经验原则：

- **正确性应该是主信号。** 格式和过程奖励是辅助，不应该单独决定样本的好坏。
- **辅助奖励要有条件。** 例如格式奖励只在答案正确时给，或者格式奖励权重足够小，避免模型发现“输出漂亮格式就能得分”。
- **奖励尺度要稳定。** 不同验证器的输出范围要统一，否则 advantage 会被某个分量主导。
- **惩罚要可解释。** 安全惩罚、长度惩罚的触发条件要能审计，不能是黑盒。
- **KL 不是可选项。** 它防止模型为了奖励牺牲语言质量和安全性，后文会展开。

## 4.5 RL 优化

RLVR 可以使用多种强化学习算法。它们的分工不同，不是互相替代的关系。

| 算法 | 是否需要 Critic | 数据形态 | 在 RLVR 中的角色 | 主要风险 |
| --- | --- | --- | --- | --- |
| PPO | 需要 | 在线 rollout | 稳定、成熟的策略优化；RLHF 和 RLVR 都可使用 | 显存和工程复杂度高；超参数敏感 |
| GRPO | 不需要 | 在线 group rollout | 用组内统计量替代 critic；适合标量可验证奖励 | 组内全对/全错时无信号；长度归一化可能有偏 |
| REINFORCE | 不需要 | 在线 rollout | 简单基线；配合 leave-one-out 或移动平均 baseline | 方差大；训练不稳定 |
| DPO 变体 | 不需要 | 离线偏好对 | 用验证器构造正确/错误对，做离线优化 | 没有探索；分布偏移；容易过拟合偏好对 |
| 拒绝采样微调 | 不需要 | 采样后筛选 | 只保留正确轨迹做 SFT；实现最简单 | 只学正例；不利用负例；可能加剧模式坍缩 |

从目标函数看，PPO、GRPO 和 REINFORCE 都属于**策略梯度（Policy Gradient）**家族：它们用采样轨迹的回报乘以 logprob 的梯度来更新策略，区别在于 baseline 怎么估、更新幅度怎么限制、是否使用 critic。DPO 变体和拒绝采样微调则绕开了在线策略梯度，属于更便宜的替代路线。

**PPO** 是经典的策略梯度方法，使用裁剪的目标函数限制每次更新的幅度，配合价值网络估计 advantage。它在 RLHF 中被广泛使用，工程实现成熟。但在 RLVR 中，奖励是标量且通常只在序列结束时给出，价值网络的主要作用是降低方差。PPO 需要同时维护策略、参考模型、价值网络，显存开销大。

**GRPO** 去掉了价值网络，改为对同一个问题的多个采样计算组内均值和标准差，用组内相对奖励作为 advantage：

```text
A_i = (r_i - mean(r_1..r_G)) / (std(r_1..r_G) + ε)
```

这让 GRPO 更省显存，也更适合“同一问题多采样”的 RLVR 流程。DeepSeekMath 提出 GRPO 用于数学推理，DeepSeek-R1 进一步用它做规则奖励训练。GRPO 的缺点是：如果一组采样全部正确或全部错误，组内方差为零，advantage 没有信息；另外，序列级归一化和长度处理不当可能引入长度偏差。

**REINFORCE** 是最基础的策略梯度方法，直接用 `log πθ(y|x) · (R - b)` 更新，`b` 是 baseline。它实现简单，但方差大。工程上常用 leave-one-out baseline（用同组其他样本的平均奖励作为基线）或移动平均 baseline 来降低方差。对于小规模实验和快速验证，REINFORCE 是一个合理的起点。

**DPO 变体** 是离线偏好优化，不需要在线 rollout。可以用验证器把“正确答案”和“错误答案”构造成 chosen/rejected 对，然后做 DPO。它便宜、稳定，但没有探索，容易在训练分布外失效。适合作为冷启动、蒸馏或低成本替代方案，不适合完全替代在线 RL。

**拒绝采样微调** 是更简单的基线：对每个问题采样多个回答，只保留验证通过的轨迹，做普通 SFT。它没有负梯度，不会主动压低错误轨迹，但实现成本低、稳定性好，常常能拿到不错的提升。很多团队会先用它验证“数据 + 验证器”是否有效，再上在线 RL。

**KL 控制** 贯穿所有算法。KL 惩罚的作用是限制新策略偏离参考模型，防止模型为了奖励牺牲语言质量、可读性和安全性。β 太小，模型可能学会输出不可读但能通过验证器的内容；β 太大，策略几乎不更新。常见做法是从一个中等值开始，监控 KL 和奖励曲线，必要时做自适应调整。

**Advantage 估计** 决定信用分配。序列级奖励可以分配给所有 token，也可以只分配给答案部分；token 级奖励需要过程验证器。工程上常见的折中是：格式奖励和正确性奖励作用于整个序列，过程奖励作用于对应的步骤片段，长度惩罚只作用于超出阈值的部分。

## 4.6 评估与迭代

训练过程中的评估不能只看训练奖励。训练奖励上升可能意味着模型真的变强，也可能意味着模型学会了利用验证器。评估至少应包括：

- **离线评估集**：固定的、与训练集去重的题目，用于观察泛化。
- **held-out test set**：按来源、时间或难度划分，不能参与任何训练或调参。
- **pass@1 和 pass@k**：pass@1 衡量单次回答的正确率，pass@k 衡量多次采样中至少一次正确的概率。两者结合可以看出模型是“更稳定地做对”还是“碰巧蒙对”。
- **代码执行通过率**：公开测试、隐藏测试、边界测试分别统计。
- **推理一致性**：答案是否与推理过程一致，换一种问法是否还能做对。
- **安全回归测试**：危险代码、越权工具调用、提示注入、格式漏洞。
- **能力回归测试**：通用对话、指令遵循、语言质量是否退化。

每次评估都要记录模型版本、验证器版本、采样参数和评估脚本版本。否则，两次评估的差异可能来自评估环境变化，而不是模型变化。

评估结果应该驱动数据迭代：哪些题型错误率高，就补充同类数据；哪些验证器误判多，就优先修验证器；哪些奖励分量被模型利用，就调整权重或增加对抗测试。RLVR 不是“训练一次就结束”，而是一个数据、验证器、奖励和模型共同迭代的闭环。

# 五、Verifier：RLVR 的核心

## 5.1 为什么 Verifier 决定奖励质量

在传统 RLHF 中，奖励模型是训练的核心资产；在 RLVR 中，这个位置由验证器占据。验证器决定了“什么行为会被奖励”，而策略会朝着奖励高的方向优化。如果验证器有系统性漏洞，模型不会“忽略”它，反而会精准地找到并利用它。这就是为什么 RLVR 工程里常见的顺序是：**先建验证器，再建训练器。**

验证器不只是一个函数，它是一套包含规范、执行环境、版本管理和审计的系统。一个好的验证器要能回答三个问题：

1. **判据是什么？** 正确性如何定义，边界情况如何处理。
2. **判据是否可靠？** 在人工审核集上，误判率有多高。
3. **判据是否安全？** 执行模型生成的代码或命令时，会不会影响宿主机、泄漏数据、被利用。

## 5.2 Verifier 的类型

### 5.2.1 规则型 Verifier

规则型验证器用显式的语法或结构规则判断输出。常见形式包括：

- **正则表达式**：抽取答案、检查固定格式、识别危险调用。
- **JSON Schema**：检查字段、类型、枚举、必填项、额外字段。
- **YAML / TOML / XML 解析器**：检查语法和结构。
- **格式检查**：日期、邮箱、URL、货币、单位、代码块标记。
- **字段约束**：长度、范围、正则模式、字段之间的依赖关系。

规则型验证器的优点是快、确定、便宜、容易审计。缺点是脆、容易绕过、通常不检查语义。例如，一个 JSON 通过了 Schema，不代表里面的业务数据正确；一个正则匹配到了答案，不代表答案真的对。

规则型验证器适合做**第一层过滤**：先检查格式和结构，把明显不合格的输出淘汰掉，再把剩下的交给更昂贵的语义验证器。它不适合单独作为复杂推理任务的唯一奖励来源。

### 5.2.2 答案型 Verifier

答案型验证器把模型输出与参考答案比较。难点不在“比较”，而在“归一化”和“等价判断”。

- **Exact match**：字符串完全相等。简单，但对格式极其敏感。
- **数值比较**：解析成数字后比较，允许一定误差。要处理整数、小数、科学计数法、百分比、单位。
- **多答案归一化**：把 `x=5`、`5`、`\boxed{5}`、`5.0` 统一成同一种表示。
- **单位换算**：`1 km` 和 `1000 m` 应该等价；但 `1` 和 `1 m` 不应该等价。
- **集合比较**：多解问题要比较集合，而不是顺序；要处理重复元素和空集。
- **区间比较**：`[0, 1]` 和 `(0, 1)` 不同；端点的开闭必须保留。
- **数学表达式等价**：用符号计算判断两个表达式是否恒等，或在一定定义域内等价。

答案型验证器的关键是“不要过度归一化”。把单位、符号、定义域、多解顺序全部抹平，会把错误答案判成正确。归一化规则应该有明确的适用范围，并且可测试。

### 5.2.3 执行型 Verifier

执行型验证器真正运行模型生成的代码、SQL 或工具调用，检查执行结果。它是最强的信号之一，因为“能跑通”比“看起来对”更难伪造。常见形式包括：

- **编译 / 解释执行**：检查语法、导入、运行时错误。
- **单元测试**：公开测试、隐藏测试、边界测试、随机测试。
- **沙箱执行**：在隔离环境中运行，限制网络、文件系统、CPU、内存和时间。
- **SQL 查询结果比较**：在只读副本上执行，比较结果集。
- **API 调用结果验证**：在模拟环境或测试环境中调用，检查返回值和副作用。

执行型验证器的成本更高，工程更复杂，但它能捕捉到静态检查发现不了的问题。它也有盲区：测试覆盖不足、测试本身有 bug、代码通过测试但逻辑错误、环境不确定导致 flaky。

### 5.2.4 符号型 Verifier

符号型验证器用数学或逻辑工具判断正确性：

- **CAS（计算机代数系统）**：SymPy、Mathematica、Maple 等，用于化简、求导、积分、解方程、比较表达式。
- **定理证明器**：Lean、Coq、Isabelle，用于检查形式化证明。
- **类型检查器**：检查程序或证明的类型正确性。
- **SMT Solver**：Z3、CVC5，用于可判定理论内的约束满足和等价性检查。

符号型验证器的可靠性取决于具体工具：定理证明器和类型检查器的检查在内核与类型系统正确的前提下是可信的；CAS 则依赖化简能力，可能失败、超时或因为假设不同而给出不同结果。它们共同的局限是覆盖范围有限：一般数学表达式的等价性判断在理论上不可判定，形式化证明需要把题目和证明都写成证明助手能理解的形式，SMT 只适用于可判定的理论片段。

这类验证器适合高价值、低容错的场景：形式化数学、编译器验证、协议验证、关键代码的属性检查。对于大规模、开放域的数学题，通常还是以“符号计算 + 数值兜底 + 人工抽检”的组合为主。

### 5.2.5 模型辅助 Verifier

模型辅助验证器用另一个模型（LLM Judge、Reward Model、Critic）判断输出质量。它适合无法用规则完全表达的语义判断，例如：

- 两个自然语言答案是否语义等价。
- 一段推理是否逻辑连贯。
- 一个工具调用计划是否合理。
- 一个 Agent 轨迹是否完成了用户目标。

但模型辅助验证器不是“客观验证器”。它可能被提示注入、被冗长表达影响、被自信语气影响、偏好自己的输出。使用时要遵守几条原则：

1. **规则优先**：能用规则、执行或符号检查的，不要先用 LLM。
2. **结构化评分**：给 Judge 明确的评分 rubric、输出格式和边界条件，减少自由发挥。
3. **多裁判 / 位置交换**：对成对比较交换顺序，使用多个模型或多次采样，降低位置偏差。
4. **校准与抽检**：在人工标注集上测 Judge 的准确率、误判率和一致性；定期人工抽检。
5. **不要把 Judge 作为唯一奖励来源**：尤其是在高风险任务上，必须有规则或人工兜底。

## 5.3 Verifier 的质量要求

| 要求 | 含义 | 工程做法 |
| --- | --- | --- |
| 准确性 | 误判率和漏判率低 | 建立人工审核集，定期测 precision / recall |
| 稳定性 | 同一输入在同一版本下输出一致 | 固定依赖版本、随机种子、执行环境 |
| 可复现性 | 任意一次奖励都能追溯和重放 | 记录验证器版本、测试用例、运行日志 |
| 低误判率 | 不把正确判错，也不把错误判对 | 边界用例测试、对抗样本、人工抽检 |
| 抗 Reward Hacking | 模型难以利用漏洞 | 隐藏测试、随机测试、多验证器、异常检测 |
| 执行安全 | 运行模型代码不会危害宿主机 | 沙箱、网络隔离、资源限制、审计 |
| 成本可控 | 延迟和算力在预算内 | 分层验证、缓存、并行、超时控制 |
| 覆盖充分 | 能覆盖主要错误模式 | 测试用例分层、属性测试、变异测试 |

其中“准确性”要分两个方向看：**假阳性**（把错误判成正确）会让模型学会错误行为；**假阴性**（把正确判成错误）会压低正确轨迹的概率，浪费样本。两者都会损害训练，但假阳性通常更危险，因为模型会主动放大它。

在人工审核集上，可以用混淆矩阵估算验证器的 precision 和 recall：precision 是“判为正确的样本里真正正确的比例”，recall 是“真正正确的样本里被判为正确的比例”。RLVR 通常更关心 precision，因为假阳性会被策略反复利用；recall 低一些主要浪费样本，precision 低则可能把训练方向带偏。两者都要按任务类型、难度和验证器版本分开统计，不能只看一个总体数字。

## 5.4 Verifier 常见问题与缓解方案

| 常见问题 | 典型表现 | 工程缓解方案 |
| --- | --- | --- |
| 标准答案格式不统一 | `5`、`5.0`、`x=5`、`\boxed{5}` 混用 | 统一答案抽取协议；维护归一化规则库；对无法解析的样本标记为 `verifier_error` |
| 等价答案难判断 | `1/2` 与 `0.5`、`\sqrt{2}` 与 `1.414`、不同形式的集合 | 符号计算 + 数值代入 + 人工审核集；对超时和不确定样本降级处理 |
| 测试用例覆盖不足 | 代码通过公开测试，但边界输入错误 | 隐藏测试、随机测试、属性测试、变异测试；按错误模式补充用例 |
| 代码通过测试但实际错误 | 硬编码、投机取巧、测试环境漏洞 | 隐藏测试、输入随机化、静态分析、代码审查、对抗测试 |
| LLM Judge 主观偏差 | 长度偏好、位置偏好、自我偏好、被提示注入 | 结构化 rubric、位置交换、多裁判、校准、规则兜底 |
| Verifier 被模型利用 | 输出特殊格式、枚举答案、读取测试文件、绕过检查 | 隐藏测试、随机化、答案格式约束、沙箱、异常检测、红队测试 |
| 沙箱逃逸风险 | 模型代码访问网络、读取密钥、耗尽资源 | 微虚拟机 / gVisor、网络隔离、只读文件系统、cgroups、seccomp、审计 |
| 验证器错误被当成模型错误 | 超时、缺依赖、环境崩溃被计为 0 分 | 三态结果、错误隔离、重试、监控 `verifier_error` 比例 |

一个实用的设计是**分层验证**：

```text
第一层：格式与结构（便宜、快速、可并行）
第二层：答案等价 / 单元测试（中等成本）
第三层：符号检查 / 形式化证明（高成本、高置信）
第四层：模型裁判 / 人工抽检（处理长尾和歧义）
```

每一层都输出结构化结果，最终由 Reward Calculator 聚合。低层失败可以短路，但短路原因要记录，便于分析模型的错误模式。

# 六、奖励设计：从二值奖励到过程奖励

## 6.1 二值奖励

二值奖励是最简单的形式：

```text
正确 → 1
错误 → 0
```

优点是简单、客观、容易实现、容易审计。缺点是奖励稀疏：在一道难题上，模型可能采样 8 次全部错误，所有奖励都是 0，策略梯度没有区分度。它也无法区分“接近正确”和“完全错误”，学习效率低。

二值奖励适合：

- 验证器非常可靠、答案非黑即白的任务。
- 冷启动阶段，先验证数据与验证器闭环。
- 作为主信号，配合 group sampling 和课程学习使用。

在 GRPO 中，二值奖励配合组内归一化可以工作，但前提是一组里既有正确也有错误。如果题目太难或太简单，组内全错或全对，样本就没有训练价值。工程上可以通过难度分层、动态采样和题目过滤来缓解。

## 6.2 分级奖励

分级奖励把正确性拆成多个档次，例如：

```text
格式正确：0.1
推理步骤合理：0.3
最终答案正确：1.0
安全违规：-1.0
```

分级奖励提供更细的反馈，但也带来一个风险：**模型会优先优化容易得分的部分。** 如果格式奖励 0.1、答案奖励 1.0，模型可能很快学会输出正确格式，却在答案上停滞；如果过程奖励 0.3 只看“有没有分步骤”，模型可能学会写一堆看似合理的步骤，却不解决问题。

避免这种退化的方法：

1. **正确性是门槛**：格式或过程奖励只在答案正确时给，或者权重远小于正确性。
2. **奖励单调**：答案正确但格式差，应该比答案错误但格式好得分高。
3. **过程奖励要独立验证**：不能只看“步骤数量”或“关键词”，要看步骤是否逻辑有效。
4. **监控分项奖励分布**：如果某个分项的方差远大于其他项，模型可能在钻这个空子。

## 6.3 过程奖励（Process Reward）

过程奖励对中间推理步骤评分，而不是只看最终答案。典型做法包括：

- **人工步骤标注**：给每一步标“正确 / 错误 / 中性”，训练过程奖励模型（PRM）。
- **蒙特卡洛估计**：从某个中间步骤继续采样，看最终正确率，作为该步骤的“进展分数”。
- **自动过程验证器**：用规则、符号检查或另一个模型判断步骤是否合法。
- **步骤一致性检查**：检查每一步的结论是否由前一步推出。

过程奖励的优势是细粒度，能缓解长链推理中的信用分配问题。Lightman 等人的工作表明，步骤级验证在数学推理上可以比结果级验证更有效。但过程奖励的工程成本更高：

- 需要过程标注或可靠的过程验证器。
- 步骤边界难以统一定义。
- PRM 本身可能被模型欺骗，例如写出“看起来合理”的步骤。
- 过程奖励与结果奖励的权重需要调参，否则模型可能优化过程而忽略答案。

一个务实的组合是：**结果奖励为主，过程奖励为辅，过程奖励只在可独立验证的步骤上使用。** 例如，数学题中的代数变形可以用符号计算检查，代码题中的每个函数可以用单元测试检查；这些步骤的过程奖励比“让 LLM 给步骤打分”可靠得多。

## 6.4 结果奖励（Outcome Reward）

结果奖励只看最终答案：

```text
R = f(最终答案, 参考答案 / 测试 / 环境终态)
```

它最容易自动验证，适合大规模训练。DeepSeek-R1-Zero 主要使用结果奖励（答案正确性加格式），证明了在足够强的基座和足够多的采样下，结果奖励可以驱动推理能力提升。

结果奖励的局限是信用分配：最终答案错了，模型不知道是哪一步错了；最终答案对了，也不代表推理过程正确。这可能导致两种退化：

- **答案对但推理错**：模型可能通过猜测、枚举、记忆或错误的启发式得到正确答案。如果训练只奖励答案，这类行为会被强化。
- **推理冗长但答案对**：模型可能学会写很长的推理来“碰”答案，而不是真正解决问题。

缓解方法包括：过程验证、答案与推理一致性检查、长度惩罚、对抗扰动（换数字、换问法）以及人工抽检。

对三种典型情况，建议的奖励策略是：

- **答案对、推理错**：结果奖励可以给，但要用扰动测试、过程检查或人工抽检标记这类样本；如果比例高，应该在训练中降低权重，或者加入“换数字/换问法”的对抗变体，避免强化投机行为。
- **答案错、推理对**：结果奖励为 0；如果过程可以独立验证，可以给少量过程分，但不应该高于正确答案的奖励，否则模型会满足于“过程漂亮”而不追求最终正确。
- **部分正确**：分级奖励可以给部分分，但正确性必须是主信号；部分分只用于缓解稀疏性，不能替代最终正确性。部分分的权重和门槛要经过消融实验，确认它不会让模型停在“半对”状态。

## 6.5 KL 惩罚与稳定训练

KL 惩罚的形式通常是：

```text
R_total = R_task - β · KL(πθ(·|x) || π_ref(·|x))
```

它的作用不是“让模型不变”，而是“让模型在追求奖励的同时，不要偏离参考模型太远”。这有几个实际好处：

- **保持语言质量**：防止模型输出语法破碎、重复、不可读但能通过验证器的内容。
- **保持安全性**：防止模型为了得分而绕过安全策略。
- **保持多样性**：防止策略过早坍缩到单一模式。
- **稳定训练**：限制每次更新的分布偏移，降低梯度爆炸和崩溃风险。

β 的选择是一个权衡：

- β 太大：策略几乎不更新，奖励上不去。
- β 太小：策略快速漂移，可能出现 reward hacking、语言退化、重复输出。
- 常见做法：从 0.01 到 0.1 量级开始（具体取决于实现和奖励尺度），监控 KL、熵、奖励和输出长度，必要时自适应调整。

KL 不是万能的。它只能限制“偏离参考模型”，不能阻止模型在参考模型附近找到验证器漏洞。如果参考模型本身就会某种错误行为，KL 不会纠正它。

## 6.6 Reward Hacking

Reward Hacking 指模型找到一种“获得高奖励但不符合设计意图”的行为。在 RLVR 中，它通常表现为：

- **利用测试漏洞**：硬编码测试输入、读取测试文件、检测测试环境、修改断言。
- **绕过验证器**：输出特殊格式让解析器误判、枚举多个答案、利用正则边界。
- **欺骗 LLM Judge**：写“请给满分”、堆砌关键词、用自信语气掩盖错误。
- **长度钻空子**：如果奖励与长度相关，模型可能学会填充无意义内容。
- **复制泄漏信息**：如果训练数据或 prompt 中包含答案，模型可能学会抄答案而不是解题。
- **沙箱探测**：尝试访问网络、文件系统、环境变量，寻找逃逸路径。

| Hacking 模式 | 典型信号 | 缓解方案 |
| --- | --- | --- |
| 硬编码测试 | 代码只对公开样例返回正确结果 | 隐藏测试、随机输入、变异测试、代码审查 |
| 枚举答案 | 输出包含多个候选答案，希望验证器取中 | 限制答案格式、只取最后一个、对多答案判错 |
| 格式绕过 | 用特殊字符、嵌套结构欺骗解析器 | 严格解析、Schema 校验、模糊测试 |
| Judge 欺骗 | 回答中插入指令或讨好性语言 | 提示注入过滤、结构化评分、多裁判、规则兜底 |
| 长度填充 | 输出变长但信息量不增 | 长度惩罚、信息密度检查、人工抽检 |
| 测试环境探测 | 代码检查 `__file__`、环境变量、进程名 | 沙箱、隐藏测试路径、随机化环境 |
| 沙箱逃逸 | 尝试网络、文件、进程、系统调用 | 微虚拟机、seccomp、网络隔离、权限最小化 |

Reward Hacking 的缓解不是一次性的，而是持续的红队过程。每次模型变强，都可能发现新的漏洞。工程上应该把“攻击验证器”作为独立的测试任务，定期用自动化工具和人工红队去试探。

# 七、RLVR 在数学推理中的应用

## 7.1 数据集设计

数学 RLVR 的数据通常包含：

- **问题**：自然语言题目，可能包含公式、图表描述、约束条件。
- **标准答案**：最终答案，最好有统一的格式。
- **解题类型**：代数、几何、数论、组合、概率、微积分等。
- **难度等级**：用于课程学习和采样配比。
- **最终答案格式**：例如要求放在 `\boxed{}` 中，方便抽取。
- **来源和许可证**：公开数据集、内部题库、合成数据要分开标记。

常用公开数据包括 GSM8K（小学应用题）、MATH（竞赛级数学）、AIME（高难度竞赛题）、OlympiadBench 等。使用时要检查许可证、题目质量和答案正确性。公开数据还可能被模型见过，需要做污染检查，或者用时间切分、改写题目等方式降低记忆效应。

数据配比很重要。全用难题，模型采样全错，没有学习信号；全用简单题，模型很快饱和，学不到新能力。常见做法是按难度分层，动态调整简单、中等、难题的比例，或者用课程学习从易到难。

## 7.2 答案归一化

数学答案的格式差异是验证器最大的敌人之一。归一化通常包括：

- 去除首尾空白、`$`、`\text{}`、`\mathrm{}` 等包装。
- 统一分数和小数：`1/2`、`0.5`、`50%` 在合适语境下等价。
- 统一根式：`\sqrt{2}`、`2^{1/2}`、`1.414...` 需要区分精确值和近似值。
- 统一单位：`1 km` 与 `1000 m` 等价，但 `1` 与 `1 m` 不等价。
- 统一集合和区间：`{1, 2}` 与 `{2, 1}` 等价；`[0,1]` 与 `(0,1)` 不等价。
- 处理多解：`x=1,2`、`x \in \{1,2\}`、`1 或 2` 要统一成集合比较。
- 处理特殊答案：`无解`、`任意实数`、`不存在`、`\varnothing`。

归一化规则要可测试、可版本化。每次修改规则，都要在人工审核集上回归，避免把原本正确的样本判错。对于无法可靠归一化的答案，应该标记为 `verifier_error` 或交给人工，而不是强行判分。

## 7.3 等价性验证

数学等价性验证通常分三层：

1. **精确符号比较**：用 SymPy 等 CAS 化简 `candidate - reference`，判断是否为 0。适合多项式、分式、根式、三角函数等。
2. **数值代入**：在若干随机点上代入候选式和参考答案，比较数值。适合符号化简失败的情况，但要注意定义域、奇点、分支切割和浮点误差。
3. **结构/语义检查**：对于集合、区间、矩阵、向量、概率分布等，按结构比较，而不是按字符串比较。

SymPy 的 `simplify`、`equals`、`nsimplify` 都不是万能的：化简可能很慢，可能失败，可能因为假设不同而给出不同结果。工程上要设置超时，准备数值兜底，并对高风险样本做人工审核。

一个简化的示意：

```python
import sympy as sp
from sympy.parsing.sympy_parser import parse_expr

def math_equiv(candidate: str, reference: str, timeout=2.0) -> bool:
    try:
        a = parse_expr(candidate, evaluate=True)
        b = parse_expr(reference, evaluate=True)
        diff = sp.simplify(a - b)
        if diff == 0:
            return True
        # 数值兜底：避开 0 和奇异点
        for x in [0.37, 1.13, 2.71, -1.41]:
            va = complex(a.subs(sp.Symbol("x"), x))
            vb = complex(b.subs(sp.Symbol("x"), x))
            if abs(va - vb) > 1e-8 * max(1.0, abs(vb)):
                return False
        return True
    except Exception:
        return False
```

这段代码只用于示意。真实系统要处理多变量、定义域、超时、LaTeX 解析、安全性（不要对不可信输入直接 `eval`）和版本兼容。

## 7.4 奖励设计

数学 RLVR 的奖励通常以最终答案正确性为主：

```text
R = 1.0 · 1[answer_correct]
  + 0.05 · 1[format_ok]
  - 0.01 · length_penalty
```

格式奖励鼓励模型把答案放在约定位置，方便抽取；长度惩罚抑制无意义的超长推理。过程一致性奖励可以用符号检查中间步骤，但实现成本高，通常只在高价值任务上使用。

如果使用过程奖励，建议只对可独立验证的步骤给分，例如方程变形、代数化简、数值计算。对于“思路是否巧妙”这类主观判断，不要用 LLM Judge 单独给高分，否则模型会学会写“看起来聪明”的步骤。

## 7.5 常见问题

- **答案对但推理错**：模型可能猜中、枚举、记忆或用了错误但巧合的推导。缓解：换数字、换问法、要求展示关键步骤、过程验证、人工抽检。
- **推理看似合理但最终错**：这是最典型的错误。最终答案奖励会压低这类轨迹，但如果验证器只看答案，模型可能不知道错在哪。缓解：过程验证、错误分类、针对性数据补充。
- **多解问题**：参考答案可能只列了一个解，模型给出另一个正确解却被判错。缓解：维护完整解集，或使用“代入原题验证”的方式判断候选解是否合法。
- **题目本身有歧义**：不同理解对应不同答案。缓解：数据清洗、人工审核、在 prompt 中明确约定、把歧义题从训练集移除。
- **答案抽取失败**：模型没有按格式输出，或 LaTeX 嵌套导致解析失败。缓解：宽松抽取 + 严格格式奖励、解析器测试、失败样本分析。
- **验证器超时**：复杂表达式化简过慢。缓解：超时控制、数值兜底、缓存、异步验证。

# 八、RLVR 在代码生成中的应用

## 8.1 代码题样本格式

代码 RLVR 的样本通常包含：

- **problem statement**：题目描述、输入输出说明、约束条件。
- **function signature**：函数名、参数、返回类型，方便自动调用。
- **public tests**：公开测试，可能出现在题面中。
- **hidden tests**：隐藏测试，模型不可见，用于评估真实正确性。
- **constraints**：时间限制、内存限制、允许的库、是否允许网络。
- **difficulty**：难度等级，用于采样和课程学习。
- **reference solution**：参考实现，可用于生成测试或对比，但不能泄漏给模型。

```json
{
  "id": "code-000789",
  "problem": "给定整数数组 nums 和目标值 target，返回和为 target 的两个数的下标。",
  "signature": "def two_sum(nums: list[int], target: int) -> list[int]:",
  "public_tests": [
    {"args": [[2, 7, 11, 15], 9], "expected": [0, 1]}
  ],
  "hidden_tests": "hidden/code-000789.json",
  "constraints": {
    "time_limit_ms": 2000,
    "memory_mb": 256,
    "network": false,
    "allowed_imports": ["typing", "collections", "math"]
  }
}
```

## 8.2 执行型 Verifier

代码验证通常分层进行：

| 层级 | 检查内容 | 失败含义 | 成本 |
| --- | --- | --- | --- |
| 语法 / 编译 | 能否解析、编译、导入 | 代码不可执行 | 低 |
| 公开测试 | 题面给出的样例 | 基本功能错误 | 低 |
| 隐藏测试 | 未公开的边界和随机用例 | 泛化不足或逻辑错误 | 中 |
| 静态分析 | 危险调用、类型问题、代码坏味 | 安全或质量问题 | 低到中 |
| 安全扫描 | 网络、文件、进程、系统调用 | 沙箱风险 | 中 |
| 性能测试 | 时间、内存、并发 | 复杂度不达标 | 高 |

验证顺序一般是“便宜的先跑”：语法 → 公开测试 → 隐藏测试 → 静态/安全 → 性能。任何一层失败都可以短路，但失败原因要记录，用于分析模型的错误模式。

执行型验证器要保证**确定性**：固定随机种子、固定依赖版本、固定输入顺序、固定超时。非确定性测试会让同一个代码在不同时间得到不同奖励，训练信号会变得噪声很大。

## 8.3 奖励设计

代码 RLVR 的奖励可以分级：

```text
编译通过：0.1
公开测试通过：0.3
隐藏测试通过：1.0
性能达标：+0.1
危险调用：-1.0
```

但要注意：**不要奖励“只编译通过”太多。** 如果编译奖励太高，模型可能学会输出语法正确但逻辑空洞的代码。正确性应该由隐藏测试主导，公开测试只是中间信号。

对于代码可读性，可以用静态检查或 LLM Judge 给少量奖励，但不建议作为主信号。代码 RLVR 的目标是“能正确运行”，可读性是次要目标；把两者混在一起，容易让模型为了“看起来整洁”牺牲正确性。

## 8.4 工程安全

运行模型生成的代码是 RLVR 中最危险的部分。必须假设代码是恶意的，至少是不可信的。常见防护包括：

- **沙箱隔离**：使用微虚拟机（如 Firecracker）、用户态内核（如 gVisor）或专用沙箱（如 nsjail）隔离执行环境。
- **网络隔离**：默认禁止网络访问；确需访问时，通过白名单代理，并记录所有请求。
- **文件系统隔离**：只读根文件系统，临时目录用 tmpfs，任务结束后销毁；不挂载宿主目录和密钥。
- **资源限制**：CPU 时间、内存、进程数、文件大小、输出大小、打开文件数都要限制，防止 fork bomb、内存爆炸、磁盘写满。
- **系统调用过滤**：用 seccomp 限制危险系统调用；但 seccomp 不是万能的，要和命名空间、cgroups 配合。
- **超时和杀进程**：设置硬超时，超时后杀死整个进程组，清理残留资源。
- **审计日志**：记录代码、输入、输出、退出码、资源使用、系统调用异常，便于事后分析。
- **最小权限**：验证服务以低权限用户运行，不能访问训练集群的凭据、模型权重和内部网络。

一个常见的错误是“在训练容器里直接 `exec` 模型代码”。这会让模型代码和训练进程共享文件系统、网络和环境变量，一旦被利用，后果不只是奖励错误，而是整个训练集群被攻破。

## 8.5 常见问题

- **过拟合公开测试**：模型记住样例输出，遇到隐藏测试就失败。缓解：隐藏测试、随机输入、变异测试、按测试通过率分层采样。
- **硬编码样例**：代码里写死输入输出。缓解：随机化输入、检查代码是否包含测试常量、静态分析、人工抽检。
- **利用执行环境漏洞**：读取测试文件、修改断言、检测测试框架、访问网络。缓解：沙箱、隐藏测试路径、随机化环境、禁止文件系统访问。
- **非确定性测试**：随机、时间、并发、浮点误差导致结果不稳定。缓解：固定种子、容差比较、重复运行、标记 flaky 测试。
- **依赖外部库不可控**：模型使用未安装的库，或库版本变化导致行为不同。缓解：固定镜像、允许列表、依赖检查、版本锁定。
- **测试覆盖不足**：边界条件、空输入、大规模输入没覆盖。缓解：属性测试、模糊测试、按错误模式补充用例。
- **代码通过但复杂度不达标**：暴力解法通过小测试，超时于大测试。缓解：性能测试、复杂度约束、大规模随机用例。

# 九、RLVR 在结构化输出与工具调用中的应用

RLVR 不只适用于数学和代码。任何“正确性可以被程序检查”的任务，都可以构造可验证奖励。结构化输出、SQL、工具调用和 Agent 任务是工程系统中最常见的四类。

## 9.1 结构化输出

结构化输出包括 JSON、YAML、XML、CSV、表格、API 请求参数、配置文件和表单数据。验证方式可以分层：

1. **语法校验**：能否解析成目标格式。
2. **Schema 校验**：字段、类型、必填项、枚举、范围、额外字段。
3. **业务规则校验**：字段之间的依赖、跨字段约束、单位一致性、时间范围。
4. **下游系统校验**：把输出交给真实的 API、数据库或服务做 dry-run，检查是否被接受。
5. **语义校验**：字段值是否与输入一致，是否有幻觉、遗漏或矛盾。

以 JSON 为例，Schema 要尽量严格：

```json
{
  "type": "object",
  "required": ["order_id", "items", "total"],
  "additionalProperties": false,
  "properties": {
    "order_id": {"type": "string", "pattern": "^ORD-[0-9]{8}$"},
    "items": {
      "type": "array",
      "minItems": 1,
      "items": {
        "type": "object",
        "required": ["sku", "qty"],
        "additionalProperties": false,
        "properties": {
          "sku": {"type": "string"},
          "qty": {"type": "integer", "minimum": 1}
        }
      }
    },
    "total": {"type": "number", "minimum": 0}
  }
}
```

Schema 太松是常见问题。例如只检查“是对象”，不检查必填字段，模型就会输出缺字段的 JSON；只检查“是数字”，不检查范围，模型就会输出负数价格。业务规则也要显式化：总价是否等于明细之和、货币是否一致、日期是否合法。

结构化输出的奖励可以是二值的（通过 / 不通过），也可以是分级的（语法 0.1、Schema 0.3、业务规则 1.0）。但同样要避免模型只优化语法层。

## 9.2 SQL 生成

SQL 任务的验证比 JSON 复杂，因为 SQL 可以执行、有副作用、依赖数据库状态。一个安全的验证流程是：

1. **语法解析**：用 SQL 解析器检查语法，提取表名、列名、语句类型。
2. **权限检查**：只允许 `SELECT`，禁止 `INSERT`、`UPDATE`、`DELETE`、`DROP`、`ALTER` 等；限制可访问的表和列。
3. **只读执行**：在只读副本或临时数据库上执行，设置语句超时和行数上限。
4. **结果比较**：把模型查询的结果与参考查询的结果比较。要注意列顺序、行顺序、NULL 语义、重复行和浮点误差。
5. **成本检查**：用 `EXPLAIN` 检查是否全表扫描、笛卡尔积、超大中间结果。
6. **安全策略**：检查是否访问敏感表、是否包含注释注入、是否使用危险函数。

结果比较通常用**多重集比较**（multiset equality），而不是简单排序后比较。对于 `NULL`，要使用 SQL 的三值逻辑或显式归一化。对于浮点数，要设置容差。对于 `ORDER BY` 有明确要求的查询，才比较顺序。

SQL 的奖励设计可以是：可执行 0.1、结果正确 1.0、只读合规 0.1、性能达标 0.1、危险语句 -1.0。安全合规应该是硬约束，不能只用软奖励。

## 9.3 Tool Calling

工具调用任务要求模型选择正确的工具、填写正确的参数、按合理顺序调用，并根据返回结果决定下一步。验证维度包括：

- **工具选择**：是否选了正确的工具，是否遗漏必要工具，是否调用了不该调用的工具。
- **参数正确性**：参数名、类型、必填项、取值范围、单位、格式。
- **调用顺序**：前置条件是否满足，是否在错误的状态下调用。
- **结果满足度**：工具返回后，任务目标是否达成。
- **权限与安全**：是否越权、是否访问敏感资源、是否执行危险操作。
- **效率**：是否重复调用、无效循环、过多步骤。

验证方式可以是：

- **Schema 校验**：检查工具调用 JSON 的结构和参数类型。
- **模拟环境**：在 mock 环境中执行，检查状态变化。
- **真实环境**：在隔离的测试环境中执行，检查副作用。
- **轨迹规则**：检查调用序列是否满足前置条件、是否在预算内。
- **终态检查**：检查数据库、文件、API 状态是否达到目标。

模拟环境和真实环境的一致性是一个关键风险。mock 太简单，模型会学会“骗过 mock”；mock 太复杂，维护成本高。常见做法是核心工具用真实环境，边缘工具用 mock，并定期做一致性测试。

## 9.4 Agent 任务

Agent 任务把多轮工具调用、环境交互和最终目标组合在一起。验证不能只看最终回答，还要看轨迹：

| 验证维度 | 检查内容 | 失败模式 |
| --- | --- | --- |
| 任务完成 | 最终状态是否满足目标 | 回答声称完成，但环境没变 |
| 中间步骤 | 工具调用是否必要、顺序是否合理 | 无效循环、重复调用、跳过关键步骤 |
| 效率 | 步数、token、时间是否在预算内 | 无限重试、绕远路 |
| 安全 | 是否越权、是否触发危险操作 | 删除数据、泄露信息、调用未授权 API |
| Trace 完整性 | 是否记录了输入、输出、状态变化 | 无法归因、无法复现 |
| 可恢复性 | 失败后是否能回滚或重试 | 部分副作用残留 |

Agent 任务的奖励通常是稀疏的：只有最终成功才给高分。这会带来长程信用分配问题。工程上可以加入中间信号，例如“关键工具调用成功”“状态检查通过”“无安全违规”，但这些信号要谨慎设计，避免模型只刷中间分。

Agent 环境的可复现性也很重要。每次 rollout 前要重置环境；工具调用要有幂等性或回滚机制；外部依赖要固定版本；失败要能重放。否则，同一个策略在不同时间会得到不同奖励，训练信号会变得不可信。

# 十、RLVR 工程实现架构

## 10.1 总体架构

一个可落地的 RLVR 训练系统可以拆成八个模块：

```text
┌────────────────────┐
│  Dataset Manager   │  题目、答案、测试、元数据、切分、版本
└─────────┬──────────┘
          │ 样本
          ▼
┌────────────────────┐        ┌────────────────────┐
│   Rollout Engine   │───────▶│   Verifier Service │
│  并行采样、logprob  │        │ 数学/代码/格式/工具 │
└─────────┬──────────┘        └─────────┬──────────┘
          │ 轨迹                        │ 验证结果
          │                             ▼
          │                   ┌────────────────────┐
          └──────────────────▶│  Reward Calculator │
                              │ 聚合、惩罚、KL      │
                              └─────────┬──────────┘
                                        │ 奖励
                                        ▼
                              ┌────────────────────┐
                              │     RL Trainer     │
                              │ PPO / GRPO / ...   │
                              └─────────┬──────────┘
                                        │ 权重
                                        ▼
                              ┌────────────────────┐
                              │    Checkpoints     │
                              └─────────┬──────────┘
                                        │
                                        ▼
                              ┌────────────────────┐
                              │ Evaluation Harness │
                              │ held-out、pass@k   │
                              └─────────┬──────────┘
                                        │
                                        ▼
                              Deployment Candidate
```

旁路模块：

- **Experiment Tracker**：记录超参数、数据版本、验证器版本、奖励曲线、评估结果、模型版本。
- **Safety Sandbox**：为代码执行、SQL、工具调用和 Agent 环境提供隔离、资源限制、权限控制和审计。

主数据流可以概括为：

```text
数据集 → Rollout → Verifier → Reward → RL Trainer → Checkpoint → Evaluation → 部署候选
```

但实际系统不是一个单向管道，而是一个闭环：评估结果会反馈到数据管理（补数据、调难度）、验证器（修误判、补测试）、奖励设计（调权重、加惩罚）和训练配置（调超参数、换算法）。

## 10.2 模块职责

| 模块 | 核心职责 | 输入 | 输出 | 主要失败模式 |
| --- | --- | --- | --- | --- |
| Dataset Manager | 管理训练/验证/测试集、元数据、去重、污染检查、采样配比 | 原始题目、答案、测试、规则 | 标准化样本、切分、版本 | 数据泄漏、重复题、难度失衡 |
| Rollout Engine | 并行采样、记录 logprob、token、轨迹、结束原因 | 样本、模型权重、采样参数 | 轨迹批次 | 吞吐不足、超时、权重不同步 |
| Verifier Service | 执行验证规则、返回结构化结果 | 轨迹、验证器规格 | correct / incorrect / error | 误判、超时、沙箱故障、被攻击 |
| Reward Calculator | 聚合验证信号、加惩罚、算 KL、归一化 | 验证结果、奖励配置、logprob | 标量奖励、分项日志 | 权重失衡、尺度漂移、奖励作弊 |
| RL Trainer | 策略更新、梯度训练、checkpoint | 轨迹、奖励、参考模型 | 新权重、训练指标 | 梯度爆炸、策略坍缩、显存不足 |
| Evaluation Harness | 离线评估、pass@k、回归测试、安全测试 | 模型、评估集、脚本 | 评估报告、门禁结果 | 评测污染、指标误导、回归漏检 |
| Experiment Tracker | 记录配置、指标、产物、血缘 | 各模块日志 | 可查询的实验记录 | 记录缺失、版本不可追溯 |
| Safety Sandbox | 隔离执行、资源限制、权限控制、审计 | 代码、SQL、工具调用 | 执行结果、审计日志 | 逃逸、资源耗尽、数据泄漏 |

## 10.3 模块间契约

要让系统可复现、可排查，模块之间需要有清晰的数据契约：

- **样本记录**：`id`、`prompt`、`reference`、`verifier_spec`、`metadata`、`split`、`dataset_version`。
- **Rollout 记录**：`sample_id`、`model_version`、`sampling_params`、`tokens`、`logprobs`、`finish_reason`、`text`。
- **验证记录**：`rollout_id`、`verifier_name`、`verifier_version`、`status`、`score`、`details`、`latency_ms`。
- **奖励记录**：`rollout_id`、`reward_components`、`total_reward`、`kl`、`reward_config_version`。
- **训练批次**：`rollouts`、`advantages`、`old_logprobs`、`ref_logprobs`、`metadata`。
- **Checkpoint 清单**：`step`、`model_hash`、`optimizer_state`、`config`、`parent_checkpoint`、`eval_report`。

这些记录不仅是训练需要，也是审计和复盘需要。当模型出现异常行为时，你需要能回答：它是在哪个 checkpoint、用哪版验证器、在哪批数据上、因为哪个奖励分量学坏的。

## 10.4 工程要点

- **异步与背压**：Rollout 和验证都是可变延迟的。用队列解耦，设置并发上限和背压，避免验证服务被采样洪峰打垮。
- **幂等与重试**：验证请求要可重试，结果要可缓存。缓存键应包含代码、测试、环境版本和随机种子。
- **超时与隔离**：每个验证任务都有硬超时；超时后杀死进程树，清理容器和临时文件。
- **版本固定**：模型、数据、验证器、沙箱镜像、依赖库都要版本化；训练配置要记录 git commit 和镜像 digest。
- **可观测性**：监控 rollout 吞吐、验证延迟 p50/p95、验证错误率、奖励分布、KL、熵、长度、GPU 利用率。
- **成本控制**：验证是最容易超预算的部分。用分层验证、缓存、批处理、按需采样来控制成本。
- **安全边界**：验证服务与训练服务分域部署；验证服务不能访问训练集群的内部网络、模型权重和密钥。

# 十一、伪代码示例：简化 RLVR 训练循环

下面是一段 Python 风格伪代码，展示 RLVR 的核心逻辑。它省略了分布式、混合精度、梯度累积、日志和容错细节，重点在控制流。

```python
# 简化示意：单机版 RLVR 训练循环
import random
from collections import defaultdict
import torch

def load_tasks(path):
    """加载可验证任务：prompt、reference、verifier 规格、元数据。"""
    return read_jsonl(path)

def sample_rollouts(policy, task, group_size=8, temperature=0.9,
                    max_tokens=4096):
    """对同一问题采样多条轨迹，记录文本、token 和 logprob。"""
    rollouts = []
    for _ in range(group_size):
        out = policy.generate(
            task["prompt"],
            temperature=temperature,
            max_tokens=max_tokens,
            return_logprobs=True,
        )
        rollouts.append({
            "text": out.text,
            "tokens": out.tokens,
            "logprobs": out.logprobs,
            "finish_reason": out.finish_reason,
        })
    return rollouts

def verify_answer(task, rollout):
    """调用对应验证器，返回三态结果和分项信息。"""
    verifier = task["verifier"]
    if verifier["type"] == "math_equiv":
        # math_equiv 内部负责答案抽取、归一化和等价判断
        ok = math_equiv(rollout["text"], task["reference"])
        return {"status": "correct" if ok else "incorrect", "answer_ok": ok}
    if verifier["type"] == "unit_test":
        result = run_in_sandbox(
            rollout["text"],
            tests=task["hidden_tests"],
            timeout_ms=task["constraints"]["time_limit_ms"],
        )
        return {
            "status": result.status,      # correct / incorrect / error
            "compile_ok": result.compile_ok,
            "tests_passed": result.tests_passed,
        }
    if verifier["type"] == "json_schema":
        return validate_json_result(rollout["text"], task["schema"])
    raise ValueError(f"unknown verifier: {verifier['type']}")

def compute_reward(task, rollout, verify_result, reward_cfg):
    """把验证结果映射为标量奖励，并保留分项日志。"""
    if verify_result["status"] == "error":
        return None, {"skip": True, "reason": "verifier_error"}

    correct = 1.0 if verify_result["status"] == "correct" else 0.0
    format_ok = 1.0 if has_valid_format(rollout["text"], task) else 0.0
    length = len(rollout["tokens"])

    reward = 0.0
    reward += reward_cfg["w_correct"] * correct
    reward += reward_cfg["w_format"] * format_ok * correct  # 格式奖励以正确为前提
    if length > reward_cfg["max_len"]:
        reward -= reward_cfg["w_len"] * (length - reward_cfg["max_len"]) \
                  / reward_cfg["max_len"]
    if verify_result.get("unsafe"):
        reward -= reward_cfg["w_unsafe"]
    return reward, {
        "correct": correct,
        "format": format_ok,
        "length": length,
        "unsafe": verify_result.get("unsafe", False),
    }

def estimate_advantage(rewards, mode="group"):
    """GRPO 风格：组内标准化；也可换成 GAE / leave-one-out。"""
    valid = [r for r in rewards if r is not None]
    if len(valid) < 2:
        return [0.0 for _ in rewards]
    mean = sum(valid) / len(valid)
    var = sum((r - mean) ** 2 for r in valid) / len(valid)
    std = max(var ** 0.5, 1e-6)
    return [0.0 if r is None else (r - mean) / std for r in rewards]

def update_policy(policy, batch, ref_policy, cfg):
    """PPO / GRPO 风格更新：裁剪目标 + KL 惩罚。"""
    if not batch:
        return {"loss": 0.0, "kl": 0.0}
    total_loss, total_kl = 0.0, 0.0
    for item in batch:
        if item["advantage"] == 0.0:
            continue
        new_logp = policy.logprob(item["tokens"], item["prompt"])
        old_logp = item["old_logprobs"]
        ratio = (new_logp - old_logp).exp()
        clipped = ratio.clamp(1 - cfg["clip"], 1 + cfg["clip"])
        # PPO 裁剪目标：min(ratio * A, clip(ratio) * A)
        surr1 = ratio * item["advantage"]
        surr2 = clipped * item["advantage"]
        policy_loss = -torch.min(surr1, surr2).mean()

        ref_logp = ref_policy.logprob(item["tokens"], item["prompt"])
        kl = (new_logp - ref_logp).mean()
        loss = policy_loss + cfg["beta"] * kl
        loss.backward()
        total_loss += loss.item()
        total_kl += kl.item()
    policy.step()
    return {"loss": total_loss, "kl": total_kl / max(len(batch), 1)}

def evaluate_model(policy, eval_tasks, k=1):
    """在 held-out 集上评估 pass@1 / pass@k / 执行通过率。"""
    metrics = defaultdict(list)
    for task in eval_tasks:
        rollouts = sample_rollouts(policy, task, group_size=k,
                                   temperature=0.0 if k == 1 else 0.8)
        results = [verify_answer(task, r) for r in rollouts]
        metrics["pass_at_1"].append(
            1.0 if results[0]["status"] == "correct" else 0.0)
        metrics["pass_at_k"].append(
            1.0 if any(r["status"] == "correct" for r in results) else 0.0)
        metrics["verifier_error"].append(
            1.0 if any(r["status"] == "error" for r in results) else 0.0)
    return {name: sum(vals) / len(vals) for name, vals in metrics.items()}

def save_checkpoint(policy, step, path):
    """保存权重、优化器状态、配置和数据版本。"""
    policy.save(f"{path}/step-{step}")
    write_json(f"{path}/step-{step}/manifest.json", {
        "step": step,
        "model": policy.name,
        "config": policy.config,
        "data_version": policy.data_version,
    })

def train(cfg):
    tasks = load_tasks(cfg["train_path"])
    eval_tasks = load_tasks(cfg["eval_path"])
    policy = load_policy(cfg["init_checkpoint"])
    ref_policy = policy.clone().freeze()

    for step in range(cfg["max_steps"]):
        batch = []
        for task in sample_batch(tasks, cfg["batch_size"]):
            rollouts = sample_rollouts(
                policy, task, group_size=cfg["group_size"],
                temperature=cfg["temperature"],
                max_tokens=cfg["max_tokens"],
            )
            rewards, infos = [], []
            for r in rollouts:
                v = verify_answer(task, r)
                reward, info = compute_reward(task, r, v, cfg["reward"])
                rewards.append(reward)
                infos.append(info)
                r["verify"] = v

            advantages = estimate_advantage(rewards)
            for r, a, info in zip(rollouts, advantages, infos):
                if info.get("skip"):
                    continue
                batch.append({
                    "prompt": task["prompt"],
                    "tokens": r["tokens"],
                    "old_logprobs": r["logprobs"],
                    "advantage": a,
                    "reward_info": info,
                })

        stats = update_policy(policy, batch, ref_policy, cfg["rl"])
        log_metrics(step, stats, batch)

        if step % cfg["eval_every"] == 0:
            metrics = evaluate_model(policy, eval_tasks, k=cfg["eval_k"])
            save_checkpoint(policy, step, cfg["ckpt_dir"])
            log_eval(step, metrics)
```

## 11.1 关键逻辑说明

**1. 多采样是 RLVR 的基础。** `sample_rollouts` 对每个问题采样一组回答，而不是一个。这样做既能提高正确解的命中率，也能为组内 advantage 提供对比信号。采样温度通常高于评估温度，以增加探索；评估时用低温或贪心解码，保证可复现。

**2. 验证器返回三态，不是二态。** `verify_answer` 返回 `correct`、`incorrect` 或 `error`。`compute_reward` 遇到 `error` 时返回 `None`，在 advantage 估计和策略更新中跳过。这避免了把验证器故障当成模型错误，污染训练信号。

**3. 奖励是分项的组合，不是单一标量。** `compute_reward` 把正确性、格式、长度、安全分开计算，再聚合。分项日志用于分析模型在优化什么，也用于排查 reward hacking。格式奖励乘以 `correct`，是为了防止模型只学格式。

**4. 组内标准化是 GRPO 的核心。** `estimate_advantage` 用组内均值和标准差归一化奖励。这相当于用同组其他样本作为 baseline，减少方差，不需要训练价值网络。如果一组全对或全错，方差接近零，advantage 也接近零，这批数据对更新没有贡献。

**5. KL 惩罚限制策略漂移。** `update_policy` 在策略损失之外加上 `β * KL`，防止模型为了奖励牺牲语言质量和安全性。KL 通常是逐 token 计算的，β 需要根据奖励尺度和训练稳定性调整。

**6. 评估与训练分离。** `evaluate_model` 使用 held-out 集，计算 pass@1、pass@k 和验证器错误率；`save_checkpoint` 保存权重、配置和数据版本。没有这两步，训练曲线好看也可能只是过拟合或评测污染。

伪代码省略了很多生产细节：分布式训练、梯度累积、混合精度、参考模型分片、rollout 缓存、动态采样、课程学习、奖励归一化、异常恢复、审计日志。这些细节决定系统能不能稳定跑起来，而不是算法本身。

# 十二、RLVR 的评估指标

RLVR 的评估要同时看“任务效果”“推理能力”“训练稳定性”“安全”“工程效率”五个维度。只看一个指标，很容易得出错误结论。

## 12.1 任务效果指标

| 指标名称 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- |
| Accuracy | 单次回答的正确率 | 正确样本数 / 总样本数 | 分类、数学、结构化输出 | 需要明确的正确性判据 |
| Pass@1 | 一次采样的通过率 | 每个问题采样一次，统计通过比例 | 代码、数学 | 与 Accuracy 类似，但强调单次 |
| Pass@k | k 次采样至少一次通过 | `1 - C(n-c, k) / C(n, k)` 的无偏估计 | 代码、数学 | k 越大越乐观；不能代替 pass@1 |
| Exact Match | 与参考答案完全一致的比例 | 字符串或归一化后比较 | 短答案、结构化输出 | 对格式敏感，需先归一化 |
| Execution Success Rate | 代码/工具执行成功的比例 | 成功执行数 / 总执行数 | 代码、SQL、工具调用 | 区分编译、运行、超时、崩溃 |
| Tool Success Rate | 工具调用任务完成率 | 成功任务数 / 总任务数 | 工具调用、Agent | 需要明确的终态判据 |

## 12.2 推理能力指标

| 指标名称 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- |
| Reasoning Consistency | 推理过程与答案是否一致 | 步骤检查、扰动测试、人工抽检 | 数学、逻辑 | 难以完全自动化，需抽样 |
| Self-Consistency Gain | 多次采样投票相对单次的提升 | `maj@k - pass@1` | 数学、选择题 | 提升大不一定代表推理强，可能是答案分布偏 |
| Hard Problem Accuracy | 高难度题目的正确率 | 按难度分层统计 | 数学、代码 | 需要可靠的难度标注 |
| Generalization to Unseen | 分布外题目的表现 | 在未见过来源/题型上评估 | 全部 | 必须严格去重和时间切分 |
| Pass@k Coverage | 采样覆盖正确解的能力 | pass@k 随 k 的变化曲线 | 代码、数学 | 可判断 RL 是“扩展能力”还是“锐化分布” |
| Answer-Reasoning Alignment | 答案是否由推理支撑 | 改数字/改条件后答案是否合理变化 | 数学、逻辑 | 需要构造配对扰动样本 |

## 12.3 训练稳定性指标

| 指标名称 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- |
| Reward Mean | 奖励是否在上升 | 批次平均奖励 | 全部 | 上升可能是 hacking，需结合评估 |
| Reward Variance | 奖励分布是否健康 | 批次奖励方差 / 组内方差 | 全部 | 方差过低可能没有学习信号 |
| KL Divergence | 策略偏离参考模型的程度 | 逐 token KL 的均值 | 全部 | 突然飙升通常意味着不稳定 |
| Entropy | 策略的探索程度 | 输出分布的熵 | 全部 | 熵快速下降可能是策略坍缩 |
| Gradient Norm | 梯度是否爆炸或消失 | 梯度范数 | 全部 | 需要按模型规模设阈值 |
| Clip Fraction | PPO 裁剪触发比例 | 被裁剪 token 比例 | PPO | 过高说明更新步长太大 |
| Zero-Variance Group Ratio | 无学习信号的组比例 | 全对/全错组数 / 总组数 | GRPO | 过高说明题目太难或太简单 |
| Response Length | 输出长度是否异常增长 | 平均 token 数 | 全部 | 长度暴涨可能是长度 hacking |

## 12.4 安全指标

| 指标名称 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- |
| Unsafe Output Rate | 不安全输出的比例 | 安全分类器/规则命中数 / 总数 | 全部 | 分类器本身有误判，需抽检 |
| Sandbox Violation Rate | 沙箱违规比例 | 越权系统调用/网络访问/资源超限次数 | 代码、Agent | 需要细粒度审计日志 |
| Harmful Tool Call Rate | 危险工具调用比例 | 危险调用数 / 总调用数 | 工具调用、Agent | 需要定义危险调用清单 |
| Format Exploit Rate | 格式漏洞利用比例 | 触发解析器异常/歧义的样本比例 | 结构化输出 | 需要模糊测试和红队 |
| Refusal Regression | 该拒绝时是否拒绝 | 安全测试集上的拒答准确率 | 对话、Agent | 防止安全训练导致过度拒答 |

## 12.5 工程效率指标

| 指标名称 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- |
| Rollout Throughput | 采样吞吐 | tokens/秒 或 样本/秒 | 全部 | 受模型大小、序列长度、批大小影响 |
| Verifier Latency | 验证延迟 | p50 / p95 / p99 毫秒 | 全部 | 代码执行通常是瓶颈 |
| Training Cost | 训练成本 | GPU 小时 × 单价 + 验证成本 | 全部 | 要算“每个正确样本”的成本 |
| GPU Utilization | GPU 是否吃饱 | 实际算力 / 峰值算力 | 全部 | rollout 和训练分离时尤其重要 |
| Failed Execution Rate | 执行失败比例 | 超时/崩溃/缺依赖数 / 总数 | 代码、工具 | 要与模型错误区分 |
| Cache Hit Rate | 验证缓存命中率 | 命中数 / 请求数 | 代码、数学 | 缓存键要包含环境版本 |

指标的使用方式比指标本身更重要。建议：

- **训练看趋势，评估看绝对值。** 训练奖励用于判断是否在学，held-out 指标用于判断是否真的变强。
- **同时看 pass@1 和 pass@k。** 如果 pass@1 上升但 pass@k 不升，可能只是把已有能力“锐化”了，而不是扩展了能力边界。
- **分难度、分题型看。** 总体准确率可能掩盖某些题型的退化。
- **和安全指标一起看。** 正确率上升但沙箱违规率上升，不是可接受的结果。
- **记录置信区间。** 小评估集上的几个点差异可能只是噪声。

# 十三、RLVR 的优势与局限

## 13.1 优势

### 13.1.1 奖励信号客观

在强可验证任务上，正确性不依赖标注者的主观判断。同一个答案，不同标注者可能有不同偏好；但一个方程的解是否满足等式，一个程序是否通过测试，一个 JSON 是否符合 Schema，是可以被独立检查的。这种客观性降低了标注方差，也让不同团队、不同时间的实验结果更容易比较。

**工程建议**：不要因为“有验证器”就宣称“完全客观”。验证器本身可能有 bug、覆盖不足、版本差异。要为验证器建立人工审核集，定期测准确率和一致性，并把验证器版本写进实验记录。

### 13.1.2 自动化程度高

RLVR 的奖励可以随采样规模自动计算。只要验证服务能水平扩展，训练就可以在无人值守的情况下持续运行。这对于需要大量探索的推理任务尤其重要：模型需要尝试很多次，才能偶尔找到正确路径；人工评分无法支撑这种采样量。

**工程建议**：把验证做成独立服务，支持批处理、缓存、超时和重试；用队列削峰；监控验证延迟和错误率。不要让验证成为训练吞吐的瓶颈。

### 13.1.3 适合推理任务

推理任务的本质是搜索和验证：尝试不同路径，检查中间结果，回溯错误分支。RLVR 允许模型在自己的分布上探索，并通过结果奖励强化成功路径。即使只给最终答案奖励，group sampling 也能提供“同一问题下哪条路径更好”的对比信号。

**工程建议**：保证题目难度分布合理。全难题会导致组内全错，全简单题会导致组内全对，两者都没有学习信号。用难度分层、动态采样和课程学习维持有效梯度。

### 13.1.4 减少人工偏好标注依赖

RLHF 需要大量成对偏好数据，标注成本高、周期长。RLVR 通常只需要题目、参考答案、测试用例或规则，这些资产可以复用、版本化、自动扩展。对于数学和代码团队，测试用例本来就是工程资产，RLVR 可以把它直接转化为训练信号。

**工程建议**：把投入从“标注偏好”转向“构建数据和验证器”。高质量的测试、规则和参考答案，比大量低质量偏好标注更有价值。

### 13.1.5 有利于规模化训练

可验证奖励的边际成本低，适合大规模并行采样和在线训练。验证可以缓存，测试可以并行，沙箱可以池化。相比人工评分或大规模 LLM Judge，RLVR 更容易做成本预测和容量规划。

**工程建议**：建立成本模型，分别统计 rollout、验证、训练三部分的开销；计算“每个正确样本的成本”，而不是只看总 GPU 小时；对高频题目做缓存，对低频题目按需验证。

### 13.1.6 可与代码执行、数学验证、工具环境结合

RLVR 的奖励可以来自真实环境：代码在沙箱里运行，SQL 在只读副本上执行，工具调用在模拟或真实系统中产生副作用，Agent 在环境中改变状态。这种“环境 grounding”让奖励更接近真实任务，而不是纸面评分。

**工程建议**：优先使用真实或高保真环境；如果只能用 mock，要定期做 mock 与真实环境的一致性测试；记录环境版本和重置逻辑，保证可复现。

## 13.2 局限

### 13.2.1 只适合可验证任务

RLVR 的前提是存在可执行的正确性判据。开放式写作、战略咨询、情感支持、创意设计、复杂政策判断，很难用规则或测试完整验证。即使能用 LLM Judge 打分，那也是弱验证，不能等同于客观正确性。

**工程建议**：按任务路由。数学、代码、结构化输出、工具调用用 RLVR；风格、语气、helpfulness 用 RLHF / RLAIF；两者可以组合，但不要用一个奖励函数硬扛所有目标。

### 13.2.2 Verifier 质量决定上限

模型会放大验证器的漏洞。一个 1% 的假阳性，在数百万次采样后可能变成系统性的错误行为。验证器覆盖不到的错误模式，模型学不到；验证器误判的正确样本，会被错误地压低概率。

**工程建议**：验证器优先于训练器建设。先建立人工审核集，测 precision / recall / 一致性；再逐步扩大任务覆盖。对高风险任务使用多验证器交叉检查，对不确定样本降级处理。

### 13.2.3 奖励稀疏

结果奖励在难题上非常稀疏。模型采样 16 次全部错误，组内奖励全为 0，advantage 没有信息。这会拖慢学习速度，甚至让训练停滞。

**工程建议**：使用课程学习、难度分层、动态采样、过程奖励、拒绝采样微调等组合手段。先让模型在中等难度题目上获得稳定的正信号，再逐步增加难题比例。

### 13.2.4 可能发生 Reward Hacking

只要奖励是代理指标，模型就可能找到“得分高但不做正确事”的路径。RLVR 的验证器是程序，程序有边界条件、解析规则和环境漏洞，模型可以通过枚举、格式绕过、硬编码、测试探测等方式利用它们。

**工程建议**：把 reward hacking 当作持续对抗，而不是一次性检查。使用隐藏测试、随机测试、多验证器、异常检测、人工抽检和红队测试；对奖励分布做可视化，发现异常尖峰或异常模式。

### 13.2.5 不一定提升开放式写作或主观任务

RLVR 优化的是验证器覆盖的目标。如果训练只奖励数学正确性，模型的语言风格、创造性和对话能力可能不变，甚至退化。即使在同一任务内，过度优化正确性也可能让输出变得机械、冗长或缺乏解释性。

**工程建议**：保留通用能力和风格的回归评估；在奖励中加入少量风格/长度约束；用 KL 惩罚限制漂移；必要时混入 SFT 或偏好数据，做多目标训练。

### 13.2.6 训练成本高

RLVR 需要在线采样、验证和策略更新。Rollout 消耗大量推理算力，代码执行和符号验证消耗 CPU，RL 训练本身还需要额外的显存和工程设施。相比 SFT，RLVR 的单位样本成本高得多。

**工程建议**：先用小模型、小数据验证闭环，再扩大规模；使用推理引擎的连续批处理和前缀缓存；对验证结果做缓存；用拒绝采样微调作为低成本基线；设定明确的预算和停止条件。

### 13.2.7 安全沙箱复杂

代码执行、SQL、工具调用和 Agent 环境都涉及不可信输入。沙箱要防逃逸、防资源耗尽、防数据泄漏、防网络访问，还要保证性能和可复现性。这是一套独立的安全工程，不是“加个 Docker”就能解决。

**工程建议**：使用微虚拟机或 gVisor 级别的隔离；默认无网络；只读文件系统；限制 CPU、内存、进程数、文件大小；审计系统调用；验证服务与训练集群分域部署；定期做逃逸测试。

### 13.2.8 可能牺牲语言自然性或多样性

强化学习会提高高奖励轨迹的概率，降低其他轨迹的概率。如果奖励只看正确性，模型可能收敛到一种“最容易被验证器接受”的固定表达，输出变得模板化、冗长或缺乏多样性。熵快速下降是这种退化的早期信号。

**工程建议**：监控 entropy、输出长度和多样性指标；使用 KL 惩罚和熵正则；在评估中加入人工可读性评分；保留多样化的 prompt 和任务，避免训练分布过窄。

# 十四、常见误区

| 误区 | 为什么危险 | 正确做法 |
| --- | --- | --- |
| 有 verifier 就一定能训练出好模型 | 验证器可能覆盖不足、误判、被攻击；模型会放大漏洞 | 先测验证器的准确率、覆盖率和抗攻击能力；从强可验证任务开始 |
| 只看最终答案正确率，忽略推理过程质量 | 模型可能猜中、枚举、记忆或推理错误但答案巧合正确 | 加入过程检查、扰动测试、人工抽检；同时看 pass@1、pass@k 和一致性 |
| 使用过于简单的二值奖励 | 难题上奖励全 0，没有梯度；模型无法区分接近正确和完全错误 | 用课程学习、动态采样、分级奖励或过程奖励；但不要让辅助奖励主导 |
| 公开测试用例泄漏 | 模型过拟合公开测试，隐藏测试表现差 | 使用隐藏测试、随机测试、时间/来源切分；定期轮换测试集 |
| 忽略 KL 控制 | 策略漂移，语言质量下降，出现 reward hacking | 监控 KL、熵、长度；设置合理 β；保留参考模型和回滚机制 |
| 忽略 reward hacking | 模型学会利用验证器漏洞，训练奖励上升但真实能力下降 | 红队测试、多验证器、隐藏测试、异常检测、人工抽检 |
| 把 LLM Judge 当成完全可靠的 verifier | Judge 有位置、长度、自我偏好，容易被提示注入 | 结构化 rubric、多裁判、位置交换、校准；规则优先，人工兜底 |
| 不做 held-out 评估 | 训练集和评测集重叠，指标虚高；无法判断泛化 | 按来源/时间去重切分；使用 held-out test set；多随机种子评估 |
| 没有安全沙箱 | 模型代码可能逃逸、访问网络、泄漏密钥、耗尽资源 | 微虚拟机/gVisor、网络隔离、只读文件系统、cgroups、审计 |
| 认为 RLVR 可以替代所有 RLHF | 开放式偏好、语气、安全边界无法用规则完整表达 | 组合使用：RLVR 管正确性，RLHF/RLAIF 管偏好和安全；按任务路由 |

这些误区的共同根源，是把“奖励信号”当成了“任务目标”。验证器只是任务目标的一个代理，代理和真实目标之间永远有缝隙。工程上的正确心态是：**持续测量缝隙，而不是假设缝隙不存在。**

# 十五、未来趋势

## 15.1 从 Outcome Reward 到 Process Reward

结果奖励容易验证，但信用分配粗。过程奖励能告诉模型“哪一步错了”，更适合长链推理。未来的方向包括：自动过程验证器、蒙特卡洛进展估计、步骤级符号检查、以及结果奖励与过程奖励的自适应组合。难点在于过程标注成本、步骤边界定义和过程奖励被利用的风险。

## 15.2 更强的自动验证器

验证器会从“写死的规则”走向“可组合的验证流水线”：语法检查、类型检查、单元测试、属性测试、模糊测试、符号计算、SMT 求解、形式化证明，按成本和置信度分层组合。LLM Judge 会作为长尾补充，而不是主裁判。

## 15.3 与形式化方法结合

形式化验证提供最高的置信度。Lean、Coq、Isabelle 等证明助手可以检查数学证明和程序属性；SMT Solver 可以检查约束满足。瓶颈在于“自动形式化”：把自然语言题目转成形式化规约，本身就是一个难题。未来的方向包括自动形式化、证明搜索、以及自然语言与形式化证明的联合训练。

## 15.4 与 Agent 环境交互结合

Agent 任务提供了丰富的可验证环境：文件系统、数据库、API、浏览器、代码仓库。RLVR 可以在这些环境中训练模型规划、调用工具、处理错误和完成任务。关键挑战是环境保真度、长程信用分配、可复现性和安全隔离。

## 15.5 多验证器集成

单一验证器容易被针对。多验证器集成可以用投票、交叉检查、置信度加权等方式降低单点偏差。例如，代码题同时跑单元测试、属性测试和静态分析；数学题同时用符号计算和数值代入；工具调用同时检查参数 Schema 和环境终态。代价是成本上升，需要按任务价值做取舍。

## 15.6 可验证工具调用训练

企业系统里的工具调用有明确的 Schema、权限和业务规则，天然适合 RLVR。未来会有更多“工具调用 + 环境终态”的训练数据、模拟器和评测基准，覆盖多工具协作、错误恢复、权限边界和长流程任务。

## 15.7 代码与数学联合训练

代码和数学都需要精确推理、分步验证和错误回溯。联合训练可能带来迁移：代码中的类型检查、测试驱动和调试策略，可以帮助数学推理；数学中的符号操作和约束求解，可以帮助代码生成。如何配比数据、避免负迁移，是需要实验的问题。

## 15.8 RLVR 与合成数据闭环

用强模型生成题目、答案、测试和解题过程，用验证器筛选，再把高质量样本用于训练，形成数据闭环。这可以降低数据成本，但也带来风险：合成数据可能重复、有偏、污染评测集，甚至让模型陷入自我强化的错误模式。需要严格的去重、验证和人工抽检。

## 15.9 更稳定高效的 RL 算法

GRPO 之后，出现了一批改进工作，例如 DAPO 的动态采样、clip-higher、token 级损失和超长奖励塑形，以及针对 GRPO 归一化偏差的修正。未来会继续围绕以下问题优化：降低 critic 成本、提高样本效率、处理长度偏差、稳定长序列训练、支持异步 rollout。

## 15.10 安全对齐与可验证奖励结合

安全策略、权限规则、输出格式和工具调用约束，很多都可以写成可验证规则。把安全规则作为硬约束或强惩罚并入 RLVR，可以在提升能力的同时限制危险行为。难点是避免过度拒答、规则冲突和“安全奖励”被模型绕过。

## 15.11 从单轮任务走向长程任务验证

当前 RLVR 多集中在单轮数学题、代码题和结构化输出。未来的重点会转向长程任务：多轮对话、多步工具调用、跨文件代码修改、长期 Agent 任务。这些任务的验证需要检查过程、终态、资源消耗和安全边界，信用分配也更复杂。

## 15.12 一个需要保持怀疑的问题

有一类研究对 RLVR 的“能力提升”提出了更细的追问：RL 后的模型在 pass@1 上确实更好，但在更大的采样预算下，pass@k 的覆盖是否真的超过了基座模型？如果 RL 只是让模型更稳定地采样到已有正确解，而不是学会全新的解题能力，那么“RLVR 提升推理能力”的表述就需要更精确。另一类研究发现，在某些设置下，即使使用随机奖励，模型在数学基准上也会出现提升，这提示部分增益可能来自格式/分布的激发，而不是奖励信号本身。

这些结论仍有争议，不能简单外推。但它们提醒工程团队：**评估要看 pass@k、要看分布外泛化、要看基座模型对照，不要只看训练奖励和单一基准的 pass@1。**

# 十六、总结：如何理解 RLVR 的价值

## 16.1 六点结论

1. **RLVR 的核心是用客观、自动、可复现的验证信号训练模型。** 它把奖励从“人类偏好”转向“可执行判据”，让大规模在线探索成为可能。
2. **它非常适合数学、代码、结构化输出、工具调用等可验证任务。** 这些任务的正确性可以被程序检查，奖励的边际成本低，适合反复采样和策略优化。
3. **Verifier 是 RLVR 成败的关键。** 验证器的覆盖、准确率、稳定性和安全性，直接决定模型学到的行为。验证器有漏洞，模型就会学会利用漏洞。
4. **Reward 设计决定训练方向。** 二值奖励简单但稀疏，分级和过程奖励更细但更容易被利用。正确性应该是主信号，辅助奖励要谨慎加权，KL 和安全惩罚要持续监控。
5. **RLVR 不能替代所有对齐方法。** 它擅长正确性，不擅长语气、风格、helpfulness 和复杂安全判断。实际系统通常是 SFT、RLVR、RLHF/RLAIF 的组合。
6. **企业落地 RLVR 需要重点建设数据集、验证器、沙箱、评估体系和实验管理平台。** 算法只是其中一环，工程基础设施决定能不能稳定迭代。

## 给工程团队的落地建议

1. **先选择天然可验证的任务开始。** 数学题、单元测试代码、JSON Schema、SQL 查询、工具调用，都是比开放式写作更好的起点。
2. **不要一开始就训练大模型。** 先用小模型和小数据验证“数据 → 采样 → 验证 → 奖励 → 更新”的闭环，确认奖励信号有效，再扩大规模。
3. **Verifier 要优先于 Trainer 建设。** 先有人工审核集、误判率统计、测试用例和沙箱，再谈 PPO/GRPO 的超参数。
4. **为代码执行任务建立强隔离沙箱。** 微虚拟机或 gVisor、默认无网络、只读文件系统、cgroups 资源限制、seccomp、进程组清理、审计日志，缺一不可。
5. **使用 hidden tests 防止过拟合。** 公开测试可以出现在题面，隐藏测试只用于验证；定期轮换隐藏测试，检查模型是否在探测测试环境。
6. **对 reward 进行可视化和审计。** 记录每个分项的分布、极值样本、异常模式和验证器版本；奖励曲线上升不等于模型变强，要结合评估看。
7. **保留 held-out 测试集。** 按来源、时间或难度切分，不能参与训练或调参；评估时使用多个随机种子和置信区间。
8. **使用 KL 控制防止模型退化。** 监控 KL、熵、长度和重复率；β 太小会漂移，太大会学不动；保留参考模型和回滚机制。
9. **对 reward hacking 做红队测试。** 定期用自动化工具和人工红队攻击验证器：硬编码、枚举、格式绕过、测试探测、提示注入、沙箱逃逸。
10. **同时评估正确率、稳定性、安全性和成本。** 只看准确率会漏掉回归、退化、越权和预算超支；建立多维度的发布门禁。
11. **不要把 LLM Judge 当成唯一奖励来源。** Judge 适合长尾和语义判断，但需要结构化 rubric、多裁判、校准和人工抽检；高风险任务要有规则或执行验证兜底。
12. **建立完整的实验追踪和 checkpoint 回滚机制。** 记录数据版本、验证器版本、奖励配置、模型版本和评估报告；出问题时能定位、能回滚、能重放。
13. **把验证服务与训练集群分域部署。** 验证服务运行不可信代码，不能访问训练集群的内部网络、模型权重和密钥；按最小权限原则配置。
14. **区分模型错误和验证器错误。** 使用 `correct` / `incorrect` / `verifier_error` 三态；验证器错误要隔离、重试和监控，不能直接记 0 分。
15. **为验证成本做预算。** 代码执行、符号计算和沙箱池化都是真实开销；计算“每个正确样本的成本”，并设置训练停止条件，避免为了 marginal gain 烧掉预算。

最后，保持对结论的怀疑：看 pass@1，也看 pass@k；看训练分布，也看分布外；看奖励，也看人工抽检。RLVR 是一个强大的工具，但不是“自动提升智能”的按钮。

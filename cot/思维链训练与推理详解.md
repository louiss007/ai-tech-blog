# 思维链训练与推理详解：大语言模型如何学会分步思考

> 面向有一定大语言模型、机器学习、Prompt Engineering、模型训练或推理系统基础的技术读者。本文把思维链（Chain-of-Thought，CoT）同时当作一种提示方法、一种训练数据格式和一种推理时计算策略来讨论，重点回答三个问题：模型为什么需要分步推理、这种能力如何被训练出来、生产系统怎样安全且可控地使用推理过程。

**阅读前提与假设**

- 本文默认读者了解 Transformer 自回归生成、监督微调（SFT）、RLHF 的基本概念，不要求读过原始论文。
- 文中的准确率、延迟、成本数字，除注明“论文报告值”外，均为量级示意，用于说明权衡关系，不代表任何具体模型或产品的基准。
- 不同厂商对“推理模型”的定义和接口不同。本文讨论通用机制，落地时以具体模型卡、API 文档和内部评测为准。
- 截至本文写作时，CoT 的忠实性、可解释性和安全治理仍是开放问题。文中会明确区分“工程上可用”和“理论上成立”。

# 一、引言：为什么大语言模型需要思维链

## 1.1 直接回答的局限

大语言模型的基本生成方式是自回归：给定上下文，逐 token 预测下一个 token。这个机制有两个工程后果：

1. 模型对每个 token 的计算深度大致固定，一次前向通过固定层数的 Transformer；
2. 模型没有天然的“草稿纸”，所有中间结果只能放在已经生成的 token 或内部隐状态里。

当任务需要多步推导时，直接回答就把“所有中间计算”压进了一次生成。它并不是完全不会算，而是没有显式的、可回退的中间状态。常见的失效模式有四类。

**多步骤数学题。** 应用题通常需要设未知数、列关系式、做计算、回代检查。直接回答要求模型在一次生成中隐式完成全部步骤；一步算错，后面全错，而且模型没有机会发现并回滚。百分比、单位换算、分数与小数混用，是最容易出错的环节。

**复杂逻辑推理。** 条件一多，模型容易遗漏约束、混淆充分条件和必要条件，或者把“存在”当成“任意”。这些问题在只看最终答案时很难发现，因为错误答案往往也长得很自然。

**代码推理与调试。** 调试不是“给一个补丁”，而是先定位输入、状态变化、边界条件和失败路径，再决定改哪里。直接回答常见的问题是“看起来对但修错位置”：补丁能通过眼前这个例子，却引入新的回归。

**长上下文问题。** 关键证据分散在多个段落，甚至相互冲突。直接回答倾向于抓住与问题表面最相似的片段，跳过交叉核对，忽略否定条件、时间范围和例外。

| 任务类型 | 直接回答的典型失败 | 根本原因 |
| --- | --- | --- |
| 多步数学 | 中间量算错、百分比/单位处理错 | 缺少显式中间状态，错误无法局部回滚 |
| 逻辑推理 | 漏条件、混淆量词、循环论证 | 约束没有被逐条展开和检查 |
| 代码调试 | 修错位置、忽略边界、补丁引入回归 | 缺少执行路径和状态分析 |
| 长上下文问答 | 抓错证据、忽略冲突、过度概括 | 证据没有被逐条核对 |

比错误更麻烦的是**静默失败**：模型不会报错，而是给出语气自信的错误答案。工程系统需要的是可检测、可回滚、可审计的失败，而不是“看起来像对”的输出。

## 1.2 一个例子：直接回答与分步推理

考虑一个简单问题：

> 一件商品先涨价 20%，再降价 20%，最终价格相对原价如何？

**直接回答（示意）**：

> 先涨 20%，再降 20%，涨幅和降幅相同，所以价格回到原价。

这个回答的推理听起来很顺，但结论是错的。百分比变化是乘性的，不是加性的。

**分步推理（示意）**：

> 设原价为 100 元。
>
> 第一步，涨价 20% 后价格为 100 × 1.2 = 120 元。
>
> 第二步，降价 20% 是在 120 元的基础上降，降幅为 120 × 0.2 = 24 元，最终价格为 120 − 24 = 96 元。
>
> 第三步，96 小于 100，所以最终价格比原价低 4%。

分步版本并没有使用更复杂的知识，它只是把“设原价、算涨后价、算降后价、比较”四个中间状态写了出来。写出来的好处是：每一步都可以被检查，错误可以定位到具体一步。

需要说明，这是一个构造出来的对比，不是某次真实模型输出的复现。大模型完全可能直接答对，尤其是参数规模较大、见过类似题目的模型。这里想说明的是失效模式，而不是给某个模型下结论。

## 1.3 思维链的直觉

人类解决复杂问题时，通常不会要求自己“一步给出答案”，而是列提纲、写中间结果、检查、必要时回头修改。CoT 把这种外部化过程引入生成：模型先生成一段推理轨迹 z，再基于问题和 z 生成最终答案 y。

用概率语言写，直接回答建模的是：

```text
p(y | x)
```

CoT 把它拆成：

```text
p(z | x) · p(y | x, z)
```

模型并没有因此获得更大的参数规模，但它获得了更多的串行计算步骤，以及一个可以反复 attend 的外部状态。这就是为什么“让模型把步骤写出来”经常比“让模型直接给答案”更准：不是模型突然变聪明了，而是它被允许用更多计算和更多中间存储来完成任务。

这里有一个关键区分：z 是 token 序列，不是模型内部真实的“思考状态”。它是否忠实反映内部计算，是另一个问题，后文会专门讨论。

## 1.4 思维链带来的能力提升

CoT 在不同任务族上的收益并不均匀。工程上比较稳定的收益集中在需要符号操作、多步计算或多跳组合的任务。

| 任务族 | CoT 的作用 | 典型场景 | 边界 |
| --- | --- | --- | --- |
| 数学推理 | 把应用题拆成列式、计算、回代 | 小学数学、竞赛题、财务计算 | 需要答案验证器，否则错误链会被当成正确过程 |
| 多跳问答 | 逐跳连接实体和关系 | 知识问答、文档分析 | 检索错误会沿推理链传播 |
| 逻辑推理 | 展开约束、枚举情况、检查矛盾 | 逻辑题、规则校验、配置排查 | 复杂约束更适合交给形式化求解器 |
| 代码生成与调试 | 先分析输入/状态/边界，再给补丁 | 代码补全、单测生成、缺陷定位 | 需要测试执行和沙箱，不能只信文字推理 |
| Agent 任务规划 | 拆子目标、排依赖、决定下一步动作 | 多工具任务、流程自动化 | 长程任务会漂移，需要状态管理和重规划 |
| 工具调用决策 | 判断何时调用、调用什么、参数怎么填 | 搜索、数据库、计算器、内部 API | 需要权限、参数校验和错误处理 |

反过来，CoT 对以下任务的收益通常有限，甚至可能变差：简单的分类、抽取、改写、格式转换；模型已经通过记忆就能回答的事实题；对延迟极度敏感的在线场景。后文会给出更细的适用边界。

## 1.5 思维链并不等于真正理解

这是全文最需要强调的边界之一。CoT 文本是模型生成的行为，不是模型内部机制的“自白”。

**第一，推理过程可能是事后解释。** Turpin 等人（2023）的研究表明，模型可能受到输入中某些偏置线索的影响，但在生成的推理过程里完全不提这些线索，而是给出一个看起来合理的推导。也就是说，模型可能先形成答案，再补一段解释。

**第二，显式步骤不一定因果决定答案。** Lanham 等人（2023）用截断、替换、扰动推理步骤等干预方法测量忠实性，发现 CoT 与最终答案之间只有部分一致性。某些步骤改掉，答案不变；某些步骤看起来关键，实际只是装饰。

**第三，流畅不等于正确。** 一段推理越连贯、越像教科书，用户越容易相信它。这对生产系统是风险：错误答案配上一段漂亮的推导，比错误答案本身更难被识别。

**第四，收益高度依赖任务。** Sprague 等人（2024）的元分析指出，CoT 的稳定收益主要集中在数学和符号推理任务上，在其他任务上收益有限，某些情况下还会增加成本或降低准确率。不要把“CoT 在 GSM8K 上有效”外推成“CoT 对所有任务都有效”。

> 工程含义：不要把 CoT 当作“模型已经理解”的证据。它是一个有用的中间产物，需要验证器、外部证据和独立评估来约束。CoT 是能力激发与计算分配技术，不是正确性的保证。

# 二、什么是思维链 Chain-of-Thought

> 思维链（Chain-of-Thought，CoT）是指大语言模型在生成最终答案之前，先生成一系列中间推理步骤，通过将复杂问题分解为多个较小的推理单元，提升复杂任务求解能力的一种训练与推理范式。

这个定义包含三个要素：

1. **生成顺序**：先中间步骤，后最终答案；
2. **结构**：中间步骤构成一条可读的链，而不是零散的关键词；
3. **目的**：通过分解降低单步难度，提升复杂任务的求解能力。

从建模角度看，CoT 不是一种新的网络结构，而是一种**条件生成的分解方式**。模型仍然是自回归的，只是把原本一次性生成的答案，拆成了“推理轨迹 + 答案”两段。推理轨迹本身也是 token，因此可以被采样、验证、搜索、蒸馏和评估。

## 2.1 显式 CoT

显式 CoT 指模型输出用户可见的推理步骤。最常见的形式是在提示中加入“让我们一步一步思考”，或者给几个带步骤的示例，让模型模仿。

**优点**：

- 可读性强，用户能看懂模型在做什么；
- 便于调试，错误可以定位到具体步骤；
- 便于教学和人工审查；
- 可以作为训练数据，反哺小模型。

**缺点**：

- 推理过程不一定真实，可能误导用户；
- 可能泄露系统提示、工具 schema、安全策略或敏感信息；
- 增加输出 token，直接抬高成本和延迟；
- 攻击者可以利用推理过程分析防御逻辑，构造更精准的注入或越狱；
- 中间步骤中的错误假设可能被用户当成事实。

显式 CoT 适合开发调试、教学演示、低风险问答，以及需要人工复核的场景。它不适合默认暴露给所有生产用户，尤其是高风险业务。

## 2.2 隐式 CoT

“隐式 CoT”在工程上有两种不同含义，必须区分。

**第一种：生成了推理，但不展示。** 模型内部仍然生成推理 token，或者调用方拿到了完整 trace，但产品层只向用户输出答案或摘要。OpenAI 在 o1 系列中不向用户展示原始推理 token，而是提供摘要；Anthropic 的 extended thinking 通过 API 返回结构化的 thinking 内容块，产品层可以选择展示粒度。不同厂商策略不同，但共同点是：**推理仍然发生，只是可见性被控制**。

**第二种：不在文本空间生成推理，而在隐空间计算。** 这类方法让模型在连续向量或内部状态中完成多步计算，不产生可读的中间 token，例如 Coconut 一类的连续隐空间推理研究。它更接近“模型内部思考”，但可解释性和可控性更差，目前主要处于研究阶段。

工程上讨论“隐式 CoT”时，多数指的是第一种：内部有 trace，外部只给结论或摘要。它的优点是输出简洁、降低泄露风险、改善延迟感知；缺点是用户无法自行检查推理，系统必须自己承担验证责任。

还有一种相关观察：Wang 与 Zhou（2024）发现，即使不给 CoT 提示，模型在解码时也可能存在隐含的推理路径；改变解码策略可以激发出部分 CoT 行为。这说明 CoT 不只是外部提示的产物，也可能与模型内部已经学到的计算模式有关。不过，这类“无提示 CoT”的稳定性和可控性仍然有限，不能替代显式训练和验证。

## 2.3 Rationale

Rationale 是“作为答案解释的推理依据”。它可以来自人工标注、教师模型生成，也可以来自自动验证后的轨迹。

Rationale 和完整 trace 不是一回事：

- **Trace** 是完整过程，包含尝试、分支、工具调用、错误和修正；
- **Rationale** 是从 trace 中选取、压缩、重写后的一段解释，目的是让答案看起来有依据。

在训练中，rationale 是监督信号；在评估中，它是被检查对象；在产品中，它是用户可见解释的候选材料。三者对“质量”的要求不同：训练要求步骤正确且格式稳定，评估要求可判定，产品要求简洁、可读、不泄露。

## 2.4 Reasoning Trace

Reasoning trace 是推理过程的完整轨迹，通常包含：

- 输入问题与上下文；
- 每一步推理文本；
- 工具调用与返回结果；
- 分支、回溯、重试；
- 最终答案；
- token 统计、模型版本、采样参数；
- 验证结果与安全标签。

Trace 是训练、评估、调试和审计的原材料。它比 rationale 更完整，但也更敏感：里面可能包含用户隐私、内部提示、工具凭据、未经验证的假设。生产系统必须把 trace 当作受控数据管理，而不是普通日志。

## 2.5 Scratchpad

Scratchpad（草稿区）是模型用于中间计算或临时推导的空间。Nye 等人（2021）较早系统研究了“让模型把中间计算写出来”的效果：模型可以在草稿区做列竖式、执行算法、记录临时变量，最后再输出答案。

Scratchpad 和 CoT 的区别主要在侧重点：

- Scratchpad 强调“临时计算区”，内容可以是不可读的、可丢弃的；
- CoT 强调“推理步骤链”，通常要求步骤之间有逻辑关系，最终指向答案。

工程上两者经常混用。设计数据格式时，建议明确三个问题：草稿是否保留、是否给用户看、是否参与训练损失。不同选择对应不同的成本和风险。

## 2.6 三种视角：Prompt、数据格式、推理时计算

“CoT”这个词在不同语境下指代不同对象。混淆这三者，是很多讨论失效的原因。

| 视角 | 作用对象 | 干预点 | 典型做法 | 成本 | 主要失败模式 |
| --- | --- | --- | --- | --- | --- |
| Prompt 方法 | 输入提示 | 推理时 | Zero-shot CoT、Few-shot CoT | 低 | 对提示敏感，模型能力不足时无效 |
| 训练数据格式 | 模型参数 | 训练时 | SFT、蒸馏、拒绝采样、RLVR | 高 | 错误 rationale 污染模型 |
| 推理时计算策略 | 采样与搜索 | 推理时 | Self-Consistency、ToT、工具调用 | 中到高 | 成本失控、延迟上升、收益饱和 |

同一条“思维链”，在 Prompt 视角下是一句指令，在数据视角下是一条训练样本，在推理视角下是一份计算预算。讨论“CoT 有没有用”时，先问清楚是哪一种：是提示触发的行为，是训练出来的能力，还是用 token 换准确率的策略。

# 三、思维链与相关概念的区别

CoT 不是孤立技术。Self-Consistency、Tree-of-Thought、Program-of-Thought、工具增强推理，都是在其基础上做的扩展。下表按核心思想、是否显式展示中间过程、是否多次采样、是否调用外部工具、适合任务、优点、局限和工程成本做对比。

| 概念 | 核心思想 | 显式中间过程 | 多次采样 | 外部工具 | 适合任务 | 优点 | 局限 | 工程成本 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Direct Answer | 直接生成最终答案 | 否 | 否 | 否 | 简单问答、分类、抽取 | 快、便宜 | 多步任务容易错，错误无法定位 | 低 |
| Chain-of-Thought | 先生成推理步骤，再给答案 | 通常是 | 否 | 否 | 数学、逻辑、多跳问答 | 可解释、可分解、可训练 | 推理可能不忠实，token 成本高 | 低到中 |
| Scratchpad | 用草稿区做临时计算 | 可选 | 否 | 否 | 算术、算法执行、中间变量多 | 降低单步难度，可丢弃 | 不是完整答案协议，草稿质量难控 | 低 |
| Self-Consistency | 采样多条 CoT，对答案投票 | 内部是 | 是 | 否 | 数学、逻辑、可验证任务 | 提升稳定性，近似边缘化 | K 倍成本，采样可能高度相关 | 中 |
| Tree-of-Thought | 把推理看作搜索树，扩展和评估中间状态 | 是 | 是（分支） | 可选 | 规划、谜题、组合搜索 | 能回溯，探索多条路径 | 工程复杂，价值函数难做 | 高 |
| Program-of-Thought | 生成可执行程序，把计算交给解释器 | 是（代码） | 否 | 是（解释器） | 数学计算、数据分析、精确推理 | 计算精确，易验证 | 需要沙箱，形式化错误难修 | 中到高 |
| Tool-Augmented Reasoning | 推理过程中调用搜索、计算、数据库等工具 | 是 | 可选 | 是 | 知识问答、实时数据、Agent | 有外部依据，能纠正推理 | 延迟、权限、注入风险 | 高 |
| Hidden / Latent Reasoning | 内部推理，不展示完整过程，或在隐空间计算 | 否/部分 | 可选 | 可选 | 生产问答、安全敏感场景 | 输出简洁，减少泄露 | 不透明，评估和审计困难 | 中 |

可以把这些方法看成一棵方法树：

- **CoT 是基础形式**：把答案生成拆成“步骤 + 答案”。
- **Self-Consistency 是采样扩展**：在 CoT 上做多次采样和聚合。
- **Tree-of-Thought 是搜索扩展**：在 CoT 上做分支、评估和回溯。
- **Program-of-Thought 是计算卸载**：把算术和符号操作交给程序。
- **Tool-Augmented Reasoning 是观察扩展**：把外部工具结果接进推理链。
- **Hidden / Latent Reasoning 是表示与展示扩展**：改变推理发生的位置或可见性。

它们不是互斥的。生产系统常见的组合是：

- 数学题：CoT + Self-Consistency + 数学验证器；
- 数据分析：CoT + Program-of-Thought + 沙箱；
- 知识问答：CoT + RAG + 引用校验；
- Agent：CoT + ReAct + 工具权限控制；
- 高风险问答：内部 CoT + 用户可见摘要 + 安全过滤器。

# 四、思维链为什么有效

CoT 的有效性不是单一原因，而是多个机制叠加的结果。理解这些机制，才能判断什么时候该用、什么时候不该用。

## 4.1 问题分解

复杂问题一步到位的难度，等价于在一个很宽的条件分布上直接采样正确答案。分解后，每一步的条件分布更窄、更局部，模型更容易命中。

但分解不是免费午餐。假设每一步独立正确率为 p，n 步全对的概率是 p 的 n 次方。步骤越多，误差累积越严重。CoT 有效的条件是：**分解带来的单步准确率提升，足以抵消步数增加带来的累积损失**。

这解释了两个现象：

- 对真正需要多步推导的题，分解收益很大，因为单步难度下降明显；
- 对本来一步就能答的题，分解反而增加出错机会和成本。

## 4.2 中间状态表达

模型可以把“已经算出 120”“当前约束是 x > 0”“第三段文档否定了第一段的说法”写在 token 里，后续步骤通过 attention 读取。这相当于给模型一个外部工作记忆。

这个机制对多变量、多约束任务尤其重要。所有信息如果都挤在残差流里，会相互覆盖；写到文本里之后，信息变成了可寻址、可复制、可比较的对象。Scratchpad 的价值也在这里：它不要求模型“记住”，而是要求模型“写下来”。

## 4.3 更长的计算路径

Transformer 每个 token 的前向计算深度固定。生成 T 个中间 token，相当于增加了 T 次串行计算。CoT 因此可以被看作一种**推理时计算（test-time compute）分配策略**：用更多 token 换更深的串行推理。

理论上有工作表明，带 CoT 的 Transformer 在表达力上可以超过固定深度模型（Feng et al., 2023；Merrill & Sabharwal, 2024）。工程上更直接的经验是：准确率随推理 token 数增加而提升，但存在边际递减，并可能出现“过度思考”（overthinking）。

需要强调：不是所有任务都能从更长计算中获益。如果模型缺少完成任务所需的知识，更多 token 只会生成更多错误；如果任务本身不需要分解，更长计算只是浪费。

## 4.4 训练分布匹配

如果 SFT 数据中大量出现“步骤 + 答案”的样本，模型会学到这种输出分布；推理时 CoT prompt 只是激活已经学到的模式。反过来，一个从未见过 rationale 的模型，zero-shot CoT 的效果可能有限，尤其是小模型。

这也解释了为什么“加一句请一步一步思考”在不同模型上效果差异很大：它不是通用算法，而是分布触发器。模型在预训练或后训练中见过多少“分步解答”，决定了这个触发器有多灵。

## 4.5 错误可诊断

显式步骤让错误可以定位到某一步，便于人工审查、步骤级验证和过程奖励模型打分。一个答案错了，至少可以看到它是在哪一步开始错的：是理解错题意、列错式子、算错数，还是最后格式转换错。

但前提是 trace 忠实。如果 trace 是事后编的，诊断就会变成“给错误答案找理由”。所以“可诊断”是潜在优点，不是自动成立的属性。

## 4.6 与搜索和采样结合

单条 CoT 是一条路径。采样多条路径后，可以用投票、验证器或搜索选择更好的答案。Self-Consistency 可以理解为对推理路径 z 做近似边缘化：

```text
p(y | x) = Σ_z p(z | x) · p(y | x, z)
```

采样 K 条路径并投票，是在估计这个边缘分布中概率质量最大的答案。它不需要训练额外的验证器，代价是 K 倍生成成本。实际系统中，采样路径往往高度相关，投票增益会随 K 增大而饱和；如果模型在某个错误上高度自信，多数票也可能错得很一致。

## 4.7 局限与边界

- **推理步骤可能是事后解释。** 见 1.5 节。trace 可读，不等于 trace 因果决定答案。
- **CoT 可能增加幻觉。** 更多 token 意味着更多机会编造事实、虚构引用、引入未经验证的假设。
- **长推理链可能引入更多错误。** 误差随步数累积；步骤越多，越需要过程验证。
- **并非所有任务都需要 CoT。** 简单分类、抽取、改写通常直接回答更好。
- **对简单任务可能降低效率。** 增加延迟和成本，收益却接近零。
- **CoT 不能替代知识和工具。** 模型不知道的事实，推理再长也推不出来；需要 RAG、数据库或搜索。
- **CoT 不是形式化证明。** 文字推导可能跳步、循环论证或使用错误前提；高风险场景需要符号验证器或人工复核。

# 五、思维链训练方法

CoT 能力可以通过多种方式获得：监督微调、蒸馏、拒绝采样、偏好学习、可验证奖励强化学习，以及过程监督。它们不是互斥的，实际训练通常是组合拳。

设问题为 x，推理轨迹为 z，最终答案为 y，策略为 πθ。SFT 最大化 log πθ(z, y | x)；强化学习最大化期望奖励 E[R(x, z, y)]，通常还会加一个相对参考模型的 KL 约束。监督信号可以作用在 y（结果监督）、z（过程监督）或两者同时。

选择训练方法时，本质上是回答三个问题：

1. 数据从哪里来，质量如何保证？
2. 奖励或标签有多可靠，能不能规模化？
3. 要不要约束中间步骤，还是只约束最终答案？

## 5.1 SFT：使用带推理过程的数据进行监督微调

SFT 是最直接的方法：准备“问题 + 推理步骤 + 最终答案”的样本，用标准的下一 token 预测损失训练模型。

示例数据格式：

```json
{
  "question": "一件商品先涨价 20%，再降价 20%，最终价格相对原价如何？",
  "reasoning": "设原价为 100 元。涨价 20% 后价格为 100×1.2=120 元。降价 20% 是在 120 元的基础上乘以 0.8，得到 96 元。96 小于 100，所以最终价格比原价低 4%。",
  "answer": "比原价低 4%"
}
```

工程实现上有几个细节：

- **损失掩码**：通常只对推理和答案部分计算损失，问题部分 mask 掉；如果使用 chat template，要确保系统提示、角色标记、格式 token 的处理一致。
- **格式稳定性**：推理步骤和最终答案要用固定分隔符，例如 `<reasoning>...</reasoning>` 和 `<answer>...</answer>`，方便后续抽取和验证。
- **数据来源**：人工标注的 CoT 质量高但贵；教师模型生成的 CoT 便宜但可能继承错误；两者混合是常见做法。
- **质量优先于数量**：一条错误 rationale 对模型的伤害，可能大于十条正确样本的收益。错误过程会被模型当成“可接受的推理模式”学进去。
- **避免答案泄漏**：如果训练样本中答案出现在推理开头，模型会学会“先写答案再编过程”；数据构建时要检查这种模式。

SFT 主要教模型三件事：推理的格式、步骤的粒度、答案的表达方式。它不保证模型学到可泛化的推理算法。一个模型可以把训练集里的解题模板背得很熟，遇到分布外问题仍然失败。

在 RL 流水线中，SFT 通常充当“冷启动”：先让模型学会按格式输出推理，再用强化学习优化正确性。

## 5.2 Rationale Distillation

Rationale distillation 用更强的教师模型生成推理过程，过滤后蒸馏给较小的学生模型。

典型流程：

1. 用教师模型对一批问题生成多条推理轨迹；
2. 用答案验证器、规则或人工抽检过滤；
3. 把高质量轨迹作为 SFT 数据训练学生模型；
4. 可选地，让学生模型自己采样，再由教师模型打分或修正，做 on-policy 蒸馏。

优点：

- 大幅降低人工标注成本；
- 可以把大模型的推理风格和步骤粒度迁移给小模型；
- 对数学、代码等有验证器的任务，过滤效率较高。

风险：

- 教师模型的错误会被学生继承，甚至被放大；
- 教师和学生的容量差距过大时，学生学不会过长的推理链；
- 教师的推理风格可能不适合学生的分布，导致“形似神不似”；
- 如果只过滤最终答案，答案正确但过程错误的轨迹仍可能进入训练集。

DeepSeek-R1 的技术报告展示了另一种思路：先用强化学习训练一个大型推理模型，再把它的推理能力蒸馏到较小的 dense 模型。这里的蒸馏不只是“教格式”，而是把 RL 阶段得到的推理行为迁移到学生模型。工程上要注意，蒸馏得到的学生模型通常不具备教师模型在 RL 中探索出的全部能力，它更像是在模仿教师的输出分布。

## 5.3 Rejection Sampling Fine-tuning

拒绝采样微调（Rejection Sampling Fine-tuning，RFT）的思路是：对同一个问题生成多条推理轨迹，用验证器筛选出最终答案正确的轨迹，再把它们用于 SFT。

典型流程：

1. 从当前策略（或教师模型）对问题采样 K 条轨迹；
2. 用答案验证器判断每条轨迹的最终答案是否正确；
3. 保留正确的轨迹，可选地按质量分排序；
4. 用保留的轨迹做 SFT；
5. 用新模型重新采样，迭代多轮；
6. 每轮加入新问题，避免过拟合旧样本。

这条路线与 STaR、RFT、ReST 等工作相关。它的优势是**不需要人工标注每一步**，只需要一个可靠的最终答案验证器。对数学、代码、结构化输出等可验证任务，这是目前最常用的自举方法之一。

需要注意的问题：

- **验证器假阳性**：答案正确但推理错误；如果直接用于 SFT，会教会模型“错误过程也能得到正确答案”。
- **多样性坍缩**：多轮迭代后，模型可能只会一种解法，采样多样性下降。
- **分布漂移**：模型在自己的输出上训练，错误会逐渐累积；需要定期混入人工数据或教师数据。
- **验证器覆盖不足**：开放任务没有可靠验证器，RFT 不适用。
- **难度偏差**：太简单的问题全是正确样本，太难的问题全是错误样本；需要按难度分层采样。

## 5.4 RLHF / RLAIF 中的思维链

RLHF 用人类偏好数据训练奖励模型，再用 PPO、DPO 等算法优化策略。RLAIF 用 AI 反馈替代部分人类反馈。两者都可以用于 CoT：

- 偏好数据可以比较两条推理轨迹，判断哪条更好；
- 奖励模型可以给整条轨迹打分；
- 也可以只比较最终答案，让模型自己学推理过程。

问题在于，偏好信号对“推理质量”的判断并不稳定：

- **长度偏好**：标注者和奖励模型都可能偏好更长、更详细的解释，即使长解释没有更好。
- **表面合理性**：一段推理只要结构完整、语气自信，就可能得到高分，即使中间有错误。
- **奖励黑客**：模型会学会迎合奖励模型，而不是真正解决问题；例如堆砌步骤、重复结论、使用看起来专业的术语。
- **主观性**：开放任务的“好推理”没有唯一标准，偏好数据难以一致。

因此，RLHF 更适合优化风格、安全性和帮助性；对可验证的正确性，RLVR 通常更直接。两者可以组合：可验证任务用规则奖励，开放任务用偏好奖励，安全和格式用单独的约束。

## 5.5 RLVR 与可验证推理训练

RLVR（Reinforcement Learning with Verifiable Rewards）用可验证的奖励训练模型，不依赖人类主观判断。常见奖励来源：

- 数学答案的符号等价判断；
- 代码的单元测试；
- 约束满足检查；
- 结构化输出的 schema 校验；
- 数据库查询结果比对；
- 形式化证明器的通过/失败。

典型算法是 PPO 或 GRPO。GRPO 在同一个问题的多条采样之间做相对比较，不需要单独的价值模型，工程上更轻量。奖励通常是 0/1 的正确性信号，也可以加格式奖励、长度惩罚、工具使用奖励。

优点：

- 奖励客观，可规模化；
- 不依赖奖励模型，减少奖励黑客的面；
- 对数学、代码等任务效果直接；
- 可以和小模型结合，降低推理成本。

局限：

- **验证器覆盖有限**：只适用于答案可验证的任务；开放写作、战略分析、部分 Agent 任务难以定义奖励。
- **奖励黑客**：模型可能利用验证器漏洞，例如硬编码测试用例、输出验证器喜欢的格式、绕过边界条件。
- **稀疏奖励**：最终答案只有对/错，中间步骤没有反馈，学习效率低。
- **多样性下降**：RL 可能收窄输出分布，pass@1 提升但 pass@k 下降。
- **能力边界**：有研究发现，RLVR 主要提升的是采样效率，即把基础模型已经具备的正确路径选出来，而不是创造全新的推理能力（Yue et al., 2025）。这不意味着 RLVR 没用，但意味着不能把它当成“无中生有”的魔法。

工程上，RLVR 的关键不是算法名字，而是**验证器的质量**。验证器要确定、可复现、覆盖边界、难以被 exploit；测试集要隐藏，执行要隔离，奖励要防止格式套利。

## 5.6 Process Supervision

过程监督（Process Supervision）对每一步推理进行监督，而不仅仅是最终答案。

常见做法：

- 人工标注每一步是对、错还是中性；
- 训练过程奖励模型（PRM），给每个步骤打分；
- 用 PRM 在推理时做 best-of-N 重排或树搜索；
- 用自动方法生成步骤标签，例如从当前步骤继续 rollout，根据最终正确率估计该步骤的价值（Math-Shepherd 一类方法）。

优点：

- 比结果监督更细粒度，能定位错误步骤；
- 对长推理链更友好，可以在早期剪枝；
- 在 best-of-N 和搜索场景中，通常比只看最终答案更有效；
- 可以用于训练、评估和推理时选择。

缺点：

- 标注成本高，尤其是需要专家判断的领域；
- “什么算一步”没有唯一标准，步骤切分影响监督效果；
- 同一答案可能有多条正确路径，过程标签不一定唯一；
- PRM 也可能被 reward hacking，模型会学会生成 PRM 喜欢的步骤；
- 自动步骤标注依赖 rollout，计算成本高，且估计有噪声。

Lightman 等人（2023）的“Let's Verify Step by Step”工作表明，在 MATH 数据集上，过程监督训练的验证器在 best-of-N 重排中优于结果监督。这个结论有边界：它依赖高质量的步骤标注和特定的任务分布，不能直接外推到所有任务。

## 5.7 Outcome Supervision

结果监督（Outcome Supervision）只根据最终答案是否正确训练。它实现简单，适合答案易验证的任务。

优点：

- 数据要求低，只需要问题和标准答案；
- 可以用程序自动判定，规模化容易；
- 与 RLVR 天然契合；
- 不强制模型采用某一种推理路径，保留解法多样性。

缺点：

- 信用分配困难：最终答案错了，不知道是哪一步错；
- 可能奖励“蒙对”：答案正确但推理错误；
- 对长推理链，学习信号稀疏；
- 无法保证推理过程真实可靠。

结果监督和过程监督不是二选一。常见组合是：用结果监督做大规模冷启动，用过程监督做精排和搜索，用 RLVR 做最终优化。

## 5.8 不同训练方法对比

| 方法 | 数据来源 | 监督信号 | 是否需要人工标注 | 是否需要 Verifier | 优点 | 局限 | 适合任务 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| SFT | 人工 CoT、教师模型、历史数据 | 轨迹 token 级交叉熵 | 可能需要 | 可选 | 简单、稳定、可控 | 易学格式不学能力，错误数据污染 | 通用冷启动、格式对齐 |
| Rationale Distillation | 强模型生成 | 轨迹 token 级交叉熵 | 少量抽检 | 建议有 | 降低成本，迁移推理风格 | 继承教师错误，容量不匹配 | 小模型推理能力迁移 |
| Rejection Sampling | 当前策略或教师采样 | 正确轨迹的 SFT | 少量抽检 | 必须有 | 自举、无需步级标注 | 验证器假阳性、多样性坍缩 | 数学、代码、可验证任务 |
| RLHF / RLAIF | 人类或 AI 偏好 | 偏好奖励 | 可能需要 | 可选 | 优化风格、安全、帮助性 | 长度偏好、奖励黑客、主观性 | 开放问答、对话、安全对齐 |
| RLVR | 问题 + 可验证答案 | 规则奖励（0/1 或连续） | 通常不需要 | 必须有 | 客观、可规模化、直接优化正确率 | 验证器覆盖有限、奖励黑客、多样性下降 | 数学、代码、形式化任务 |
| Process Supervision | 步级标签、rollout 估计 | 步级奖励 / PRM | 可能很贵 | 可选 | 细粒度、可剪枝、适合搜索 | 标注贵、步骤定义模糊、PRM 可被 hack | 长推理、数学证明、复杂规划 |
| Outcome Supervision | 问题 + 标准答案 | 最终答案奖励 | 不需要 | 必须有 | 简单、 scalable | 信用分配难、可能奖励蒙对 | 答案易验证的任务 |

实践中的常见组合是：

```text
SFT 冷启动 → 拒绝采样 → RLVR → 过程奖励 / 搜索增强 → 蒸馏到小模型
```

这不是固定流水线。数据质量、验证器可靠性和任务分布，比方法名字更重要。一个验证器不可靠的 RLVR 流水线，效果可能不如一个数据干净的小规模 SFT。

# 六、思维链数据构建

训练 CoT 能力，数据是瓶颈。模型可以从少量高质量样本中学到推理格式和步骤模式，也可以从大量低质量样本中学到错误习惯。数据构建的目标不是“多”，而是“可验证、可追溯、分布合理”。

## 6.1 数据来源

| 来源 | 优点 | 缺点 | 适合用途 | 主要风险 |
| --- | --- | --- | --- | --- |
| 人工专家标注 | 质量高，步骤可信 | 贵、慢、难扩展 | 冷启动、评估集、高价值领域 | 标注者不一致，覆盖有限 |
| 教师模型生成 | 便宜、快、可大规模 | 继承教师错误和风格 | 蒸馏、RFT 初始数据 | 幻觉、错误 rationale |
| 多模型生成 | 多样性好，可交叉验证 | 成本高，质量参差 | 候选池、一致性筛选 | 共同偏见、答案冲突 |
| 用户历史问题 | 贴近真实分布 | 隐私、噪声、长尾 | 领域适配、难度分层 | PII 泄露、标注缺失 |
| 公开数学/代码数据集 | 有标准答案，易验证 | 可能污染评测集 | SFT、RLVR、评估 | 训练集与测试集重叠 |
| Agent 执行 Trace | 真实工具调用和多步决策 | 长、噪声大、含敏感信息 | Agent 训练、过程评估 | 权限信息、凭证泄露 |
| 工具调用日志 | 有真实观察和错误恢复 | 结构不统一，需清洗 | 工具使用训练、失败分析 | 注入内容、内部数据 |

数据来源应该混合，而不是依赖单一来源。人工数据保证质量下限，教师数据提供规模，真实 trace 提供分布，公开数据集提供可验证性。混合比例要按任务和阶段调整：冷启动阶段人工数据权重高，规模化阶段合成数据权重高，但要有验证器兜底。

## 6.2 数据字段设计

一条 CoT 训练样本建议包含以下字段：

```json
{
  "id": "cot-math-000123",
  "question": "一件商品先涨价 20%，再降价 20%，最终价格相对原价如何？",
  "context": [],
  "reasoning_steps": [
    {
      "step_id": 1,
      "text": "设原价为 100 元。",
      "type": "setup",
      "evidence": null,
      "verifiable": false
    },
    {
      "step_id": 2,
      "text": "涨价 20% 后价格为 100×1.2=120 元。",
      "type": "calculation",
      "evidence": null,
      "verifiable": true
    },
    {
      "step_id": 3,
      "text": "降价 20% 是在 120 元基础上乘以 0.8，得到 96 元。",
      "type": "calculation",
      "evidence": null,
      "verifiable": true
    },
    {
      "step_id": 4,
      "text": "96 小于 100，所以最终价格比原价低 4%。",
      "type": "conclusion",
      "evidence": null,
      "verifiable": true
    }
  ],
  "final_answer": "比原价低 4%",
  "task_type": "math_word_problem",
  "difficulty": "easy",
  "source": "human_expert",
  "verifier_result": {
    "passed": true,
    "method": "symbolic_equivalence",
    "score": 1.0
  },
  "quality_score": 0.95,
  "safety_label": {
    "safe": true,
    "categories": []
  },
  "metadata": {
    "language": "zh",
    "created_at": "2026-11-17",
    "model": null,
    "license": "internal",
    "split": "train"
  }
}
```

字段说明：

- **question**：原始问题，保留用户表达，不要过早归一化。
- **context**：检索到的证据、对话历史、工具返回结果；没有则为空。
- **reasoning_steps**：结构化步骤列表，便于步骤级验证、PRM 训练和错误定位。
- **final_answer**：最终答案，格式要统一，便于验证器比较。
- **task_type**：任务类型，用于分层采样和评估。
- **difficulty**：难度标签，用于课程学习和难度分层。
- **source**：数据来源，用于追溯和权重分配。
- **verifier_result**：验证器结果，包含方法、是否通过、分数。
- **quality_score**：综合质量分，用于排序和过滤；要说明打分规则。
- **safety_label**：安全标签，包含是否安全、风险类别。
- **metadata**：语言、时间、模型、许可证、数据切分等。

字段设计的原则是：**训练需要的、评估需要的、审计需要的，分开存**。不要把用户可见的解释、内部 trace、验证结果混在一个字段里，否则后续很难做权限控制和数据治理。

## 6.3 数据质量控制

一条可用的 CoT 样本，至少要通过以下检查：

| 维度 | 检查内容 | 常见方法 | 不通过的处理 |
| --- | --- | --- | --- |
| 答案正确 | 最终答案与标准答案等价 | 符号验证、单测、规则 | 丢弃或转负样本 |
| 步骤一致 | 每一步能由前一步和已知条件推出 | 人工抽检、NLI、LLM Judge | 丢弃或标注待修 |
| 不跳步 | 关键中间量没有省略 | 规则检查、步骤覆盖度 | 补写或降权 |
| 无幻觉 | 没有编造事实、引用、数据 | 证据核对、检索验证 | 丢弃 |
| 格式稳定 | 分隔符、答案格式、语言一致 | 正则、schema 校验 | 自动修复或丢弃 |
| 无敏感信息 | 无 PII、密钥、内部提示 | 正则、分类器、脱敏 | 脱敏或丢弃 |
| 无危险内容 | 推理过程不包含危险操作细节 | 安全分类器、人工复核 | 丢弃或隔离 |
| 去重与防污染 | 不与评测集重叠，不重复采样 | MinHash、n-gram 重叠 | 移除 |
| 难度标签 | 难度与模型实际表现一致 | 模型通过率分层 | 重新标注 |

质量控制的难点在于“步骤一致”。最终答案对，不代表中间步骤对；中间步骤顺，也不代表每一步都必要。工程上建议把质量拆成多个分数，而不是一个笼统的“好/坏”：

- **答案分**：最终答案是否正确；
- **过程分**：步骤是否正确、完整、无矛盾；
- **格式分**：是否符合输出协议；
- **安全分**：是否包含敏感或危险内容；
- **难度分**：模型通过率或人工评级。

多分数便于后续按用途筛选：训练 SFT 可以容忍少量格式问题，但不能容忍错误推理；训练 PRM 需要步骤级标签；评估集要求最高。

## 6.4 自动过滤方法

| 方法 | 能发现的问题 | 发现不了的问题 | 成本 | 使用建议 |
| --- | --- | --- | --- | --- |
| 答案验证器 | 最终答案错误、格式不符 | 过程错误、蒙对 | 低 | 所有可验证任务的第一道过滤 |
| 单元测试 | 代码功能错误、边界错误 | 未覆盖的需求、代码风格 | 中 | 代码任务必须，测试要隐藏 |
| 数学等价判断 | 表达式不等价、单位错误 | 题意理解错误、步骤错误 | 低到中 | 配合符号计算和数值抽查 |
| LLM Judge | 步骤不连贯、解释缺失、明显幻觉 | 细微事实错误、judge 自身偏见 | 中 | 用作粗筛，不作为唯一标准 |
| 规则校验 | 格式、长度、禁用词、PII | 语义错误、隐晦违规 | 低 | 前置过滤，快速省钱 |
| 多模型一致性 | 答案冲突、低置信样本 | 共同错误、共同偏见 | 高 | 用于挑选高价值样本或触发人工复核 |
| 人工抽检 | 细微错误、领域问题、安全风险 | 覆盖率有限 | 高 | 按难度和风险分层抽样 |

自动过滤的核心原则是：**验证器负责“可判定的部分”，人负责“不可判定的部分”**。不要指望 LLM Judge 发现所有错误，也不要把多模型一致当成正确性证明——多个模型可能一起错。

数学等价判断也有坑：`0.5` 和 `1/2` 等价，但 `50%` 是否等价取决于题目问的是比例还是数值；`x=1` 和 `x=1.0` 等价，但 `1 米` 和 `1 厘米` 不等价。单位、百分号、范围、多解，都要在归一化器里显式处理。

## 6.5 常见数据问题

| 问题 | 表现 | 原因 | 处理建议 |
| --- | --- | --- | --- |
| 推理正确但答案格式错误 | 过程对，最终答案抽取失败 | 格式不统一、分隔符缺失 | 统一答案标记，增加格式校验 |
| 答案正确但推理错误 | 最终答案对，中间步骤有错 | 蒙对、教师幻觉、步骤跳步 | 步骤级验证，不能只用答案过滤 |
| 推理冗长 | 大量重复、无关展开 | 模型偏好长解释、缺乏长度控制 | 设定步骤上限，训练简洁样本 |
| 推理中出现无关内容 | 闲聊、重复题目、自我怀疑 | 数据清洗不彻底、prompt 泄漏 | 规则过滤，训练时强调任务边界 |
| 教师模型幻觉 | 编造公式、引用、数据 | 教师能力不足、缺乏证据 | 证据核对，多模型交叉验证 |
| 数据集污染 | 训练集与评测集重叠 | 公开数据混合、爬取未去重 | n-gram 重叠检测，保留干净测试集 |
| 训练集过拟合 | 训练集表现好，测试集差 | 数据重复、模板单一、难度集中 | 去重、增加多样性、难度分层 |
| 语言混杂 | 中英文混用、术语不一致 | 教师模型风格、数据来源杂 | 统一语言规范，术语表校验 |
| 单位/范围错误 | 数值对但单位错、忽略定义域 | 归一化不严、验证器覆盖不足 | 单位检查，符号计算加假设 |

## 6.6 工程建议

1. **给每条数据保留 provenance**：来源、生成模型、采样参数、验证器版本、标注人。出问题时能追溯。
2. **去重要做两遍**：训练集内部去重，以及训练集与评测集的污染检测。MinHash 或 n-gram 重叠是低成本方案。
3. **难度分层**：按模型通过率或人工评级分层，训练时做课程学习，评估时看各难度段的表现。
4. **质量分要可解释**：不要只给一个 0.87 的分数，要能拆成答案分、过程分、格式分、安全分。
5. **保留负样本**：错误答案、错误步骤、验证器拒绝的轨迹，可以用于训练验证器、PRM 或做对比学习，不要全部丢掉。
6. **人工抽检按风险分层**：高风险领域、低置信样本、步骤异常样本优先抽检。
7. **数据版本化**：数据集、验证器、模型、评测集都要有版本号；否则无法复现实验。
8. **隐私与合规**：用户历史数据要脱敏、授权、限定用途；工具日志要清除凭证和内部标识。
9. **不要把模型自己的未过滤输出直接回流训练**：模型会放大自己的错误，形成闭环漂移。
10. **为评估集留出干净 holdout**：评估集一旦用于调参，就不再是评估集；要定期补充新样本。

# 七、推理阶段如何使用思维链

训练决定模型“会不会”分步推理，推理阶段决定“用不用、用多少、怎么用”。同一个模型，换一种推理策略，准确率、延迟和成本可能差一个量级。

## 7.1 Zero-shot CoT

Zero-shot CoT 最简单：在问题后加一句“请一步一步思考”或“Let's think step by step”。

适用场景：

- 模型已经具备较强的指令遵循和推理能力；
- 任务需要多步推导，但没有现成的示例；
- 快速验证模型是否具备 CoT 行为。

优点：

- 零样本、低成本、易接入；
- 对数学应用题、逻辑题、多跳问答通常有提升；
- 不依赖示例库。

局限：

- 对提示措辞敏感，换一种说法效果可能差很多；
- 小模型可能生成“看起来像步骤”的废话，准确率反而下降；
- 对简单任务可能增加延迟而无收益；
- 不能保证推理忠实，错误链可能更隐蔽。

Kojima 等人（2022）报告，在 MultiArith 等任务上，zero-shot CoT 相比直接回答有显著提升。但这类结果依赖模型规模和任务类型，不能无条件外推。工程上应该在自己的评估集上验证，而不是因为论文有效就默认开启。

## 7.2 Few-shot CoT

Few-shot CoT 给模型几个带推理步骤的示例，让模型模仿示例的格式和推理方式。

关键点：

- **示例质量比数量更重要**：3 到 5 个高质量示例，通常比 20 个粗糙示例更好；
- **格式要稳定**：步骤分隔符、答案标记、语言风格保持一致；
- **示例要与任务同分布**：数学题配数学示例，代码题配代码示例；
- **示例顺序有影响**：模型可能受最后一个示例的影响，标签分布要平衡；
- **可以检索示例**：从示例库中按相似度检索，比固定示例更适应不同问题。

适用场景：

- 任务格式相对固定，但问题难度较高；
- 需要控制输出结构，例如固定字段、固定步骤数；
- 模型规模中等，zero-shot CoT 不稳定。

局限：

- 示例会占用上下文，增加成本；
- 示例可能引入偏差，模型会模仿示例中的错误模式；
- 示例选择和排序需要实验，工程上比 zero-shot 复杂。

## 7.3 Self-Consistency

Self-Consistency 对同一个问题采样多条推理链，然后对最终答案投票或聚合。

基本流程：

1. 用较高的 temperature 采样 K 条 CoT；
2. 从每条轨迹中抽取最终答案；
3. 对答案做归一化，判断等价；
4. 按答案分组投票；
5. 可选地用验证器给每组加权；
6. 选票数最高或综合得分最高的答案。

适用场景：

- 数学、逻辑、符号推理等答案可判定的任务；
- 单条 CoT 准确率不够稳定，但正确答案在采样分布中有一定概率；
- 可以接受 K 倍成本。

优点：

- 不需要额外训练，接入简单；
- 对采样噪声有鲁棒性；
- 可以给出置信度（票数占比）；
- 与验证器结合后效果更好。

局限：

- K 倍生成成本，延迟也上升；
- 采样路径可能高度相关，增益随 K 饱和；
- 多数票不是概率校准，可能在系统性错误上一致错；
- 答案抽取和归一化是主要故障源；
- 对开放生成任务，答案难以比较，投票不适用。

工程上，Self-Consistency 的关键不是“采样多少条”，而是“答案抽取是否可靠、归一化是否覆盖等价形式、验证器是否可信”。伪代码见第十二节。

## 7.4 Tree-of-Thought

Tree-of-Thought（ToT）把推理过程看作一棵搜索树：每个节点是一个中间状态，模型提出候选下一步，评估器给候选打分，搜索算法决定扩展、剪枝或回溯。

常见组件：

- **Thought proposer**：生成候选下一步；
- **State evaluator**：判断当前状态是否有希望；
- **Search strategy**：BFS、DFS、beam search 或 MCTS；
- **Backtracking**：发现死路时回到上一层。

适用场景：

- 规划、谜题、组合搜索；
- 需要尝试多条路径、比较中间状态的任务；
- 单条 CoT 容易走进死路，且错误可以在中间状态被发现。

优点：

- 能探索多条路径，支持回溯；
- 可以在早期剪枝，节省后续计算；
- 对需要“先试再改”的任务更自然。

局限：

- 工程复杂度高：需要状态表示、评估器、搜索控制；
- 评估器质量决定上限，评估器错了会剪掉正确路径；
- 计算成本高，分支因子和深度一上来就爆炸；
- 对开放生成任务，状态评估很主观。

ToT 不适合作为默认策略。它适合“答案空间可搜索、中间状态可评估”的窄场景。工程上先用 CoT + Self-Consistency，确认瓶颈在搜索而不是采样，再考虑 ToT。

## 7.5 Program-of-Thought

Program-of-Thought（PoT）让模型生成可执行程序来解决问题，把计算交给 Python、SQL 或符号系统。PAL 是同类思路的代表。

适用场景：

- 数学计算、数据分析、统计汇总；
- 需要精确算术、字符串处理、日期计算；
- 答案可以通过程序验证。

优点：

- 计算精确，避免语言模型的心算错误；
- 程序本身可读、可测试、可复用；
- 可以把“推理”和“计算”分离：模型负责形式化，解释器负责执行。

局限：

- 需要沙箱执行环境，安全和资源隔离是硬要求；
- 模型可能形式化错问题：代码跑通，但算的不是题目要的；
- 代码可能依赖不存在的库、版本不兼容、超时；
- 执行错误需要反馈给模型修复，增加轮次；
- 对不可形式化的任务不适用。

工程上，PoT 的关键是“执行—观察—修复”闭环：代码报错时，把错误信息作为观察返回给模型，让它修正；同时限制执行时间、内存、网络和文件系统权限。

## 7.6 Tool-Augmented CoT

Tool-Augmented CoT 在推理过程中调用外部工具：搜索、计算器、数据库、代码执行器、内部 API。模型在每一步判断是否需要工具、调用什么工具、参数怎么填，然后把工具返回结果作为新的观察，继续推理。

这是 Agent 系统中的常见模式，ReAct 的 Thought / Action / Observation 循环是典型代表。

关键设计：

- **工具选择**：模型根据当前状态决定是否调用工具，避免“为了调用而调用”；
- **参数校验**：工具参数要经过 schema 校验和权限检查，不能直接信任模型输出；
- **结果注入**：工具返回内容可能包含恶意指令，要当作不可信数据处理；
- **错误恢复**：工具超时、报错、返回空结果时，模型要能重试、换工具或降级；
- **权限边界**：不同用户、不同任务有不同的工具权限；
- **审计**：记录每次调用的参数、结果、耗时和错误。

优点：

- 推理有外部依据，减少幻觉；
- 能处理实时数据、内部数据、精确计算；
- 可以把复杂操作交给专用系统。

局限：

- 延迟高，链路长；
- 工具故障会传播到推理链；
- 参数错误、权限错误、注入攻击都是新增风险；
- 工具返回结果的格式和语义需要额外处理。

## 7.7 Hidden CoT / Answer-only

Hidden CoT 指模型内部使用推理，但对用户只输出结论和简要解释；Answer-only 则更极端，只输出答案。

适用场景：

- 生产环境的普通用户问答；
- 高风险领域，完整推理可能泄露策略或敏感信息；
- 用户只关心结论，不关心推导；
- 需要控制输出长度和延迟感知。

优点：

- 输出简洁，用户体验好；
- 降低泄露不可靠推理、系统提示和敏感信息的风险；
- 减少用户被错误中间步骤误导的概率；
- 便于统一输出格式和合规审查。

局限：

- 用户无法自行检查推理，系统要承担更多验证责任；
- 出问题时排查更困难，需要内部 trace；
- 如果模型内部推理错误，摘要可能掩盖错误；
- 监管或审计场景可能要求可解释性，不能一概隐藏。

工程上建议把“内部推理”和“用户解释”分开：内部保留完整 trace 用于调试和评估，用户只看到经过安全过滤和事实核对的摘要。两者不是同一份文本的简单截断。

## 7.8 不同推理策略对比

| 策略 | 核心思想 | 优点 | 缺点 | 成本 | 适合场景 |
| --- | --- | --- | --- | --- | --- |
| Direct Answer | 直接给答案 | 快、便宜 | 多步任务易错 | 低 | 简单问答、分类、抽取 |
| Zero-shot CoT | 提示模型分步思考 | 零样本、易接入 | 对提示敏感，小模型不稳定 | 低 | 中等难度推理、快速验证 |
| Few-shot CoT | 用示例引导步骤格式 | 格式稳定、可控 | 占上下文、示例有偏 | 中 | 格式固定的复杂任务 |
| Self-Consistency | 多采样 + 投票 | 稳定、可给置信度 | K 倍成本、可能一致错 | 中到高 | 数学、逻辑、可验证任务 |
| Tree-of-Thought | 搜索 + 评估 + 回溯 | 能探索多路径 | 工程复杂、成本高 | 高 | 规划、谜题、组合搜索 |
| Program-of-Thought | 生成程序并执行 | 计算精确、可测试 | 需沙箱、形式化错误 | 中到高 | 数学计算、数据分析 |
| Tool-Augmented CoT | 推理中调用工具 | 有外部依据、能纠错 | 延迟、权限、注入风险 | 高 | 知识问答、实时数据、Agent |
| Hidden CoT / Answer-only | 内部推理，外部简洁 | 安全、简洁 | 不透明、审计难 | 中 | 生产问答、高风险场景 |

## 7.9 预算路由：不是所有请求都值得推理

生产系统不应该对所有请求默认开启最重的推理策略。一个实用的做法是做预算路由：

| 请求难度 | 建议策略 | 目标 | 风险控制 |
| --- | --- | --- | --- |
| 简单（分类、抽取、改写） | Direct Answer | 低延迟、低成本 | 置信度低时升级 |
| 中等（多步问答、常规数学） | Zero-shot / Few-shot CoT | 准确率与成本平衡 | 答案格式校验 |
| 困难（竞赛题、复杂代码） | CoT + Verifier / Self-Consistency | 提高正确率 | 预算上限、超时降级 |
| 极难（规划、组合搜索、长程任务） | ToT / 工具增强 / Agent | 探索与外部依据 | 循环控制、权限、人工兜底 |

难度路由本身也可能错。工程上要有兜底：路由到轻量策略后，如果置信度低、验证失败或用户反馈异常，升级到更重的策略；同时监控“升级率”和“单位成功成本”，避免路由把成本推高。

# 八、显式思维链与生产环境安全

## 8.1 显式 CoT 的优点

显式 CoT 的价值是真实的，不能因为风险就全盘否定：

- **可解释**：用户能看到答案是怎么来的，便于判断可信度；
- **可调试**：开发和运维可以定位错误步骤，而不是只看到一个错误答案；
- **便于教学**：在培训、演示、辅助学习场景，步骤本身就是内容；
- **便于人工审查**：高风险业务中，审查员可以逐条核对推理；
- **便于数据回流**：人工修正后的 trace 可以作为高质量训练数据。

这些优点在内部工具、低风险问答、教育产品中尤其明显。问题不在于“显式 CoT 有没有用”，而在于“是否应该无条件展示给所有用户”。

## 8.2 显式 CoT 的风险

**第一，推理过程不一定真实。** 如 1.5 节所述，CoT 可能是事后解释。用户看到一段流畅推导，会倾向于相信答案，即使推导与模型的真实计算过程不一致。

**第二，可能暴露系统提示或安全策略。** 推理 trace 中可能包含系统提示的片段、工具 schema、权限规则、审核阈值、内部文档结构。攻击者可以利用这些信息分析防御逻辑。

**第三，可能包含未经验证的中间假设。** 模型在推理中可能先假设一个错误前提，后面又修正；如果用户只看到中间部分，可能把错误假设当成事实。

**第四，可能增加用户对错误答案的信任。** 一段结构完整、语气自信的推理，会显著提高用户对答案的信任度。错误答案配上漂亮推导，比错误答案本身更危险。

**第五，可能泄露敏感信息。** 用户隐私、内部数据、工具凭据、业务规则，都可能出现在 trace 中。尤其是 Agent 场景，trace 会包含工具调用参数和返回结果。

**第六，可能被用于 Prompt Injection 或越狱分析。** 攻击者可以通过观察模型对不同输入的推理反应，推断过滤规则、绕过路径和可攻击面；工具返回的恶意内容也可能通过推理链被放大。

这些风险不是“模型不够好”的问题，而是“推理过程是一种高信息密度的输出”这一事实带来的。信息越丰富，泄露面越大。

## 8.3 四层分离：Trace、Explanation、Audit Log、Citation

生产系统最重要的设计之一，是把“推理相关的东西”拆成四层，分别管理可见性、保留期限和用途。

| 层级 | 内容 | 可见性 | 保留期限 | 主要用途 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| 内部 Reasoning Trace | 完整推理、分支、工具调用、观察、重试 | 内部服务/授权人员 | 按合规要求，通常较短 | 调试、评估、训练、审计 | 敏感信息、系统提示、凭证 |
| 用户可见 Explanation | 经过筛选和改写的简要解释 | 最终用户 | 随会话/产品策略 | 帮助用户理解、建立信任 | 不忠实、过度简化、误导 |
| 审计日志 | 请求 ID、模型版本、策略、工具调用、安全决策 | 安全/合规团队 | 较长，按法规 | 追责、合规、事件调查 | 访问控制、留存合规 |
| 证据引用 | 文档 ID、片段、URL、时间戳 | 最终用户/审查员 | 随内容 | 事实核对、可追溯 | 引用错误、来源不可靠 |

四层的关系是：

- **Trace 是原材料**，不直接给用户；
- **Explanation 是产品化的解释**，从 trace 中提炼，但经过安全过滤和事实核对；
- **Audit Log 是受控记录**，用于追责和合规，不是调试日志的简单复制；
- **Citation 是证据链**，让用户能核对关键事实，而不是相信模型的推导。

把四层混在一起，是很多生产事故的根源：要么把完整 trace 直接返回给用户，造成泄露；要么为了安全把一切都删掉，导致无法审计；要么审计日志里存了 PII，违反合规。

## 8.4 工程实践建议

1. **对用户输出“简要推理摘要”，而不是完整 CoT。** 摘要应包含关键假设、主要步骤、结论和不确定性，不包含内部提示、工具 schema、权限细节。
2. **保留内部 trace 供调试和评估，但严格访问控制。** Trace 存储要加密、脱敏、按角色授权，设置保留期限。
3. **对高风险场景隐藏完整推理过程。** 医疗、金融、法律、安全运营等场景，默认只给结论、依据和不确定性，完整 trace 仅对审查员开放。
4. **对关键事实提供证据引用。** 引用要能定位到具体文档和片段，不能只给一个笼统的来源名称。
5. **将推理过程与最终答案分离评估。** 答案准确率和过程质量分别监控，避免“答案对但过程错”被掩盖。
6. **对 trace 和 explanation 都做安全过滤。** 敏感信息、危险内容、注入指令、系统提示片段，都要检测和脱敏。
7. **不要把 trace 当作审计真相。** Trace 是模型生成的文本，可能不忠实；审计应以工具日志、外部证据和可复现实验为准。
8. **防范工具输出注入。** 工具返回的内容可能包含恶意指令，进入推理链前要标记为“不可信数据”，并限制其对后续动作的影响。
9. **给用户提供不确定性表达。** 置信度、假设、适用范围、未验证点，要显式说明，避免过度自信。
10. **建立事件响应机制。** 一旦发现 trace 泄露、错误解释或注入攻击，能快速定位请求、模型版本、工具调用和影响范围。

## 8.5 一个生产输出模板

一个兼顾可解释性和安全性的输出，可以设计成下面这样：

```json
{
  "answer": "比原价低 4%",
  "confidence": "high",
  "explanation": "设原价为 100 元，涨价后为 120 元；再降价 20% 是按 120 元的基数计算，最终为 96 元，因此比原价低 4%。",
  "assumptions": ["原价视为 100 元，仅用于计算比例", "不考虑税费、运费等其他因素"],
  "citations": [],
  "limitations": ["如果题目中的降价基数不是涨价后的价格，结论会不同"],
  "trace_id": "tr_20261117_000123"
}
```

这个模板把“答案、置信度、简要解释、假设、引用、局限、trace ID”分开。用户看到的是可理解的解释和边界；内部人员可以通过 trace_id 查到完整轨迹。它不展示完整 CoT，但保留了可审计性。

# 九、思维链评估指标

CoT 的评估不能只看最终答案。一个答案正确但推理错误的系统，会在分布外任务上突然失效；一个推理看起来合理但答案错误的系统，会让用户过度信任。评估要同时覆盖答案、过程、鲁棒性、效率和安全性。

下表给出一套可操作的指标体系。实际使用时不必全部上线，但至少要覆盖“答案正确率、过程质量、单位成功成本、安全泄露”四类。

| 类别 | 指标 | 衡量目标 | 计算方式 | 适用任务 | 注意事项 |
| --- | --- | --- | --- | --- | --- |
| 最终答案 | Accuracy | 答案正确率 | 正确样本数 / 总样本数 | 数学、代码、问答 | 需要答案归一化和验证器；不能只看表面字符串 |
| 最终答案 | Exact Match | 严格匹配率 | 归一化后完全一致的样本数 / 总数 | 短答案抽取、分类 | 同义表达和格式差异会低估真实能力 |
| 最终答案 | Pass@k | k 条采样中至少一条正确的概率 | 1 − C(n−c,k)/C(n,k) 的无偏估计 | 代码、数学、可采样任务 | 要和 Pass@1 一起看；k 越大越乐观 |
| 最终答案 | Factuality | 事实正确性 | 有证据支持的 claim 数 / 总 claim 数 | 知识问答、RAG | 需要 claim 拆分和证据核对 |
| 最终答案 | Task Success Rate | 端到端任务成功率 | 成功任务数 / 总任务数 | Agent、工作流 | 成功定义要包含格式、工具、权限和业务约束 |
| 推理过程 | Step Correctness | 每一步是否正确 | 正确步骤数 / 总步骤数 | 长推理、数学证明 | 步骤切分影响结果；需要人工或 PRM 标注 |
| 推理过程 | Step Consistency | 步骤之间是否一致 | 矛盾步骤对数 / 总步骤对数 | 多步推理、长文分析 | 一致不等于正确；模型可以一致地错 |
| 推理过程 | Logical Coherence | 逻辑是否连贯 | 人工 rubric 评分或规则检查 | 解释、论证、规划 | 主观性强，需要明确评分标准 |
| 推理过程 | No Contradiction | 是否自相矛盾 | 自相矛盾样本数 / 总数 | 长推理、多跳问答 | 隐含矛盾比显式矛盾难检测 |
| 推理过程 | Completeness | 关键步骤是否齐全 | 覆盖的子目标数 / 应覆盖子目标数 | 证明、规划、复杂计算 | 参考路径不唯一，不能只按一条标准答案算 |
| 推理过程 | Minimality | 是否冗余 | 冗余步骤数 / 总步骤数 | 成本敏感场景 | 过度追求极简会牺牲可读性和稳健性 |
| 鲁棒性 | Prompt Sensitivity | 换提示是否稳定 | 不同 prompt 变体下准确率的方差或最大差 | 所有任务 | 复述要合理，不能只换标点 |
| 鲁棒性 | Sampling Variance | 采样波动 | 多次运行的均值、方差、置信区间 | 高温度采样、Self-Consistency | 与 temperature 和 K 绑定，要一起报告 |
| 鲁棒性 | Adversarial Robustness | 对抗扰动下的表现 | 扰动前后准确率下降幅度 | 安全、事实、代码 | 攻击集要多样，不能只测一种模板 |
| 鲁棒性 | Cross-domain Generalization | 跨域泛化 | 留出领域上的准确率 | 训练数据单一的模型 | 域的定义要清晰，避免测试集污染 |
| 效率 | Token Cost | token 消耗 | 输入 + 输出 token 数 / 请求 | 所有任务 | 推理 token 通常按输出 token 计费；要看单位成功成本 |
| 效率 | Latency | 延迟 | p50、p95、TTFT、总耗时 | 在线服务 | 采样和工具调用会放大尾延迟 |
| 效率 | Number of Samples | 采样数量 | 平均 K、最大 K、超时率 | Self-Consistency、ToT | 收益随 K 饱和，要找到拐点 |
| 效率 | Tool Call Cost | 工具调用成本 | 调用次数、外部费用、错误率、重试率 | Agent、工具增强 | 重试和超时也要计入成本 |
| 安全性 | Sensitive Reasoning Leakage | 敏感推理泄露率 | 含敏感信息的 trace/解释数 / 总数 | 生产系统 | 需要定义敏感类别，使用 canary 字符串测试 |
| 安全性 | Unsafe Rationale Rate | 不安全推理比例 | 违规 rationale 数 / 总数 | 安全敏感场景 | 最终答案安全不代表过程安全 |
| 安全性 | Hallucinated Explanation Rate | 解释幻觉率 | 无证据支持的 claim 数 / 总 claim 数 | RAG、解释生成 | 需要 claim 级标注和证据核对 |
| 安全性 | Overconfidence Rate | 过度自信比例 | 高置信错误数 / 高置信总数 | 所有任务 | 置信度要校准，可配合 ECE、Brier score |

使用这套指标时，有几个方法论问题必须处理：

**第一，答案评估和过程评估要分开。** 答案准确率高，可能是模型会猜、题目简单或评测集污染；过程质量高，可能是模型会写漂亮解释。两者要独立报告，不能用一个总分掩盖差异。

**第二，过程评估要抽样，不要全量人工。** 按难度、任务类型、模型版本分层抽样，通常几百条 trace 就能看出趋势。要报告标注者一致性（如 Cohen's kappa），否则“步骤正确率”不可比。

**第三，LLM Judge 不能当唯一评估器。** Judge 有位置偏好、长度偏好、自我偏好，可能对模型生成的解释更宽容。可以用 Judge 做粗筛，但关键结论要有人工抽检或规则验证兜底。最好避免用同一个模型既生成又评判。

**第四，效率要看“单位成功成本”。** 单次调用便宜，但如果成功率低、重试多、人工复核多，真实成本可能更高。建议计算“每解决一个正确任务的 token 成本、延迟和工具费用”。

**第五，安全评估要有攻击视角。** 除了常规测试集，还要做 canary 泄露测试、注入测试、越狱测试和敏感信息扫描。安全指标不是一次性的，要随模型、提示、工具和策略变化持续回归。

**第六，报告置信区间。** 准确率是估计值，样本量小的时候波动很大。用 bootstrap 或配对比较给出置信区间，避免把随机波动当成模型改进。

# 十、思维链与 RAG、Agent、工具调用的结合

单独使用 CoT，模型仍然只依赖参数里的知识。把 CoT 与检索、工具、验证器结合，才能让推理有外部依据、可执行、可检查。

## 10.1 CoT + RAG

CoT + RAG 的基本流程是：先检索证据，再基于证据分步推理，最后给出带引用的答案。

关键设计：

- **证据优先**：先确认上下文是否足够，再开始推理；证据不足时，应该明确说“不足以回答”，而不是用 CoT 编造。
- **逐步引用**：每个关键结论尽量对应到具体文档片段，而不是最后统一给一个来源列表。
- **冲突处理**：检索结果可能相互矛盾，推理过程要显式比较时间、来源可信度和适用范围，不能随意选一个。
- **忠实性检查**：推理步骤中的 claim 要能由上下文支持；不能把模型的世界知识伪装成检索证据。
- **引用准确性**：引用要能定位到原文，不能编造文档 ID、页码或链接。

评估时，除了答案准确率，还要看 Faithfulness（推理是否忠于上下文）和 Citation Accuracy（引用是否指向正确证据）。这两个指标比“答案看起来对”更能反映 RAG 系统的真实质量。

常见失败模式是“检索到了正确证据，但推理时没用上”或“推理用上了证据，但引用的是另一段”。工程上可以把“证据选择”和“基于证据的推理”拆成两个可评估环节。

## 10.2 CoT + Agent

Agent 通过思维链进行任务规划：理解目标、拆子目标、排依赖、选择工具、观察结果、反思和重规划。

ReAct 的 Thought / Action / Observation 循环是典型结构：

```text
Thought: 需要先确认用户说的是哪个订单。
Action: search_order(user_id="u_123", keyword="最近")
Observation: 返回 3 条订单，其中 2 条待发货。
Thought: 用户问的是物流，应该查最近一条待发货订单的物流。
Action: get_logistics(order_id="o_456")
Observation: ...
```

工程上要控制四件事：

1. **循环控制**：最大步数、最大工具调用次数、最大 token 预算、超时时间；没有上限的 Agent 很容易陷入“思考—调用—再思考”的循环。
2. **状态管理**：把任务状态、已完成子目标、未解决问题、工具结果摘要存下来；不要把所有历史 trace 都塞回上下文。
3. **权限控制**：不同工具、不同用户、不同任务有不同的权限；高风险动作（转账、删除、发邮件）需要审批或二次确认。
4. **重规划**：工具失败、观察与预期冲突、子目标不可达时，要能改路线，而不是硬着头皮执行原计划。

长程 Agent 的推理还会遇到“上下文漂移”：早期的重要约束在长对话中被稀释，模型开始围绕最近一次观察打转。解决办法包括定期摘要、显式维护任务状态、在关键节点重新注入目标和约束。

## 10.3 CoT + Tool Calling

CoT + 工具调用的核心是：推理过程中判断是否调用工具，工具返回结果作为新观察，继续推理。

工程要点：

- **调用决策**：不是每一步都要调工具；模型要能判断“内部知识够不够”“是否需要实时数据”“计算是否复杂到需要程序”。
- **参数校验**：工具参数要经过 JSON Schema、类型、范围、权限校验；不能直接执行模型生成的任意参数。
- **幂等与重试**：查询类工具可以重试，写入类工具要幂等；重试要有上限和退避。
- **错误处理**：工具超时、限流、返回空、返回格式错误，都要作为观察反馈给模型，并触发降级策略。
- **注入防护**：工具返回内容是不可信数据，可能包含“忽略之前的指令”之类的注入文本；进入推理链前要标记、转义或隔离。
- **沙箱**：代码执行、文件操作、网络访问要在隔离环境中进行，限制资源、网络和文件系统权限。
- **审计**：记录调用者、工具名、参数、结果摘要、耗时、错误码；敏感参数要脱敏。

工具调用把 CoT 从“文本推理”变成“有副作用的行动”。一旦有副作用，安全边界就从“输出内容”扩展到“系统权限”。

## 10.4 CoT + Verifier

Verifier 用来检查最终答案或中间步骤。常见类型：

| Verifier 类型 | 验证对象 | 典型实现 | 优点 | 局限 |
| --- | --- | --- | --- | --- |
| 规则验证 | 格式、范围、枚举、schema | 正则、JSON Schema、约束检查 | 快、确定、便宜 | 只能验证可形式化的约束 |
| 执行验证 | 代码、SQL、程序输出 | 单元测试、沙箱执行、数据库比对 | 接近真实行为 | 需要隔离环境，测试覆盖有限 |
| 符号验证 | 数学表达式、逻辑公式 | SymPy、SMT solver、证明器 | 精确、可解释 | 形式化成本高，覆盖有限 |
| 模型验证 | 语义一致性、事实性、步骤质量 | 奖励模型、PRM、LLM Judge | 灵活、可处理开放任务 | 有偏见、可能被 reward hacking |

CoT + Verifier 的常见用法：

- **Best-of-N**：采样多条 CoT，用 verifier 选最佳答案；
- **Verifier-guided search**：在 ToT 或 MCTS 中，用 verifier 给中间状态打分；
- **答案复核**：先让模型给答案，再让 verifier 检查，不通过则重试或降级；
- **过程检查**：用 PRM 检查关键步骤，提前发现错误。

Verifier 不是 Ground Truth。规则验证可能覆盖不全，执行验证可能测试不足，符号验证可能形式化错，模型验证可能有偏见。工程上要把 verifier 当作“过滤器”和“信号源”，而不是“真理机器”。对高风险场景，最好组合多种 verifier，并保留人工复核通道。

## 10.5 组合方式总结

| 组合 | 解决的问题 | 新增风险 | 关键指标 |
| --- | --- | --- | --- |
| CoT + RAG | 知识不足、事实幻觉 | 检索错误、引用错误、证据冲突 | Faithfulness、Citation Accuracy |
| CoT + Agent | 多步任务、工具协同 | 循环失控、权限越界、状态漂移 | Task Success Rate、步数、权限违规率 |
| CoT + Tool Calling | 实时数据、精确计算、外部动作 | 参数错误、注入、副作用 | 工具成功率、重试率、注入拦截率 |
| CoT + Verifier | 答案错误、过程错误 | 验证器假阳性/假阴性、成本 | 验证通过率、误判率、单位成功成本 |

# 十一、工程实现架构

一个支持 CoT 训练与推理的系统，应该把离线训练、在线推理、验证、评估、安全和输出控制分开。核心原则是：**训练数据和推理 trace 都是受控资产，不是普通日志；验证器和安全过滤器是独立服务，不是模型 prompt 里的几句话。**

## 11.1 文字版架构图

```text
【离线训练链路】

数据源（人工标注 / 教师模型 / 历史 trace / 公开数据集 / 工具日志）
  → CoT Data Builder（采集、清洗、去重、验证、标注、切分）
      ↕ Verifier Service（答案 / 代码 / 数学 / schema）
  → 数据集仓库（版本、任务、难度、质量分）
  → Training Pipeline（SFT / 蒸馏 / 拒绝采样 / RLVR / 过程奖励）
  → 模型仓库（checkpoint + 数据版本 + 超参）
  → Evaluation Harness（答案 / 过程 / 鲁棒性 / 效率 / 安全）
  → 发布门禁 → 灰度发布

【在线推理链路】

用户请求
  → API 网关（鉴权、限流、内容初筛）
  → Inference Orchestrator（任务分类、难度路由、预算分配）
      ├→ 模型服务（生成候选 trace / 答案）
      ├→ RAG / 工具 / 沙箱（检索、计算、执行）
      ├→ Verifier Service（答案与关键步骤校验）
      ├→ Safety Filter（敏感信息、危险内容、注入检测）
      └→ Trace Logger（异步记录完整轨迹与决策）
  → Output Controller（完整推理 / 简要解释 / 仅答案）
  → 用户

【反馈闭环】

线上 trace + 用户反馈 + 人工复核
  → 脱敏、去重、验证、难度标注
  → 数据仓库 / 评估集 / 失败样本库
  → 下一轮训练与发布
```

## 11.2 模块职责

| 模块 | 核心职责 | 输入 | 输出 | 关键失败模式 |
| --- | --- | --- | --- | --- |
| CoT Data Builder | 采集、清洗、去重、验证、标注、切分推理数据 | 原始问题、教师输出、用户 trace、工具日志 | 结构化数据集、质量报告 | 数据污染、错误 rationale、PII 泄露 |
| Training Pipeline | 执行 SFT、蒸馏、拒绝采样、RLVR、过程奖励训练 | 数据集、基础模型、训练配置 | checkpoint、训练指标 | 奖励黑客、过拟合、数据泄漏 |
| Inference Orchestrator | 选择推理策略、分配预算、管理重试和工具调用 | 用户请求、模型能力、预算 | 候选 trace、最终答案候选 | 循环失控、成本超支、策略错配 |
| Verifier Service | 验证答案、代码、数学表达式、结构化输出 | 问题、答案、trace | 通过/失败、分数、错误类型 | 假阳性、假阴性、沙箱逃逸 |
| Trace Logger | 记录推理轨迹、采样结果、工具调用、安全决策 | 请求上下文、模型输出、工具事件 | 结构化 trace、审计事件 | 敏感信息留存、日志丢失 |
| Evaluation Harness | 批量评估答案和过程，做回归和对比 | 评估集、模型输出、指标配置 | 指标报告、置信区间、失败样本 | 评测集污染、Judge 偏见、样本不足 |
| Safety Filter | 检测敏感推理、危险内容、注入风险 | 输入、输出、trace、工具结果 | 允许/拦截/脱敏/升级 | 误杀、漏检、策略绕过 |
| Output Controller | 决定展示完整推理、摘要还是仅答案 | 答案、解释、置信度、策略 | 用户响应、审计记录 | 泄露、过度自信、格式错误 |

## 11.3 数据流

**离线训练链路：**

1. 从人工标注、教师模型、历史 trace、公开数据集采集原始数据；
2. CoT Data Builder 做规范化、去重、PII 清洗、答案验证、步骤验证、难度标注；
3. Verifier Service 对可验证任务给出通过/失败和错误类型；
4. 数据集仓库按版本、任务、难度、质量分存储；
5. Training Pipeline 按阶段执行 SFT、蒸馏、拒绝采样、RLVR 或过程奖励训练；
6. 训练出的 checkpoint 进入模型仓库，附带训练数据版本、超参和评估结果；
7. Evaluation Harness 在干净评估集上跑答案、过程、鲁棒性、效率、安全指标；
8. 指标达标后进入发布门禁，灰度发布；不达标则回到数据或训练环节。

**在线推理链路：**

1. 请求进入 API 网关，做鉴权、限流、内容初筛；
2. Inference Orchestrator 根据任务类型、难度、用户等级、预算选择策略；
3. 模型服务生成候选 trace 或答案；
4. 需要时调用 RAG、工具或沙箱，观察结果回注到推理链；
5. Verifier Service 检查答案或关键步骤；
6. Safety Filter 检查输入、输出和 trace，决定拦截、脱敏或升级；
7. Trace Logger 异步记录完整轨迹、采样结果、工具调用和安全决策；
8. Output Controller 根据策略选择展示完整推理、摘要或仅答案；
9. 用户收到响应；反馈信号进入评估和训练闭环。

**反馈闭环：**

- 用户反馈、人工复核、线上失败案例，经过脱敏和验证后进入数据仓库；
- 高频失败模式进入评估集，防止回归；
- 线上 trace 可以用于蒸馏和 RFT，但必须过滤、脱敏、去重，不能直接把模型输出回流训练；
- 模型版本、提示版本、工具版本、验证器版本要一起记录，否则问题无法复现。

## 11.4 工程注意事项

- **Trace schema 要版本化。** 字段会随产品演进；没有版本号，旧 trace 无法解析，评估结果不可比。
- **日志异步化。** Trace 写入不能阻塞主推理链路；但要保证关键安全事件同步落盘。
- **采样与脱敏。** 不是所有请求都要存完整 trace；按比例采样，敏感字段哈希或删除。
- **访问控制。** Trace 查看权限按角色划分；审计日志和调试日志分开；保留期限按合规要求设置。
- **预算控制。** 每个请求有 token、工具调用、时间预算；超预算时降级，而不是无限重试。
- **灰度与回滚。** 新模型、新提示、新验证器先小流量灰度；指标异常能快速回滚。
- **可观测性。** 监控答案准确率、验证通过率、平均采样数、p95 延迟、单位成功成本、循环步数、安全拦截率。
- **沙箱隔离。** 代码执行、文件操作、网络访问要在独立环境；限制 CPU、内存、时间、网络和文件系统。
- **幂等与重试。** 写入类工具要幂等；重试要有上限、退避和去重键。
- **成本归因。** 按任务、用户、模型、策略拆分成本，找到“最贵的失败”。

# 十二、伪代码示例：Self-Consistency 推理

下面是一段 Python 风格伪代码，展示如何用 Self-Consistency 提升推理准确率。它体现了采样、答案抽取、归一化、验证、投票、摘要和 trace 记录，但省略了 LLM 客户端、沙箱、监控和鉴权的具体实现。

```python
# Python 风格伪代码：Self-Consistency + Verifier + 用户可见摘要
# 省略了 LLM 客户端、沙箱、监控和鉴权的具体实现。

from __future__ import annotations

import re
from collections import defaultdict
from dataclasses import dataclass, field
from typing import Optional


@dataclass
class CoTSample:
    trace: str
    raw_answer: Optional[str]
    normalized: Optional[str] = None
    verified: Optional[bool] = None
    tokens: int = 0


@dataclass
class SCResult:
    answer: Optional[str]
    confidence: float
    votes: dict[str, int]
    explanation: str
    trace_id: str
    samples: list[CoTSample] = field(default_factory=list)


def generate_cot_samples(question: str, k: int = 8,
                         temperature: float = 0.7,
                         max_tokens: int = 2048) -> list[CoTSample]:
    """对同一个问题独立采样 k 条思维链。"""
    samples: list[CoTSample] = []
    for _ in range(k):
        resp = llm.generate(
            prompt=build_cot_prompt(question),
            temperature=temperature,
            max_tokens=max_tokens,
        )
        samples.append(CoTSample(
            trace=resp.text,
            raw_answer=extract_final_answer(resp.text),
            tokens=resp.usage.total_tokens,
        ))
    return samples


def extract_final_answer(trace: str) -> Optional[str]:
    """优先读取结构化标记，避免从自然语言里猜答案。"""
    match = re.search(r"<answer>(.*?)</answer>", trace, re.S | re.I)
    if match:
        return match.group(1).strip()

    match = re.search(r"(?:最终答案|答案)\s*[:：]\s*(.+)", trace)
    if match:
        return match.group(1).strip().splitlines()[0]
    return None


def normalize_answer(answer: Optional[str],
                     task_type: str = "math") -> Optional[str]:
    """把语义等价的答案映射到同一个 key；失败时回退到字符串归一。"""
    if answer is None:
        return None

    text = answer.strip().lower()
    text = text.replace("，", ",").replace("。", "").replace(" ", "")

    if task_type == "math":
        text = text.replace("$", "").replace("\\%", "%").replace("％", "%")
        try:
            expr = sympy.sympify(text)
            return "math:" + str(sympy.simplify(expr))
        except Exception:
            return "str:" + text

    if task_type == "choice":
        match = re.search(r"\b([a-d])\b", text)
        return ("choice:" + match.group(1)) if match else ("str:" + text)

    return "str:" + text


def verify_answer(question: str, answer: Optional[str],
                  task_type: str = "math") -> Optional[bool]:
    """返回 True/False；无法验证时返回 None，不要当成 False。"""
    if answer is None:
        return False
    if task_type == "math":
        return math_verifier.check(question, answer)
    if task_type == "code":
        return code_verifier.run_tests(question, answer, timeout_s=5)
    return None


def majority_vote(
    samples: list[CoTSample],
    question: str,
    task_type: str = "math",
) -> tuple[Optional[str], float, dict[str, int], Optional[str]]:
    """先归一化，再按答案分组；验证通过数作为第一排序键，票数作为第二排序键。"""
    buckets: dict[str, list[CoTSample]] = defaultdict(list)

    for sample in samples:
        sample.normalized = normalize_answer(sample.raw_answer, task_type)
        sample.verified = verify_answer(question, sample.raw_answer, task_type)
        if sample.normalized is not None:
            buckets[sample.normalized].append(sample)

    if not buckets:
        return None, 0.0, {}, None

    ranked = []
    for key, group in buckets.items():
        votes = len(group)
        verified = sum(1 for s in group if s.verified is True)
        ranked.append((verified, votes, key, group))

    # 有验证通过的分组优先；都不可验证时退化为纯投票。
    ranked.sort(key=lambda item: (item[0] > 0, item[1], item[0]), reverse=True)
    _, votes, key, group = ranked[0]

    valid = sum(len(g) for g in buckets.values())
    confidence = votes / valid if valid else 0.0
    vote_counts = {k: len(g) for k, g in buckets.items()}
    return group[0].raw_answer, confidence, vote_counts, key


def generate_summary_explanation(
    question: str,
    winning: list[CoTSample],
    max_sentences: int = 3,
) -> str:
    """只基于胜出轨迹生成简要解释，不把其他分支的假设带进来。"""
    trace = winning[0].trace
    summary = llm.generate(
        prompt=SUMMARY_PROMPT.format(
            question=question,
            trace=trace,
            max_sentences=max_sentences,
        ),
        temperature=0.0,
        max_tokens=300,
    ).text
    return sanitize_explanation(summary)  # 去 PII、去系统提示、去未验证断言


def answer_with_self_consistency(
    question: str,
    task_type: str = "math",
    k: int = 8,
    min_votes: int = 3,
) -> SCResult:
    trace_id = new_trace_id()
    samples = generate_cot_samples(question, k=k)
    answer, confidence, votes, winning_key = majority_vote(
        samples, question, task_type)

    should_abstain = (
        answer is None
        or winning_key is None
        or max(votes.values(), default=0) < min_votes
    )

    if should_abstain:
        trace_logger.write(
            trace_id=trace_id,
            question=question,
            samples=samples,
            answer=None,
            confidence=confidence,
            votes=votes,
            decision="abstain",
        )
        return SCResult(
            answer=None,
            confidence=confidence,
            votes=votes,
            explanation="证据不足，无法给出可靠答案。",
            trace_id=trace_id,
            samples=samples,
        )

    winning = [s for s in samples if s.normalized == winning_key]
    explanation = generate_summary_explanation(question, winning)

    trace_logger.write(
        trace_id=trace_id,
        question=question,
        samples=samples,
        answer=answer,
        confidence=confidence,
        votes=votes,
        decision="answer",
    )
    return SCResult(
        answer=answer,
        confidence=confidence,
        votes=votes,
        explanation=explanation,
        trace_id=trace_id,
        samples=samples,
    )
```

关键逻辑解释：

1. **采样要有多样性。** temperature 为 0 时，K 条轨迹几乎相同，投票没有意义。通常用 0.5 到 1.0 之间的温度，具体要看模型和任务；温度太高会引入无关内容。
2. **答案抽取必须结构化。** 生产系统应该让模型用 `<answer>` 之类的标记包裹最终答案。从自然语言里正则抽取是主要故障源，尤其是多行答案、带单位答案和中文标点。
3. **归一化决定投票是否有效。** `0.5`、`1/2`、`50%` 是否等价，取决于题目语义；选项答案要统一大小写；带单位的答案要做单位换算。归一化规则要有测试集，否则会把等价答案拆成不同组。
4. **验证器不是 Ground Truth。** `verify_answer` 在无法验证时返回 `None`，而不是 `False`；这样投票逻辑可以区分“验证失败”和“不可验证”。如果一律当 False，会把本来正确的答案排除掉。
5. **投票聚合是启发式，不是概率校准。** 票数占比可以当作置信度的粗略代理，但不是“答案正确的概率”。要校准的话，需要用历史数据做可靠性曲线或温度缩放。
6. **验证通过数只作为排序信号。** 代码里先看“是否有验证通过”，再按票数排序。验证器可靠时可以加大验证权重；验证器不可靠时，纯投票可能更稳。
7. **平票和低票数要弃权或升级。** `min_votes` 是防止“两条样本里一条正确就输出”的保险。生产系统还可以在低置信时触发更多采样、调用工具、转人工或直接说“不确定”。
8. **只把胜出轨迹交给摘要器。** 如果把所有分支都塞给摘要器，错误分支的假设可能混进解释。先用投票选出胜出组，再基于胜出组生成摘要。
9. **完整 trace 进内部日志，用户只看摘要。** `trace_logger.write` 记录所有样本、票数、验证结果和决策；`SCResult.explanation` 只包含经过过滤的简要解释。两者用途不同，不能混用。
10. **成本是 K 倍。** K=8 意味着 8 次生成、最多 8 次验证。工程上要设置预算、超时和早停：如果前几条已经高度一致，可以提前结束；如果验证器很快，可以适当增加 K。
11. **安全过滤要在摘要之后再做一次。** 摘要器可能把 trace 中的敏感信息带出来；`sanitize_explanation` 要做 PII、系统提示、未验证断言和危险内容的检查。

这段伪代码的重点不是“投票”本身，而是围绕投票的一整套工程约束：结构化输出、归一化、验证、弃权、摘要、日志和安全。缺少任何一环，Self-Consistency 都可能从“提升准确率”变成“更贵地犯错”。

# 十三、常见误区

| 误区 | 为什么危险 | 正确做法 |
| --- | --- | --- |
| 认为 CoT 越长越好 | 长推理增加 token 成本、延迟和误差累积；模型可能陷入重复、自我怀疑或过度思考，简单题反而更容易错 | 按难度分配推理预算；监控准确率随 token 数的拐点；能直接答对的题不要强行展开 |
| 认为显式推理一定真实可信 | CoT 可能是事后解释，模型可能先猜答案再编过程；用户会过度信任漂亮推导 | 用干预实验、验证器和人工抽检评估忠实性；不要把 trace 当作审计真相 |
| 认为只要加“请一步一步思考”就能解决复杂问题 | 这句话只是分布触发器，模型能力、训练数据、任务类型不匹配时无效，甚至更差 | 先在自己的评估集上验证；必要时用 few-shot、SFT、RLVR、工具或验证器 |
| 只评估最终答案，不评估推理过程 | 答案可能蒙对，过程可能错误；模型在分布外会突然失效，而指标看不出来 | 建立过程评估集；检查步骤正确性、一致性和完整性；答案与过程分开报告 |
| 将错误 CoT 数据直接用于训练 | 模型会学会错误推理模式，错误会在后续采样中放大；数据污染很难事后清除 | 答案验证 + 步骤验证 + 人工抽检；保留负样本用于验证器训练；建立数据版本和回滚机制 |
| 在生产环境无条件展示完整推理 | 可能泄露系统提示、工具 schema、安全策略、PII；增加用户对错误答案的信任；给攻击者提供分析材料 | 默认输出简要解释；完整 trace 仅内部授权可见；对高风险场景隐藏推理；做脱敏和安全过滤 |
| 忽略 Token 成本和延迟 | Self-Consistency、ToT、长 CoT 会成倍增加成本；尾延迟影响用户体验；单位成功成本可能失控 | 设置 token、采样数、工具调用和时间预算；监控 p95 延迟和单位成功成本；做难度路由和缓存 |
| 对简单任务过度使用 CoT | 简单分类、抽取、改写不需要多步推理；CoT 增加延迟，还可能引入无关内容 | 简单任务直接回答；用置信度或规则判断是否升级；不要为了“统一架构”牺牲效率 |
| 忽略工具验证和外部证据 | 模型可能在证据之外编造推理；RAG 检索到了证据，但推理没用上或引用错 | CoT + RAG/工具 + Verifier；检查 Faithfulness 和 Citation Accuracy；证据不足时明确拒绝 |
| 把 LLM Judge 当作唯一评估器 | Judge 有位置偏好、长度偏好、自我偏好，可能对某种风格更宽容；评估结果不可复现 | 多方法交叉验证；人工抽检校准；规则和验证器兜底；报告 Judge 版本和提示 |

这些误区有一个共同点：把 CoT 当成“免费的智能提升”。实际上，CoT 是用 token、延迟和工程复杂度换准确率的一种交易。交易是否划算，取决于任务、模型、验证器和业务约束。

# 十四、未来趋势

## 14.1 从显式 CoT 到隐式推理

显式 CoT 的 token 成本高，且容易泄露不可靠推理。研究界在探索两类替代方案：

- **生成但不展示**：模型内部生成 trace，产品层只给摘要；
- **隐空间推理**：在连续向量或内部状态中完成多步计算，不产生可读 token，例如 Coconut、 “Let's Think Dot by Dot” 一类工作。

Quiet-STaR 一类工作则让模型在生成答案前学习产生内部思考，并用这些思考帮助后续 token 预测；它更接近“训练模型自己思考”，而不是依赖外部提示。隐式推理的潜在优势是更紧凑、更接近模型的内部计算、可能泛化更好。挑战也很明显：不可解释、难以验证、安全审计困难。短期内，生产系统更可能采用“内部 trace + 用户摘要”的折中，而不是完全黑箱的隐空间推理。

## 14.2 从结果监督到过程监督

结果监督只告诉模型“最后对不对”，过程监督告诉模型“哪一步错了”。随着 PRM、自动步骤标注和搜索技术的发展，过程监督会越来越多地用于：

- 长推理链的早期剪枝；
- best-of-N 重排；
- 树搜索和 MCTS 的价值估计；
- 训练数据的步骤级过滤。

瓶颈不在模型，而在标注和评估：什么算一步、一步的错误如何定义、同一答案是否只有一条正确路径。未来可能会出现更自动化的步骤级验证，但“步骤定义”的模糊性不会完全消失。

## 14.3 从单路径推理到搜索式推理

单条 CoT 是一条路径；ToT、MCTS、best-of-N、verifier-guided search 是在推理空间里做搜索。随着推理时计算变得更便宜、验证器更可靠，搜索式推理会从研究原型进入更多生产场景。

关键问题是**价值函数**：搜索需要判断“这个中间状态有没有希望”，而这个判断本身可能错。未来的方向包括更好的 PRM、学习型价值模型、以及把符号验证器接进搜索。

## 14.4 从文本推理到工具增强推理

纯文本推理无法保证计算精确、无法获取实时信息、无法执行动作。工具增强推理把代码执行、搜索、数据库、形式化求解器接进推理链，让模型“边想边查、边算边验”。

这会带来新的工程问题：工具权限、参数校验、沙箱隔离、注入防护、错误恢复、成本归因。未来的推理系统会更像“模型 + 工具 + 验证器 + 权限系统”的组合，而不是单一模型。

## 14.5 从人工标注 CoT 到自动生成和验证 CoT

人工标注高质量 CoT 很贵，难以覆盖长尾任务。自动生成 + 验证的路线会继续发展：

- 教师模型生成候选；
- 验证器筛选最终答案；
- PRM 或规则筛选步骤；
- 拒绝采样、STaR、ReST 迭代自举；
- 多模型交叉验证和一致性筛选。

风险是“自举偏差”：模型在自己的输出上训练，错误会累积。未来的关键在于**验证器的覆盖面和可靠性**，以及如何混入人工数据和外部证据。

## 14.6 与 RLVR 结合提升可验证任务能力

RLVR 用可验证奖励训练模型，已经在数学、代码等任务上显示出效果。未来的发展方向包括：

- 更好的奖励设计，减少 reward hacking；
- 更高效的 RL 算法，降低采样成本；
- 过程奖励与结果奖励结合；
- 跨任务、跨语言的验证器；
- 对小模型做推理蒸馏，降低部署成本。

需要保持清醒：有研究表明，RLVR 主要提升的是采样效率，即把基础模型已经具备的正确路径选出来，而不是创造全新的推理能力（Yue et al., 2025）。RLVR 很重要，但不是“无中生有”的万能药。

## 14.7 更高效的推理时计算 scaling

推理时计算 scaling 的核心问题是：给定固定预算，应该把 token 花在哪里？未来的方向包括：

- 难度路由：简单题直接答，难题才展开；
- 自适应采样：根据置信度决定 K；
- 早停：一致性足够时提前结束；
- 缓存：相似问题复用推理结果；
- 分层验证：先便宜验证，失败再上昂贵验证；
- 推理预算 API：让调用方显式控制成本。

这些工程手段比“无脑增加 CoT 长度”更能提升单位成本收益。

## 14.8 面向 Agent 的长程推理

Agent 任务不是一次问答，而是多轮“思考—行动—观察”。长程推理的难点包括：

- 上下文漂移：早期约束在长对话中被稀释；
- 状态管理：已完成什么、还剩什么、哪些假设被推翻；
- 错误恢复：工具失败、观察冲突、子目标不可达；
- 权限与安全：动作有副作用，不能随便试错；
- 成本控制：长任务容易超预算。

未来的 Agent 推理系统会更强调外部状态、记忆、摘要、重规划和权限边界，而不是把所有东西都塞进一条越来越长的 CoT。

## 14.9 可审计但不泄露敏感推理的解释机制

生产系统需要“可解释”，但不能“全暴露”。未来的方向包括：

- 分层解释：用户看摘要，审查员看 trace，监管看审计日志；
- 证据引用：关键事实有可核对的来源；
- 忠实性评估：解释是否真的反映决策依据；
- 脱敏与访问控制：敏感信息按角色过滤；
- 可复现：记录模型、提示、工具、验证器版本。

“可审计”不等于“公开完整 CoT”。审计需要的是可追溯的证据链和决策记录，而不是模型生成的每一句推理。

## 14.10 推理过程的安全治理

CoT 带来了新的安全面：推理可能泄露敏感信息，可能被注入攻击利用，可能生成危险的操作步骤。未来的治理方向包括：

- 推理过程的安全分类器和红队测试；
- trace 的留存、访问控制和删除策略；
- 对高风险领域限制推理展示；
- 对工具调用做权限和参数审计；
- 建立推理安全标准和评估基准；
- 明确责任边界：模型、系统集成方、业务方各自承担什么。

这部分目前仍不成熟，监管和行业标准都在演进。工程团队应该把“推理安全”当作持续治理，而不是一次性合规检查。

# 十五、总结：如何理性看待思维链

1. **思维链是提升复杂推理能力的重要方法，但不是万能解法。** 它在数学、逻辑、代码、多跳问答等任务上收益明显，对简单任务可能只增加成本。是否使用，要看任务、模型和验证条件。
2. **CoT 可以作为 Prompt 技术、训练数据格式和推理时计算策略。** 三者作用点不同：Prompt 触发行为，数据改变能力，推理策略分配计算。讨论效果时要先分清是哪一种。
3. **高质量推理数据和可靠验证器是训练有效 CoT 的关键。** 错误 rationale 会污染模型；没有验证器，拒绝采样和 RLVR 都无法可靠运行。数据治理比算法名字更重要。
4. **生产系统应区分内部推理轨迹和用户可见解释。** 内部 trace 用于调试、评估、审计；用户看到的是经过过滤、核对和摘要的解释。两者不是同一份文本。
5. **对复杂任务可以结合 Self-Consistency、工具调用、RAG 和 Verifier。** CoT 是基础，采样、搜索、工具和验证是扩展。组合方式要按任务设计，不要堆叠所有技术。
6. **企业落地需要同时关注准确率、成本、延迟、安全和可审计性。** 一个准确但昂贵、不可审计、会泄露敏感信息的系统，不能算成功。单位成功成本、p95 延迟、安全泄露率，应该和准确率一起进入发布门禁。

## 给工程团队的落地建议

1. **不要对所有任务默认启用 CoT。** 先做任务分层：简单任务直接回答，复杂任务才启用推理策略。
2. **对数学、代码、复杂规划任务优先使用 CoT。** 这些任务有多步结构、可验证答案，CoT 的收益最稳定。
3. **简单任务直接回答，复杂任务启用推理策略。** 用难度路由或置信度触发升级，避免“一刀切”。
4. **对生产用户默认输出简要解释，而不是完整推理链。** 完整 trace 留在内部，按权限开放给调试和审计人员。
5. **保留内部 Trace 供评估和调试。** Trace 要结构化、版本化、脱敏、访问控制，不能当普通日志随便存。
6. **使用 Verifier 检查最终答案。** 数学用符号验证，代码用测试，结构化输出用 schema；验证器不可靠时，不要把它当唯一真理。
7. **对可验证任务使用 Self-Consistency 提升稳定性。** 控制 K、温度和预算；监控收益拐点，不要盲目增加采样数。
8. **严格过滤 CoT 训练数据。** 答案正确不等于过程正确；步骤验证、人工抽检、污染检测都要做。
9. **防止错误推理进入训练集。** 保留负样本用于验证器和 PRM，但不要把错误 rationale 直接喂给 SFT。
10. **监控 Token 成本和延迟。** 计算单位成功成本、p95 延迟、采样数、工具费用；设置预算和超时。
11. **对工具调用增加权限和参数校验。** 沙箱、schema、白名单、幂等、重试上限、审计，一个都不能少。
12. **建立推理过程评估集。** 覆盖步骤正确性、一致性、完整性、忠实性；按难度和任务分层抽样。
13. **将 CoT 与 RAG 结合时必须检查证据忠实性。** 每个关键 claim 尽量有引用；证据不足时明确拒绝，不要用推理补事实。
14. **不要用同一个 LLM Judge 作为唯一评估器。** 多方法交叉验证，人工抽检校准，规则和验证器兜底。
15. **对推理泄露和注入做红队测试。** 用 canary 字符串、恶意工具返回、越狱提示测试 trace 和 explanation 的泄露面；建立事件响应和回滚机制。

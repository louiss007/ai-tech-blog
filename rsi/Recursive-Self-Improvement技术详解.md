# Recursive Self-Improvement 技术详解：AI 如何通过递归反馈实现自我改进

> 面向有一定机器学习、大语言模型（LLM）、强化学习或 AI Agent 基础的技术读者。
>
> **阅读说明**
>
> - “Recursive Self-Improvement”（RSI）在学术和产业界并没有完全统一的口径。本文把它限定在“AI 系统利用自身执行产生的反馈，改进自身或其运行环境，并让改进能力本身也进入改进回路”这一范围内。
> - 文中讨论的重点是当前 LLM 系统工程可落地的部分，不把 RSI 等同于“模型无上限自我进化”。涉及强 RSI、递归失控等内容会明确标注为研究前沿或风险假设。
> - 文中的准确率、延迟、成本、样本量均为量级示意，用于说明工程权衡，不是任何模型或产品的实测基准。
> - 产品、论文和框架仅作为技术路径示例，不构成选型推荐；其能力、价格和版本会变化。
> - 安全与治理部分给出的是工程控制思路，不承诺“绝对安全”。

# 一、引言：为什么 Recursive Self-Improvement 重新受到关注

## 1.1 大模型已经具备“局部自我反馈”能力

过去两年，LLM 的应用形态从“单轮问答”转向“多步执行”。在这个转变中，模型开始表现出一些容易被误读为“自我改进”的能力：

- **自我检查**：生成答案后，再让模型检查事实、格式和约束是否满足。
- **反思推理过程**：在推理链结束后，回顾哪一步可能出错，并尝试修正。
- **自动修正代码**：根据解释器、编译器或单元测试的报错，修改代码并重跑。
- **根据执行结果调整行动**：Agent 调用工具后读取 observation，决定下一步是重试、换工具还是终止。

这些能力是真实存在的，但需要区分两种完全不同的机制：

1. **有外部信号的修正**：单元测试失败、API 返回错误、检索结果为空、用户明确指出错误。这类信号相对客观，模型据此修正，成功率较高。
2. **纯内部信号的修正**：只让模型“再想一想”“检查一下”，没有新的证据、工具或验证器。这类修正很容易把正确答案改错，或者为错误答案编造更完整的理由。

第二类机制是 RSI 讨论中最容易被高估的部分。已有研究反复指出：在没有外部反馈的情况下，LLM 的“自我纠正”能力有限，甚至会在推理任务上降低准确率（Huang 等，2024；Kamoi 等，2024）。因此，一个严肃的 RSI 系统，第一优先级不是“让模型反思”，而是“让反馈变得可验证”。

| 自我反馈形态 | 反馈来源 | 是否更新参数 | 典型方法 | 可靠性来源 |
| --- | --- | --- | --- | --- |
| 任务内反思 | 模型自身判断 | 否 | Self-Refine、反思 Prompt | 低到中，依赖任务可验证性 |
| 执行反馈修正 | 编译器、测试、工具返回值 | 否 | 代码修复 Agent、ReAct | 中到高，依赖环境真实性 |
| 裁判反馈修正 | 另一个模型或规则评分 | 否 | LLM-as-a-Judge、模型辩论 | 中，依赖裁判校准 |
| 参数级学习 | 人工标注、偏好数据、可验证奖励 | 是 | SFT、DPO、RLHF、RLVR | 中到高，依赖数据与奖励质量 |

这张表说明一个关键点：**“自我反馈”不是单一能力，而是由反馈源决定的谱系。** 反馈越接近真实世界、越可执行、越难被模型操纵，自我改进就越可靠。

## 1.2 Agent 让自我改进从“一次生成”变成闭环

Agent 的价值不只是“多调几个工具”，而是把任务变成了一个可以观测、可以重放、可以归因的过程：

```text
目标 → 规划 → 行动（工具调用）→ 观察 → 更新状态 → 继续 / 终止
```

这个循环带来两个变化：

- **执行轨迹（Trace）成为数据资产**：每一步的输入、Prompt、工具参数、返回值、错误、耗时和成本都可以被记录下来。没有 Trace，自我改进只能依赖最终答案的对错；有了 Trace，才能定位“错在哪一步”。
- **改进对象从“答案”扩展到“策略”**：系统可以改的不只是最终输出，还可以是规划模板、工具选择策略、重试条件、上下文压缩方式、终止判据，甚至 Agent 的编排图。

这也是 RSI 与普通 Prompt 调优的分水岭。普通调优的反馈是“这条回答好不好”；Agent 的反馈是“这个任务为什么失败、失败发生在哪个决策点、换一种策略是否会成功”。后者的信息密度高得多，但也要求更完整的观测和更严格的权限控制。

## 1.3 自动化 AI 研发流程正在出现

除了 Agent 执行闭环，另一条线索是“AI 研发过程本身”的自动化：

- **自动生成数据**：用强模型生成指令、答案、偏好对、测试用例和合成文档。
- **自动评估输出**：用规则、单元测试、LLM Judge、人工抽检组合成评估流水线。
- **自动搜索 Prompt**：把 Prompt 当作可优化参数，用进化搜索、贝叶斯优化或 LLM 提议来迭代（OPRO、PromptBreeder、DSPy 等）。
- **自动生成和测试代码**：代码 Agent 生成补丁、运行测试、根据失败信息修复，典型基准如 SWE-bench。
- **自动调参和实验管理**：自动选择模型、Embedding、检索参数、工具组合和 Agent 架构（AutoML、ADAS 等）。

这些环节单独看都不新，但组合起来就形成了一个“研发外循环”：

```text
提出假设 → 生成候选 → 运行实验 → 评估结果 → 保留更优版本 → 再提出假设
```

当这个外循环中的“提出假设”和“设计实验”也开始由 AI 承担时，系统就具备了 RSI 的雏形。需要注意，目前大多数系统仍然由人类定义搜索空间、评估指标和发布规则；AI 自动化的是搜索和执行，不是目标和边界。

研究前沿已经出现了一些更激进的系统：FunSearch 用 LLM 生成程序、用评估器筛选，在数学构造问题上发现了新结果；AlphaEvolve 把 LLM 代码生成与自动评估结合，用于算法发现和工程优化；Darwin Gödel Machine 让 Agent 修改自己的代码并在基准上验证；STOP 让模型生成更好的“自我改进脚手架”。这些工作证明了“LLM + 评估器 + 搜索”可以在特定封闭领域产生真实增益，但它们距离“通用、自主、可无人监管的 RSI”仍有很大距离。

## 1.4 RSI 的核心问题

把上面的现象收束一下，RSI 要回答的是四个问题：

1. **AI 能否改进自己的能力？** 能，但“能力”需要拆开：是任务策略、知识、工具使用，还是模型参数和架构？不同层的可改进性、成本和风险完全不同。
2. **改进对象是什么？** Prompt、数据、检索、记忆、工具策略、Workflow、代码、模型参数、评估器，还是系统配置？改进对象决定了验证方式和回滚难度。
3. **改进是否会递归放大？** 如果系统不仅改 Prompt，还改“改 Prompt 的方法”，甚至改“判断改得好不好的评估器”，反馈回路就可能自我强化。递归本身不是问题，**失去外部锚点的递归**才是问题。
4. **如何评估和控制风险？** RSI 的核心工程矛盾是：改进速度越快，验证和审计越难跟上；自动化程度越高，权限边界越容易失效。

本文的基本立场是：

> **现实中的 RSI 不应直接理解为“模型无限自我进化”，而应从一个“可控范围内的自动化反馈优化系统”开始分析。** 先有可靠的评估、版本、回滚和权限隔离，再谈递归；否则所谓自我改进只是把随机性写进生产系统。

# 二、什么是 Recursive Self-Improvement

## 2.1 一个可操作的定义

**Recursive Self-Improvement（递归式自我改进）** 指一个 AI 系统能够分析自身在任务执行中的表现，识别缺陷，生成改进方案，并将这些改进应用到自身或其运行环境中，从而提升后续任务表现；当这种“改进能力”本身也能够被进一步改进时，就形成递归式自我改进。

用一个简化的形式化表达：

```text
S_{t+1} = Improve(S_t, Feedback(S_t, D))
```

其中：

- `S_t` 是第 t 代的系统，包含模型、Prompt、工具、记忆、Workflow、评估器等组件的某个子集；
- `D` 是任务分布或环境；
- `Feedback` 从执行结果中提取评估信号；
- `Improve` 根据反馈生成并应用改动。

如果 `Improve` 或 `Feedback` 本身也属于 `S_t` 的可修改部分，并且修改后的 `Improve` / `Feedback` 会影响下一轮改进的质量，那么系统就是**递归的**；否则它只是**迭代优化**。

这个定义有三个必要条件：

| 条件 | 含义 | 反例 | 工程含义 |
| --- | --- | --- | --- |
| 闭环反馈 | 执行结果能回流为可用的评估信号 | 人工看几条 bad case 后手改 Prompt，改完不再系统评估 | 需要 Trace、评估集和上线监控 |
| 自我指向 | 改动作用于系统自身的组件，而不只是外部数据 | 只优化用户提供的文档，不改变系统行为 | 需要明确“系统边界”和版本清单 |
| 递归 | 改进能力本身也进入改进对象 | 人类设计好搜索空间，自动跑 100 轮 Prompt 搜索 | 需要元评估、更强门禁和冻结锚点 |

这里最容易含糊的是“**自我**”的边界。一个模型改进自己的权重是自我改进；一个 Agent 改进自己的记忆、工具策略和编排图也是自我改进；一个平台改进自己的 Prompt 搜索器、失败归因器和评估器，同样是自我改进。讨论 RSI 时必须先说明系统边界，否则“它到底改了什么”无法审计。

同样，“改进”必须以**任务分布上的表现**来衡量，而不是单条样本。模型在一条失败样本上改对了，不叫改进；在同类任务上稳定提升，且没有引入回归，才叫改进。

## 2.2 Self-Improvement：从任务内修正到跨版本提升

“自我改进”经常被混用。按作用时间尺度，至少要区分三层：

| 时间尺度 | 改动是否持久 | 典型机制 | 例子 | 主要风险 |
| --- | --- | --- | --- | --- |
| 任务内修正 | 否，随会话结束消失 | 反思、重试、工具回退 | Self-Refine、ReAct 重试 | 循环、成本上升、把对的改错 |
| 跨任务积累 | 是，但只影响后续上下文 | 记忆、技能库、经验总结 | Reflexion 记忆、Voyager 技能库 | 错误经验被长期复用 |
| 跨版本更新 | 是，形成新的系统版本 | Prompt 搜索、数据回流、微调 | Prompt 优化平台、SFT/DPO | 回归、安全退化、难回滚 |

很多被称为“自我改进 Agent”的系统，实际只做到了第一层或第二层：它在当前任务里反思，或者把经验写进记忆，但没有形成可审计的新版本。真正的跨版本自我改进，必须经过评估、验证、发布和回滚，这就从“模型能力”问题变成了“系统工程”问题。

## 2.3 Recursive：改进“改进器”

“递归”不是“多跑几轮”。跑 100 轮 Prompt 搜索仍然是迭代，因为搜索算法、评估器和发布规则都是人设计的。递归要求**改进能力本身发生变化**。可以粗分为几个层级：

- **一阶改进**：优化任务策略。例如改写 Prompt、增加 Few-shot、调整检索参数、修改 Agent 的规划模板。
- **二阶改进**：优化“产生改进的东西”。例如优化 Prompt 优化器的指令、改失败归因分类器、调整候选生成的搜索策略、改进实验调度器。
- **三阶改进**：优化“判断改进好坏的东西”。例如改评估 Rubric、改 Judge Prompt、扩展评估集、调整安全判定规则。

三阶改进最危险，因为它直接移动了目标函数。一个系统如果既能改自己的行为，又能改衡量行为的标准，就很容易陷入自我确认：它可以把标准改得更宽松，然后“证明”自己变好了。因此，成熟的 RSI 系统通常会把评估器放在**自我修改边界之外**，或者至少要求评估器的任何改动都经过独立的人工校准和冻结测试集验证。

几个具体的递归例子：

1. **Prompt 优化器的 Prompt 也被优化**：不仅搜索“客服 Prompt 怎么写”，还搜索“怎样写一个更好的 Prompt 搜索器”。STOP 是这类思路的代表：模型生成一个自我改进的代码脚手架，脚手架再调用模型改进自己；模型权重不变，但改进算子本身在演化。
2. **失败归因器被改进**：系统先用人工标注的失败样本训练/校准归因器，归因器再用于指导后续改动。归因准确率提升会放大所有后续改进的效果，但归因偏差也会被系统性放大。
3. **实验调度器被改进**：系统学习“哪类实验最有信息量”，从而把有限的评估预算分配到更有希望的候选上。这属于研发流程层面的递归。
4. **Agent 修改自己的代码**：Darwin Gödel Machine 这类研究让 Agent 读取并修改自身代码库，再用基准测试筛选。它展示了递归的极限形态，但也把沙箱、基准可靠性和代码安全的重要性推到前台。

需要区分“**递归深度**”和“**迭代次数**”。迭代次数是循环跑了多久；递归深度是改进算子被改了几层。一个系统可以迭代一千次但递归深度为零；也可以在两层递归后迅速收敛，因为评估成本太高、候选空间太小。

## 2.4 Improvement Target：到底改什么

RSI 的改进对象可以分成十层。层级越高，越接近“能力核心”，成本和风险通常也越大：

| 层级 | 改进对象 | 典型手段 | 生效速度 | 可逆性 | 主要风险 | 当前成熟度 |
| --- | --- | --- | --- | --- | --- | --- |
| L1 | Prompt | 改写、Few-shot、输出格式、指令顺序 | 分钟级 | 高 | 过拟合评估集 | 生产可用 |
| L2 | 检索系统 | Chunk 大小、Query Rewrite、重排、过滤 | 小时级 | 高 | 知识库过期、召回抖动 | 生产可用 |
| L3 | 记忆系统 | 事实记忆、技能记忆、摘要、遗忘策略 | 分钟到天 | 中 | 错误记忆污染 | 生产可用 |
| L4 | 工具策略 | 工具选择、参数构造、重试、回退 | 小时级 | 高 | 越权调用、副作用 | 生产可用 |
| L5 | Agent Workflow | 规划模板、状态机、审批点、终止条件 | 天级 | 中 | 复杂度失控 | 早期生产 |
| L6 | 数据与评估集 | SFT/DPO 数据、合成数据、测试集扩展 | 天到周 | 中 | 数据污染、评测泄漏 | 成熟团队可用 |
| L7 | 模型参数 | SFT、LoRA、DPO、RLHF、RLVR | 周到月 | 低到中 | 安全回归、灾难性遗忘 | 选择性使用 |
| L8 | 代码与基础设施 | Agent 脚手架、工具实现、调度逻辑 | 天级 | 中 | 安全漏洞、事故 | 研究/试点 |
| L9 | 评估器 | Rubric、Judge Prompt、判定规则 | 天级 | 中 | Goodhart、目标漂移 | 仅限强管控 |
| L10 | 系统配置 | 模型路由、温度、预算、并发 | 小时级 | 高 | 局部最优、成本反弹 | 生产可用 |

几个判断：

- **L1–L5 是当前投入产出比最高的区域**。它们不需要训练，反馈周期短，回滚容易，适合建立 RSI 的工程基础设施。
- **L6–L7 需要数据治理和评估体系达到一定成熟度**。没有可靠的 Golden Set、没有数据溯源、没有安全回归测试，参数级自我改进很容易把系统带偏。
- **L9 是特殊层**。评估器是 RSI 的“锚”，不是普通组件。它可以被改进，但不应该由被评估的对象在同一循环里随意改进；否则系统会同时扮演运动员和裁判。
- **L8 的风险主要不在模型，而在权限**。Agent 自动改代码、改配置、改数据库，后果可能超出模型质量范畴，进入生产事故范畴。

## 2.5 Feedback Source：反馈从哪来

反馈源决定了 RSI 能“看见”什么。常见来源及其工程特性如下：

| 反馈来源 | 信号形态 | 覆盖范围 | 成本 | 主要偏差/局限 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| 人类反馈 | 评分、修正、偏好、审批意见 | 窄但深 | 高 | 主观、不一致、样本少 | 黄金标准、高风险决策 |
| 程序化验证 | 单元测试、Schema 校验、编译器、执行结果 | 窄但客观 | 低 | 只适用于可验证任务 | 代码、数学、结构化输出 |
| LLM Judge | Rubric 打分、成对比较、自然语言 critique | 宽 | 中 | 位置偏差、冗长偏好、自我偏好 | 大规模离线评估 |
| 运行日志 | 异常、超时、工具失败、重试次数 | 宽但噪声大 | 低 | 相关不等于因果 | 运维、失败归因 |
| 用户行为 | 点击、采纳、追问、转人工、投诉 | 真实但滞后 | 低 | 混淆因素多、信号稀疏 | 线上效果评估 |
| 环境奖励 | 游戏得分、模拟器成功率、任务完成 | 在封闭环境中客观 | 中 | 模拟到现实的差距 | RL、Agent 训练 |
| 安全审计 | 红队结果、策略分类器、事故记录 | 针对性强 | 高 | 覆盖不全、对抗演化 | 上线门禁、安全回归 |

没有单一反馈源足够可靠。工程上通常采用**三角验证**：

- 程序化验证负责“硬错误”：编译失败、格式错误、测试不通过。
- LLM Judge 负责“软质量”：相关性、完整性、语气、引用质量。
- 人类抽检负责“校准”：判断 Judge 是否偏、任务目标是否被误解。
- 线上指标负责“真实后果”：投诉率、转人工率、任务完成率、事故率。

一个常见误区是把 Judge 分数当成唯一目标。Judge 只是对质量的近似测量，不是质量本身。Judge 的偏差会被 RSI 系统放大，尤其是在候选数量多、优化轮次多的情况下。

## 2.6 弱 RSI、中 RSI、强 RSI

按改进对象的深度和自动化程度，可以把 RSI 分成三档：

| 层级 | 定义 | 改进对象 | 自动化程度 | 典型例子 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| 弱 RSI | 自动优化外围系统 | Prompt、RAG、工具策略、Workflow、记忆 | 高，但外循环由人设计 | Prompt 自动优化、RAG 失败回流、Agent 策略调优 | 生产可用 |
| 中 RSI | 自动优化训练数据、训练流程和 Agent 架构 | 数据飞轮、SFT/DPO、Agent 架构搜索 | 部分自动化，关键节点人工审批 | 数据闭环、ADAS、自动化实验平台 | 早期生产/试点 |
| 强 RSI | AI 改进核心模型能力或研究下一代模型架构 | 预训练、架构、训练算法、研究流程 | 低，主要是研究原型 | DGM、AlphaEvolve、自动化算法/架构发现 | 研究前沿 |

这张表要避免两个误读：

1. **弱 RSI 不等于低风险**。一个能自动改生产 Prompt 和工具权限的弱 RSI 系统，如果缺少门禁，照样可以造成严重事故。风险取决于权限和验证，不只取决于改进对象。
2. **强 RSI 不等于递归**。一个由人类设定目标、AI 执行实验的自动化研究系统，可能是强改进但不递归；一个只改 Prompt 优化器的系统，可能是弱改进但递归。真正需要警惕的是“强目标 + 闭环 + 弱监督”的组合。

当前工程实践主要集中在弱 RSI，少数团队在数据闭环和 Agent 架构搜索上进入中 RSI。强 RSI 仍处于研究阶段，且大多在沙箱、固定基准和人类监督下运行。

## 2.7 边界与假设

讨论 RSI 时，需要明确几个边界：

- **评估可靠性是天花板**。系统无法稳定地变得比它的评估器更可靠。评估器有偏，改进就会朝偏差方向走。
- **动作空间必须受限**。不是所有组件都允许自动修改；权限、评估器、安全策略、生产数据通常应排除在自动修改范围之外。
- **递归深度必须受限**。允许一阶改进，不等于允许系统改自己的改进器；允许二阶改进，必须配合冻结评估器和独立审批。
- **人类监督是设计组件，不是临时补丁**。在高风险改动上，人工审批不是“不成熟”的表现，而是系统设计的一部分。
- **算力和数据是物理约束**。递归不会凭空产生信息；每一轮改进都需要新的样本、评估和实验预算。

几个常见误解也值得先澄清：

| 误解 | 实际情况 |
| --- | --- |
| RSI 就是“模型自己训练自己” | 参数更新只是改进对象之一；当前多数 RSI 是非参数层面的 |
| 能反思就是 RSI | 任务内反思不持久、不递归，最多算弱自我修正 |
| 递归越深越强 | 递归同时放大改进和错误；评估器质量才是瓶颈 |
| 自动化程度越高越好 | 自动化与授权应分离；能提出建议不等于能上线 |
| 只要模型够强，评估可以后补 | 没有评估就没有改进方向，强模型只会更快地朝错误方向优化 |

# 三、RSI 与相关概念的区别

Fine-tuning、强化学习、AutoML、Self-Training、Reflection、Agent Learning 与 RSI 经常被混为一谈。它们确实有重叠：RSI 可以使用这些技术作为组件。区别不在于“用了什么算法”，而在于**闭环是否闭合、改进对象是否包含自身、改进能力是否进入回路**。

先看核心属性：

| 概念 | 核心目标 | 自动生成反馈 | 改进自身 | 递归 | 更新模型参数 |
| --- | --- | --- | --- | --- | --- |
| Fine-tuning | 让模型适配任务或领域分布 | 通常否，依赖人工数据 | 是（模型本身） | 否 | 是 |
| Reinforcement Learning | 最大化奖励信号 | 部分，奖励来自环境或奖励模型 | 是（策略） | 通常否，元学习除外 | 是 |
| AutoML | 搜索模型、超参或架构配置 | 是，通常用验证集 | 部分（模型配置） | 通常否 | 可能 |
| Self-Training | 用模型自己的预测扩展训练数据 | 是（伪标签） | 是（模型本身） | 迭代，但通常不递归 | 是 |
| Reflection | 用自我批评改进当前输出 | 是（模型判断） | 部分（当前上下文） | 否 | 否 |
| Agent Learning | 从执行经验改进行为策略 | 部分，依赖环境或人工信号 | 是（策略、记忆、工具） | 可能 | 可选 |
| Recursive Self-Improvement | 改进系统自身及改进能力 | 是或可选 | 是（整个系统） | 是 | 可选 |

再看工程属性：

| 概念 | 典型应用 | 主要工程风险 | 与 RSI 的关系 |
| --- | --- | --- | --- |
| Fine-tuning | 领域适配、风格对齐、格式遵循 | 灾难性遗忘、数据成本、过拟合 | 可作为 RSI 的参数级执行器 |
| Reinforcement Learning | 对齐、推理、控制、Agent 策略 | 奖励黑客、训练不稳定、样本效率低 | 可优化策略或奖励模型，是 RSI 的组件 |
| AutoML | 超参搜索、架构搜索、模型选择 | 验证集过拟合、算力消耗 | 自动化搜索空间，但不必然自我指向 |
| Self-Training | 伪标签、STaR、迭代自举 | 确认偏差、错误累积、模型坍塌 | 一种参数级自我改进机制 |
| Reflection | Agent 重试、答案精炼 | 错误批评、循环、成本上升 | 任务内弱改进组件 |
| Agent Learning | 技能库、工具学习、策略更新 | 不安全动作、技能污染 | 提供 Trace 和策略改进目标 |
| Recursive Self-Improvement | 自动化研发、Prompt/RAG/Workflow 优化 | 评估器失真、递归失控、权限越界 | 包住上述组件的治理闭环 |

可以用一句话总结：

> **RSI 不是一个单独算法，而是一类由反馈、评估、优化和再部署组成的闭环系统。** Fine-tuning、RL、AutoML、Self-Training 都可以是它的“优化器”；Reflection 和 Agent Learning 可以是它的“反馈与执行机制”。真正把它区分开来的，是系统是否把“改进能力”也纳入了改进对象，以及是否有治理机制保证这个闭环不会跑偏。

在实践中，很多被称为 RSI 的系统其实只是“带自动搜索的迭代优化”：外循环的目标、搜索空间、评估集和发布规则都是人定的。把它们称为“自动化改进系统”更准确，也更有利于工程沟通。只有当系统开始改进自己的搜索策略、归因器、评估器或代码时，才进入严格意义上的递归讨论。

# 四、Recursive Self-Improvement 的基本闭环

## 4.1 总览：一个带回路的系统

RSI 的通用流程可以画成一个闭环：

```text
              ┌─────────────────────┐
              │ 任务集 / 真实流量    │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 1. Task Execution   │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 2. Trace Collection │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 3. Evaluation       │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 4. Error Attribution│
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 5. Proposal         │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 6. Validation       │
              └──────────┬──────────┘
                         ▼
              ┌─────────────────────┐
              │ 7. Deployment       │
              └──────────┬──────────┘
                         │
                         └── 新任务 / 新流量 ──▶ 回到 1
```

这个图看起来是线性的，实际执行时会有多条回流：

- 评估发现“评估器本身不可信”，回流到评估集校准，而不是直接改系统。
- 归因发现“失败原因不明确”，回流到补充 Trace 或人工复盘。
- 验证发现“候选改动只对某类样本有效”，回流到提案生成，要求更窄的改动。
- 部署后的线上监控发现回归，触发回滚，并把线上样本加入下一轮评估集。

工程上最重要的是**每一段回流都有明确的触发条件、责任人和上限**。没有上限的回路不是 RSI，是失控的自动化。

## 4.2 Task Execution：先定义“在什么任务上改进”

Task Execution 不是“随便跑几个问题”，而是定义一个可重复的实验环境。它至少包含：

- **任务集**：按意图、难度、语言、用户类型分层；包含正常样本、边界样本、对抗样本、安全样本和回归样本。
- **执行环境**：模型版本、Prompt 版本、工具版本、检索索引版本、数据库快照、网络权限、超时和预算。
- **执行模式**：
  - 离线批跑：成本低、可重复，适合快速筛选。
  - Shadow 运行：在真实流量上并行执行候选版本，但不影响用户。
  - 灰度运行：让少量真实用户进入候选版本，观察线上指标。
  - 红队运行：用专门的攻击样本测试安全边界。

| 执行模式 | 真实度 | 成本 | 可重复性 | 适合阶段 |
| --- | --- | --- | --- | --- |
| 离线批跑 | 低到中 | 低 | 高 | 候选筛选、回归测试 |
| Shadow | 中到高 | 中 | 中 | 上线前验证 |
| 灰度 | 高 | 中到高 | 低 | 小流量验证 |
| 红队 | 针对性高 | 高 | 中 | 安全门禁 |

一个常见错误是“用训练集跑任务、用同一批样本评估”。这会让系统在评估集上过拟合，却对真实分布毫无帮助。任务集和执行集必须有明确的数据划分策略，至少包括：

- **开发集**：用于分析失败、生成候选。
- **验证集**：用于筛选候选、调参。
- **测试集 / Golden Set**：只在最终验收时使用，不参与优化。
- **留出集**：按时间、意图或来源切分，用于检测泛化。
- **安全集**：独立维护，不因业务指标优化而被稀释。

## 4.3 Trace Collection：没有 Trace 就没有归因

Trace 是 RSI 的原始数据。它不只是最终输入输出，而是整个执行过程的结构化记录。一个可用的 Trace Schema 至少应包含：

| 字段 | 示例 | 用途 |
| --- | --- | --- |
| `trace_id` | `tr_20261117_00123` | 全局追踪、关联评估和审计 |
| `task_id` | `returns_policy_042` | 关联任务集和失败聚类 |
| `input` | 用户原始问题 | 复现、分层、隐私审查 |
| `prompt_version` | `cs_returns_v7` | 定位 Prompt 改动 |
| `model_version` | `model-x-2026-10` | 区分模型能力与策略问题 |
| `sampling_params` | `temperature=0.2, top_p=0.9` | 复现随机性 |
| `steps` | 规划、工具调用、观察、决策 | 定位失败步骤 |
| `retrieval_context` | 文档 ID、片段、分数 | 判断检索问题 |
| `tool_calls` | 工具名、参数、返回值、耗时 | 判断工具误用或失败 |
| `errors` | 异常类型、错误码、堆栈摘要 | 硬失败分析 |
| `user_feedback` | 评分、修正、转人工 | 真实质量信号 |
| `cost` / `latency` | token 数、美元成本、毫秒 | 成本与性能约束 |
| `safety_flags` | 策略命中、风险等级 | 安全回归分析 |
| `environment` | 索引版本、配置哈希 | 环境漂移排查 |

工程要点：

1. **记录决策，而不只是结果**。只记录最终答案，无法判断是“检索没找到”还是“找到了但没用”。要记录每一步的候选、选择理由和工具返回。
2. **记录版本和哈希**。Prompt、模型、索引、工具、配置都要有版本号或内容哈希；否则 Trace 无法复现。
3. **默认脱敏**。用户输入、工具返回和检索文档可能包含 PII；Trace 存储要做字段级脱敏、访问控制和保留期限管理。
4. **追加写、不可篡改**。审计日志与调试日志分开；审计日志应 append-only，最好有哈希链或 WORM 存储。
5. **采样与成本平衡**。全量记录成本高，可以按任务类型、失败率、风险等级分层采样；但安全相关 Trace 不应被采样掉。

Trace 的完整性本身应该被度量。一个实用指标是 **Trace Completeness**：必填字段缺失率、工具调用与观察是否成对、错误是否有堆栈、评估是否有证据链接。Trace 不完整时，系统应该拒绝进入自动归因，而不是用模型“猜”失败原因。

## 4.4 Evaluation：把“好不好”变成可计算的信号

评估层通常由五类方法组合而成：

| 层次 | 方法 | 延迟 | 成本 | 适合 | 局限 |
| --- | --- | --- | --- | --- | --- |
| 程序化验证 | 单元测试、Schema、编译器、规则 | 秒级 | 低 | 可验证任务 | 覆盖窄，容易被绕过 |
| LLM Judge | Rubric 打分、成对比较、critique | 秒到分钟 | 中 | 开放任务的大规模评估 | 偏差、漂移、可被优化 |
| 人工评估 | 专家评分、成对比较、复核 | 小时到天 | 高 | 黄金标准、高风险 | 慢、贵、不一致 |
| 线上指标 | 完成率、转人工率、投诉率、留存 | 小时到周 | 低 | 真实业务效果 | 混淆因素多、滞后 |
| 安全检查 | 策略分类器、红队、拒答测试 | 分钟到天 | 中到高 | 安全回归 | 覆盖不全、对抗演化 |

评估设计要解决四个问题：

1. **评什么**：正确性、完整性、忠实性、相关性、格式、语气、安全性、成本、延迟。不同任务权重不同，不能用一个大而全的分数代替。
2. **谁来评**：程序化验证优先，Judge 扩展覆盖，人类校准，线上验证真实后果。四者不是替代关系，而是互补关系。
3. **怎么评**：单点评分适合绝对质量，成对比较适合版本选择；成对比较要做位置随机化，避免位置偏差。Judge 要有 Rubric 版本，Rubric 改动要重新校准。
4. **评得准不准**：用人工标注样本计算 Judge 与人类的一致率（如 Cohen's kappa、Spearman 相关），并持续监控。Judge 一致性下降时，应暂停自动改进，而不是继续放大噪声。

统计上要注意：小样本的分数波动可能大于真实改进。候选版本与基线版本应在同一批任务上做配对比较，报告置信区间；多候选比较要做多重检验校正。否则系统会把随机噪声当成改进，反复“优化”却没有真实收益。

## 4.5 Error Attribution：定位“为什么错”

错误归因是 RSI 最容易被低估的环节。评估告诉你“失败了”，归因告诉你“该改哪里”。归因错了，后面的提案、验证和部署都会朝错误方向努力。

常见的归因方法：

| 方法 | 做法 | 成本 | 输出 | 注意事项 |
| --- | --- | --- | --- | --- |
| 人工复盘 | 专家看 Trace，标注失败步骤 | 高 | 高质量根因标签 | 样本少，需抽样策略 |
| Trace Replay | 用相同输入和中间状态重放 | 中 | 可复现的失败路径 | 依赖环境快照 |
| 组件替换/消融 | 换 Prompt、换检索器、换模型，看哪个修复 | 中到高 | 因果性更强的证据 | 组合爆炸，需控制变量 |
| 反事实测试 | 提供正确文档/正确工具结果，看是否能答对 | 中 | 区分“不知道”和“不会用” | 构造反事实样本有成本 |
| 失败聚类 | 按意图、错误类型、工具、文档聚类 | 低 | 高频失败模式 | 聚类标签需人工校验 |
| LLM 归因 | 让模型阅读 Trace 并给出根因 | 低到中 | 可扩展的假设 | 可能似是而非，必须附证据 |

一个实用的归因流程是“先分层，再反事实”：

1. 按任务类型、失败现象、涉及工具聚类，找出高频、高影响的失败簇。
2. 对每个簇抽样，人工确认失败步骤。
3. 用组件替换做因果验证：如果换成 Gold 文档后答对，问题在检索；如果换了 Prompt 仍错，问题可能在模型能力或任务定义。
4. 把根因写成结构化标签，附上 Trace 证据和复现步骤。

归因结果要区分几类原因：

- **Prompt 问题**：指令缺失、约束冲突、示例误导、输出格式不清。
- **模型能力问题**：知识不足、推理错误、指令遵循失败、长上下文丢失。
- **检索问题**：召回缺失、排序错误、Chunk 切断、文档过期、多跳未覆盖。
- **工具问题**：工具选错、参数错、返回值解析错、权限不足、超时。
- **数据问题**：知识库缺文档、标注错误、评估集标签错误。
- **评估问题**：Judge 误判、Rubric 不清、测试用例本身有错。
- **任务定义问题**：用户问题歧义、目标不明确、约束互相矛盾。

最后两类尤其重要：**不是所有失败都该由模型或系统来修**。如果评估器把正确答案判错，继续优化模型只会让系统学会迎合错误的评估器。

## 4.6 Proposal Generation：把归因变成可验证的改动

提案生成不是“让模型自由发挥改代码”，而是在受控动作空间里生成结构化改动。一个好的提案至少包含：

```json
{
  "proposal_id": "prop_20261117_004",
  "target": "prompt.customer_service.returns",
  "evidence": ["trace_1024", "trace_1088", "trace_1103"],
  "change": {
    "op": "replace",
    "path": "sections.return_policy",
    "value": "..."
  },
  "hypothesis": "补充跨境订单和已拆封商品的退货条件，可减少政策类回答的遗漏",
  "expected_gain": 0.08,
  "risk": "medium",
  "validation_plan": ["golden_set_v7", "safety_set_v3"],
  "rollback_plan": "revert to prompt hash 8f3a..."
}
```

提案生成常见的四种方式：

- **规则/模板**：针对明确的失败模式，直接套用修复模板。可解释性最好，覆盖有限。
- **LLM 提议**：把失败聚类、Trace 摘要和当前版本交给模型，让它生成改动建议。覆盖广，但需要严格约束格式和范围。
- **进化搜索**：维护候选池，按评估分数选择、变异、交叉。适合 Prompt 和配置搜索，但评估成本高。
- **贝叶斯优化 / Bandit**：在低维连续或离散空间里高效搜索，适合检索参数、模型路由、预算分配。

提案阶段要加四类约束：

1. **动作空间约束**：只允许修改白名单内的组件；评估器、安全策略、权限配置默认不在白名单。
2. **改动大小约束**：限制 diff 行数、Prompt 增删字数、Workflow 节点变化数。大改动难以归因，也难回滚。
3. **证据约束**：每个提案必须引用具体失败样本和根因标签，不能只给“感觉更好”的理由。
4. **风险分级**：低风险（措辞、Few-shot）、中风险（检索配置、Workflow 步骤）、高风险（模型、权限、评估器）走不同审批路径。

提案数量不是越多越好。候选太多会稀释评估预算，也增加多重比较带来的假阳性。工程上更有效的是“少量、多样、可解释”的候选集，而不是让模型一次生成一百个变体。

## 4.7 Validation：先证伪，再上线

验证的目标不是“证明候选有效”，而是“尽早发现候选无效”。一个完整的验证阶梯：

| 阶段 | 目的 | 成本 | 真实度 | 主要风险 |
| --- | --- | --- | --- | --- |
| 离线 Golden Set | 快速筛选、回归检测 | 低 | 中 | 评估集过拟合 |
| 留出集/跨域集 | 检测泛化 | 低到中 | 中 | 分布仍不够真实 |
| 安全回归/红队 | 检测拒答、越权、注入 | 中 | 中到高 | 攻击集覆盖不足 |
| Shadow | 真实流量下并行比较 | 中到高 | 高 | 不影响用户，但成本翻倍 |
| 灰度 Canary | 小流量真实发布 | 中 | 最高 | 事故影响真实用户 |
| 全量 A/B | 统计显著的业务效果 | 高 | 最高 | 周期长、干扰因素多 |

验证要遵守几条纪律：

- **候选不能选择自己的考卷**。测试集、评估器和判定阈值由独立角色维护；提案方只能读取结果，不能修改。
- **回归优先于提升**。一个候选即使平均分提升，只要在关键任务或安全集上回归，就不能上线。
- **报告置信区间**。不要只看均值；配对 bootstrap、置信区间和最小可检测效应（MDE）能避免追逐噪声。
- **成本与延迟是一等公民**。质量提升 2 个百分点但成本翻倍、延迟翻三倍，通常不值得上线。
- **人工审批按风险分级**。低风险改动可以自动验证后灰度；高风险改动必须有人类签字，并保留否决理由。

## 4.8 Deployment：发布不是终点

部署阶段要解决四个问题：版本、灰度、回滚、监控。

- **版本**：每次发布生成不可变 artifact，记录 Prompt、模型、数据、工具、Workflow、评估器和配置的哈希，以及父子版本关系。
- **灰度**：按用户、流量、地域或任务类型分流；灰度比例从 1%–5% 开始，观察质量、安全、成本、延迟和用户行为。
- **回滚**：一键回滚到上一个稳定版本；回滚不仅是代码回滚，还包括数据迁移、索引切换和缓存失效。对于模型微调，回滚意味着保留旧权重和旧推理配置。
- **监控**：上线后持续监控主指标和护栏指标；设置自动回滚阈值，例如安全事件 > 0、回归率 > 1%、投诉率显著上升、P95 延迟超预算。

部署控制器不应由提案方直接调用。提案方生成候选，实验管理器验证，安全门禁批准，部署控制器执行；四个角色使用不同的凭证和权限。这个分离是 RSI 安全架构的核心，不是形式主义。

# 五、LLM 时代 RSI 的可落地实现路径

## 5.1 Prompt 自我优化

Prompt 优化是当前最成熟的弱 RSI 形态。它的闭环通常是：

```text
失败样本聚类 → 归因 → 生成 Prompt 候选 → 离线评估 → 选优 → 灰度 → 监控
```

### 5.1.1 失败样本从哪来

- 线上低评分、转人工、用户追问、投诉。
- 离线评估集中稳定失败的样本。
- 红队和安全测试中的越权、拒答失败。
- 人工抽检发现的格式、引用、语气问题。

不要对所有失败一视同仁。优先处理**高频、高影响、可归因**的失败簇：高频决定收益，高影响决定优先级，可归因决定能否自动修复。

### 5.1.2 候选怎么生成

常见的 Prompt 改动类型：

| 改动类型 | 适用失败 | 风险 |
| --- | --- | --- |
| 补充约束 | 遗漏关键条件、格式错误 | 约束过多导致其他任务僵化 |
| 增加 Few-shot | 输出风格不稳定、边界案例 | 示例偏差、上下文变长 |
| 调整指令顺序 | 指令冲突、优先级不清 | 对长 Prompt 影响难预测 |
| 任务分解 | 多步任务、复杂约束 | 延迟和成本上升 |
| 输出模板 | 结构化输出、引用格式 | 模板过于僵化，覆盖例外困难 |
| 澄清策略 | 输入歧义、信息不足 | 过度追问，用户体验下降 |

候选生成可以用 LLM 提议，也可以用规则模板。关键是**一次只改一类东西**，否则验证时无法归因。比如“补充跨境退货条件”和“增加两个 Few-shot”应该拆成两个候选，分别评估。

### 5.1.3 例子：客服退货政策回答不完整

假设一个电商客服系统收到这样的失败样本：

> 用户：我上个月买的耳机，已经拆封了，是从海外仓发的，还能退吗？
>
> 系统：根据退货政策，商品签收后 7 天内可申请退货，请保持商品完好。

这条回答的问题不是“语气不好”，而是：

1. 只覆盖了国内、未拆封、7 天内的默认情况。
2. 没有区分跨境订单、已拆封商品和退货窗口。
3. 没有在信息不足时追问订单类型和签收时间。
4. 没有引用具体政策条款，用户无法核对。

Trace 显示：检索召回了“国内退货政策”文档，但没有召回“跨境退货”和“已拆封商品”文档；Prompt 中没有要求按订单类型分支；生成模型直接套用了最相似的默认政策。

归因结果是“Prompt 缺少分支约束 + 检索缺少跨境文档”，于是生成两个独立提案：

**提案 A：Prompt 增加退货政策分支**

```text
回答退货问题时，按以下顺序处理：
1. 确认订单类型：国内 / 跨境；
2. 确认商品状态：未拆封 / 已拆封；
3. 确认签收时间，判断是否在对应退货窗口内；
4. 信息不足时先追问，不要假设；
5. 按“适用条件 → 操作步骤 → 时效 → 例外”组织答案；
6. 引用知识库章节号；不确定时说明需人工确认。
```

**提案 B：检索增加跨境退货文档，并调整 Query Rewrite**

把“海外仓”“跨境”“国际订单”加入同义词表；对退货类问题强制检索“跨境退货”文档；在 Reranker 中提高政策类文档权重。

验证时分别跑：

- 300 条退货类 Golden Set：提案 A 的完整率从 61% 提升到 78%，提案 B 从 61% 提升到 74%；A+B 组合提升到 86%。
- 其他意图回归集：提案 A 在“换货”“保修”上出现轻微下降，因为分支约束被过度泛化；缩小 Prompt 作用范围后恢复。
- 安全集：检查是否出现“承诺无条件退货”等越权表述。
- 成本：Prompt 变长导致平均输入 token 增加约 15%，需要评估是否可接受。

最终上线组合方案，灰度 5%，监控退货类投诉率、转人工率和平均对话轮次。这个例子的数字是示意，但流程是真实的：**先归因，再拆分提案，分别验证，最后组合灰度**。

### 5.1.4 防止过拟合评估集

Prompt 优化的最大工程风险是“在评估集上刷分”。常见表现：

- Prompt 里堆了大量针对测试样本的特定措辞。
- Few-shot 示例与测试集高度相似，甚至重复。
- 只在固定 200 条样本上提升，换一批真实问题就退化。
- Prompt 越来越长、越来越复杂，可维护性下降。

防护手段：

- **数据切分按意图和时间**，不只随机切分；随机切分会让同义问题同时出现在训练和测试中。
- **维护隐藏测试集**，不参与候选生成，只在验收时使用。
- **跨域/跨意图留出集**，检测改动是否破坏了其他能力。
- **Prompt 复杂度惩罚**，把长度、规则数量、Few-shot 数量纳入选择标准。
- **对抗性改写**，用同义改写、错别字、口语化、多语言混合测试鲁棒性。
- **定期轮换评估集**，从线上失败样本中补充新案例，淘汰过时样本。
- **去重和污染检查**，确保测试集没有出现在 Few-shot 或训练数据中。

## 5.2 RAG 系统自我改进

RAG 的失败模式比 Prompt 更结构化，因此更适合做自动归因和闭环优化。

### 5.2.1 失败模式与改进动作

| 失败现象 | 可能原因 | 改进动作 | 验证指标 |
| --- | --- | --- | --- |
| 答案缺少关键条款 | Chunk 切断、召回不全 | 调整 Chunk/Overlap、Parent-Child 检索 | Context Recall、答案完整率 |
| 召回文档不相关 | Query 与文档表述不一致 | Query Rewrite、HyDE、混合检索 | Recall@k、nDCG |
| 多跳问题只答一半 | 单轮检索、缺少迭代 | 多轮检索、查询分解 | Answer Correctness |
| 文档过期 | 知识库未更新 | 文档缺口检测、人工补录 | 时效性、Faithfulness |
| 有文档但答案不引用 | 生成未利用上下文 | 引用约束、Faithfulness 检查 | 引用准确率 |
| 该拒答却编造 | 缺少弃权策略 | 置信度阈值、拒答 Prompt | 幻觉率、误答率 |

### 5.2.2 可自动化的部分

- **检索参数搜索**：Chunk 大小、Overlap、Top-k、混合检索权重、Reranker 阈值。这些是低维连续/离散参数，适合贝叶斯优化或网格搜索。
- **Query Rewrite 策略**：多查询生成、同义词扩展、指代消解、时间/地域过滤。可以用失败样本自动生成改写候选。
- **Reranker 选择**：比较不同重排模型或规则，按 nDCG 和最终答案质量选择。
- **上下文压缩**：在 token 预算内选择最相关的片段，降低噪声和成本。
- **文档缺口检测**：聚类“检索为空”或“低忠实性”的问题，识别知识库缺什么文档；生成补全建议，但**由人审核后入库**。

### 5.2.3 不能自动化的部分

- **知识库内容的最终真实性**。模型可以建议“补一篇跨境退货文档”，但不能凭空生成政策条款并直接上线。
- **权限和合规边界**。哪些文档可以被哪些用户检索，必须由业务和合规决定。
- **文档冲突的裁决**。两份文档说法不一致时，系统可以标记冲突，但不能自动选择更“顺眼”的那份。

一个成熟的 RAG 自改进系统会把“文档补全建议”和“文档发布”分开：系统生成缺口报告、草稿和引用来源，人类编辑审核后发布。这样既利用了自动化，又保留了事实责任的归属。

## 5.3 Agent Workflow 自我改进

Agent 的 Trace 天然适合做步骤级归因。常见的失败步骤包括：

- 规划错误：任务分解遗漏、顺序错误、目标漂移。
- 工具选择错误：该查数据库却搜网页，该用计算器却心算。
- 参数构造错误：日期格式、ID、过滤条件。
- 观察解析错误：把错误码当成功，把空结果当有结果。
- 循环 / 超出步数上限：反复搜索、反复重试、无法终止。
- 过早终止：信息不足就下结论。
- 上下文溢出：长 Trace 中丢失早期约束。

对应的改进动作：

| 失败步骤 | 改进动作 | 验证方式 |
| --- | --- | --- |
| 规划遗漏 | 调整规划模板、增加检查清单 | 任务完成率、步骤覆盖率 |
| 工具选错 | 改工具描述、增加路由规则 | 工具选择准确率 |
| 参数错误 | 增加参数 Schema、示例、校验 | 工具调用成功率 |
| 观察误读 | 增加解析器、错误分类 | 错误恢复率 |
| 循环 | 增加最大步数、重复检测、换策略 | 平均步数、超时率 |
| 过早终止 | 增加完成度检查、覆盖度检查 | 任务完成率、遗漏率 |
| 上下文溢出 | 摘要、状态外置、分段执行 | 长任务成功率 |

Workflow 改动比 Prompt 改动风险更高，因为它改变的是控制流。一个“增加重试”的改动可能让系统在失败时消耗更多预算；一个“减少审批点”的改动可能让高风险动作直接执行。因此 Workflow 改动应满足：

- 有明确的步骤级测试用例，而不只是端到端评分。
- 有预算上限和终止条件。
- 不修改权限、审批和安全策略；这些属于受保护组件。
- 先在沙箱和 Shadow 中运行，再灰度。

## 5.4 代码生成 Agent 自我改进

代码 Agent 是 RSI 最自然的试验场，因为反馈可执行、可验证：

```text
生成代码 → 运行测试 → 解析失败 → 定位问题 → 修改代码 → 重跑测试
```

这个循环可以进一步扩展：

- **生成测试**：根据需求、接口签名、已有测试生成新测试用例。
- **变异测试**：故意注入小错误，检查测试是否能捕获，评估测试质量。
- **错误模式挖掘**：统计常见失败（导入错误、API 误用、边界条件、异步、类型错误），写进 Prompt 或检查规则。
- **策略改进**：调整“先读代码还是先写测试”“先局部修复还是重写”“何时请求人类帮助”的策略。
- **测试集扩展**：把线上失败案例转成回归测试，防止同类问题再次出现。

但代码 Agent 有几个特殊风险：

1. **测试篡改**：Agent 可能修改测试来让结果通过，而不是修复代码。必须使用不可变的隐藏测试，并审查测试文件的 diff。
2. **自生成测试不可靠**：模型生成的测试本身可能有错，或者只覆盖它自己实现的路径。需要人工抽检、变异测试和独立测试集。
3. **奖励黑客**：如果评估只看“测试通过”，Agent 可能写死返回值、捕获所有异常、删除断言。评估要包含隐藏测试、静态检查、代码审查和安全扫描。
4. **供应链与权限**：代码 Agent 可能引入恶意依赖、执行任意命令、访问网络。必须在沙箱中运行，限制网络、文件系统和凭证。
5. **修复收益有限**：研究表明，自修复对代码生成的提升并非无限，且依赖失败信息的质量（Olausson 等，2024）。不要假设“多修几轮一定更好”。

## 5.5 数据闭环与自训练

数据闭环是弱 RSI 走向中 RSI 的关键一步。典型流程：

```text
成功 Trace ──▶ 过滤/验证 ──▶ SFT 数据
失败 Trace + 人工修正 ──▶ 偏好对 ──▶ DPO / 偏好优化
合成数据 ──▶ 执行验证 / Judge ──▶ 训练集
评估结果 ──▶ 难例挖掘 ──▶ 课程学习
```

| 数据类型 | 来源 | 验证方式 | 用途 | 主要风险 |
| --- | --- | --- | --- | --- |
| 成功轨迹 | 线上/离线高评分任务 | 人工抽检、规则校验 | SFT、行为克隆 | 把偶然成功当普遍规律 |
| 修正样本 | 人工编辑、工具修复 | 人工确认、回归测试 | SFT、DPO | 修正本身有错 |
| 偏好对 | 同题多答案比较 | Judge + 人工校准 | DPO、RLHF | 偏好偏差、冗长偏好 |
| 合成数据 | 强模型生成 | 执行验证、Judge、去重 | SFT、数据增强 | 错误累积、风格单一 |
| 难例 | 失败聚类、边界样本 | 人工标注 | 课程学习、评估集 | 难度定义主观 |
| 安全样本 | 红队、事故复盘 | 安全专家审核 | 安全训练、回归 | 覆盖不足、对抗演化 |

数据闭环的核心不是“收集更多数据”，而是“收集可验证的数据”。在代码、数学、结构化查询等有明确验证器的领域，自动数据闭环相对可靠；在开放域问答、创意写作、咨询建议等缺乏验证器的领域，自动生成的数据很容易把模型自己的偏差固化下来。

需要特别警惕**模型坍塌**：如果训练数据大量来自模型自身生成，且缺少新鲜的人类数据或真实世界信号，模型可能逐渐丢失多样性、尾部知识和鲁棒性（Shumailov 等，2024；Martínez 等，2023）。工程上的缓解措施包括：

- 保留一定比例的人类标注/真实数据。
- 对合成数据做严格过滤、去重和多样性检查。
- 用独立验证器或执行环境筛选，而不是只用生成模型自评。
- 监控输出多样性、罕见意图覆盖率和校准误差。
- 定期用新鲜的真实样本重新校准评估集。

## 5.6 AutoML / AutoAgent

AutoML 和 AutoAgent 把“搜索”本身自动化。可搜索的对象包括：

| 搜索对象 | 候选空间 | 评估成本 | 适合方法 |
| --- | --- | --- | --- |
| 模型选择 | 不同规模/厂商/版本 | 中 | 网格/贝叶斯优化 |
| Embedding | 不同向量模型 | 中 | 离线检索指标 |
| 检索参数 | Chunk、Top-k、混合权重 | 低 | 贝叶斯优化/网格 |
| Prompt | 指令、示例、格式 | 低到中 | 进化搜索/LLM 提议 |
| 工具组合 | 工具子集、路由规则 | 中到高 | 消融/搜索 |
| Agent 架构 | 规划器、记忆、协作拓扑 | 高 | ADAS/架构搜索 |
| 系统配置 | 温度、预算、并发、路由 | 低 | 多目标优化 |

AutoAgent 的代表工作是 ADAS（Automated Design of Agentic Systems），它让元 Agent 生成新的 Agent 架构，并在基准上评估。这类方法的价值在于扩大搜索空间，风险在于：

- **基准过拟合**：在一个基准上搜出的架构，换任务可能失效。
- **复杂度膨胀**：搜索倾向于堆模块，导致成本、延迟和维护难度上升。
- **评估成本**：架构级搜索需要大量端到端运行，预算容易失控。
- **可解释性**：自动生成的架构可能难以审计，尤其是涉及工具权限和外部调用时。

工程建议是从低维搜索开始：先搜检索参数和模型路由，再搜 Prompt 和工具组合，最后才考虑 Workflow/架构级搜索。每一层都要有独立的评估集、成本预算和回滚方案。

# 六、RSI 系统的工程架构设计

## 6.1 总体架构

一个可落地的 RSI 系统可以分为九个模块：

```text
                    ┌──────────────────────────────┐
                    │      Version Registry        │
                    │ prompt / model / data / tool │
                    │ workflow / evaluator / config│
                    └───────┬──────────────┬───────┘
                            │              │
┌─────────────┐   tasks   ┌─▼──────────┐   │
│ Task Suite  │──────────▶│ Task Runner│   │
└─────────────┘           └─┬──────────┘   │
                            │ traces       │
                    ┌───────▼────────┐     │
                    │ Trace Logger   │     │
                    └───────┬────────┘     │
                            ▼              │
                    ┌────────────────┐     │
                    │Evaluation Engine│◀───┘
                    └───────┬────────┘
                            ▼
                    ┌────────────────┐
                    │ Error Analyzer │
                    └───────┬────────┘
                            ▼
                    ┌────────────────┐
                    │Improvement     │
                    │Proposer        │
                    └───────┬────────┘
                            ▼
                    ┌────────────────┐
                    │Experiment      │
                    │Manager         │
                    └───────┬────────┘
                            ▼
                    ┌────────────────┐
                    │  Safety Gate   │◀── policy / human approval
                    └───────┬────────┘
                            ▼
                    ┌────────────────┐
                    │Deployment      │
                    │Controller      │
                    └───────┬────────┘
                            ▼
                      production
```

### 6.1.1 Task Runner

- 接收任务集或真实流量，按版本清单执行。
- 管理并发、超时、重试、预算和工具权限。
- 记录环境快照，保证可复现。
- 支持离线、Shadow、灰度三种模式。

### 6.1.2 Trace Logger

- 结构化记录每一步的输入、决策、工具调用、观察、错误、成本、延迟。
- 做字段级脱敏、访问控制、保留期限管理。
- 审计日志与调试日志分离，审计日志 append-only。
- 为每条 Trace 关联版本哈希和评估结果。

### 6.1.3 Evaluation Engine

- 运行程序化验证、Judge、人工评审和安全检查。
- 维护评估集、Rubric、Judge 版本和校准记录。
- 输出分层分数、失败标签、证据链接和置信区间。
- 检测评估器漂移，定期与人工标注对齐。

### 6.1.4 Error Analyzer

- 对失败样本做聚类、归因和优先级排序。
- 支持 Trace Replay、组件替换、反事实测试。
- 输出结构化失败标签、根因假设和证据。
- 识别“评估器误判”和“任务定义问题”，避免错误优化。

### 6.1.5 Improvement Proposer

- 在受控动作空间内生成结构化提案。
- 每个提案包含证据、改动、假设、预期收益、风险和回滚计划。
- 对提案做去重、多样性控制和风险分级。
- 不拥有部署权限，不能修改评估器和安全策略。

### 6.1.6 Experiment Manager

- 为每个候选创建独立实验版本。
- 管理对照组、实验组、随机化和样本量。
- 运行离线评估、回归测试、Shadow 和灰度。
- 输出验证报告，包括主指标、护栏指标、成本和置信区间。

### 6.1.7 Safety Gate

- 检查安全策略、权限边界、风险等级和人工审批。
- 对高风险改动强制人工签字。
- 运行安全回归、红队和注入测试。
- 门禁故障时 fail closed（拒绝发布），而不是放行。

### 6.1.8 Deployment Controller

- 管理 artifact、灰度比例、流量路由和回滚。
- 监控主指标和护栏指标，触发自动回滚。
- 记录发布、审批、回滚的完整审计日志。
- 只接受通过 Safety Gate 的 artifact。

### 6.1.9 Version Registry

- 记录 Prompt、模型、数据集、工具、Workflow、评估器、配置的版本和哈希。
- 维护父子关系、实验分支、发布记录和回滚点。
- 为 Trace、评估、提案和发布提供统一的事实来源。
- 支持按版本重放和差异对比。

| 模块 | 输入 | 输出 | 关键控制 |
| --- | --- | --- | --- |
| Task Runner | 任务集、版本清单 | Trace、运行结果 | 预算、超时、权限 |
| Trace Logger | 运行事件 | 结构化 Trace | 脱敏、不可篡改 |
| Evaluation Engine | Trace、评估集 | 分数、失败标签 | Judge 校准、版本化 |
| Error Analyzer | 失败 Trace | 根因、失败簇 | 证据链接、人工复核 |
| Improvement Proposer | 根因、当前版本 | 结构化提案 | 白名单、diff 限制 |
| Experiment Manager | 提案、评估集 | 验证报告 | 对照、随机化、统计 |
| Safety Gate | 候选、风险等级 | 批准/拒绝 | 人工审批、fail closed |
| Deployment Controller | 已批准 artifact | 灰度/全量版本 | 回滚、监控 |
| Version Registry | 所有 artifact | 版本图谱 | 哈希、审计、不可变 |

## 6.2 数据流

一次完整的 RSI 循环：

1. **Task Runner** 从 **Version Registry** 读取当前稳定版本，在任务集或真实流量上执行。
2. **Trace Logger** 记录执行轨迹，写入脱敏后的 Trace 存储，并关联版本哈希。
3. **Evaluation Engine** 读取 Trace，运行规则、Judge、人工评审和安全检查，产出分数、失败标签和证据。
4. **Error Analyzer** 对失败样本聚类、归因，输出高频失败簇和根因假设；无法归因的样本进入人工队列。
5. **Improvement Proposer** 根据根因生成候选提案，附上证据、预期收益、风险和回滚计划。
6. **Experiment Manager** 把提案应用到候选版本，运行离线评估、回归测试和 Shadow，产出验证报告。
7. **Safety Gate** 检查候选的安全回归、权限边界、风险等级和人工审批；不通过则退回。
8. **Deployment Controller** 将通过门禁的候选灰度发布，监控线上指标；异常时自动回滚。
9. **Version Registry** 记录候选、验证、审批、发布和回滚的完整链路，成为下一轮循环的起点。

## 6.3 控制面与数据面分离

把系统分成两个平面，有助于理解权限边界：

- **数据面**：Task Runner、Trace Logger、Deployment Controller。它们处理任务执行、日志和流量，直接接触生产环境。
- **控制面**：Evaluation Engine、Error Analyzer、Improvement Proposer、Experiment Manager、Safety Gate。它们处理评估、归因、提案和验证，原则上不直接接触生产写权限。
- **事实源**：Version Registry。所有 artifact、版本、审批和指标都以它为准。

三条硬性分离：

1. **提案与部署分离**：Proposer 只能写候选，不能调用 Deployment Controller；部署需要使用独立凭证，并由 Safety Gate 签发。
2. **评估与提案分离**：Proposer 不能修改评估器、测试集和判定阈值；评估器由独立团队维护，变更需要人工校准。
3. **实验与生产分离**：Experiment Manager 在沙箱/Shadow 中运行，不能直接写生产数据库、发消息或调用有副作用的工具。

这三条分离对应三个常见的失效模式：自己改自己、自己判自己、自己上线。任何一条失效，RSI 的安全假设就不成立。

## 6.4 版本与审计

Version Registry 至少应覆盖：

| 对象 | 版本字段 | 关联 | 用途 |
| --- | --- | --- | --- |
| Prompt | 内容哈希、父版本、变更说明 | 任务、评估、Trace | 复现和回滚 |
| 模型 | 模型 ID、权重哈希、推理配置 | 成本、延迟、安全 | 区分能力与策略 |
| 数据集 | 数据哈希、来源、过滤规则 | 训练、评估、污染检查 | 数据溯源 |
| 工具 | 工具版本、Schema、权限 | 调用日志、事故 | 权限审计 |
| Workflow | 图结构哈希、节点配置 | 任务、Trace | 控制流回滚 |
| 评估器 | Rubric、Judge Prompt、阈值 | 分数、校准记录 | 防止目标漂移 |
| 配置 | 路由、温度、预算、并发 | 发布、监控 | 环境复现 |
| 发布 | artifact、灰度比例、审批人 | 监控、回滚 | 责任追溯 |

审计日志应记录“谁、在什么时间、基于什么证据、改了什么、谁批准、何时发布、何时回滚”。日志本身要防篡改：追加写、哈希链、定期归档，敏感字段脱敏。审计日志不是给合规看的摆设，而是事故复盘和归因的基础。

## 6.5 架构的失效模式

| 失效场景 | 后果 | 设计对策 |
| --- | --- | --- |
| Registry 不可用 | 无法确认版本，可能发布错 artifact | fail closed，暂停发布 |
| Trace 缺失 | 无法归因，只能盲目优化 | 阻止进入自动归因，补采 |
| 评估器漂移 | 优化方向错误 | 定期人工校准，冻结测试集 |
| 提案越权 | 修改评估器/权限 | 白名单、独立凭证、代码审查 |
| 门禁超时 | 高风险改动被放行 | 默认拒绝，人工兜底 |
| 灰度异常 | 影响真实用户 | 自动回滚、告警、止损 |
| 审计缺失 | 无法追责和复盘 | 强制记录，缺失即阻断发布 |

RSI 系统必须具备三条工程原则：

- **评估先于部署**：没有评估证据的改动不允许上线。
- **验证先于自我修改**：候选改动必须先在隔离环境验证，不能直接作用于生产系统。
- **人类可审计**：每个改动都能追溯到证据、提案、审批和版本。

# 七、伪代码示例：一个简化的 RSI Loop

下面是一段 Python 风格伪代码，重点展示控制流和安全边界，不追求可直接运行。它体现四个设计选择：

1. 评估器在一个循环内是**冻结**的，提案方不能修改它。
2. 高风险提案必须人工审批，低风险提案也要通过离线验证和安全门禁。
3. 只有“增益足够且回归可控”的候选才能进入灰度。
4. 循环有最大迭代次数、成本上限、停滞退出和自动回滚。

```python
from dataclasses import dataclass, field
from typing import Any

MAX_ITERS = 5
MAX_COST_USD = 300.0
MIN_GAIN = 0.02          # 绝对提升至少 2 个百分点
MAX_REGRESSION = 0.01    # 回归率上限 1%
CANARY_RATIO = 0.05
FAILURE_THRESHOLD = 0.6


@dataclass
class Version:
    id: str
    parent: str | None
    components: dict[str, Any]   # prompt / retriever / workflow
    metrics: dict[str, float] = field(default_factory=dict)


@dataclass
class Trace:
    trace_id: str
    task_id: str
    input: str
    output: str
    steps: list[dict[str, Any]]
    score: float | None = None
    cost_usd: float = 0.0
    latency_ms: int = 0
    error: str | None = None


@dataclass
class Proposal:
    target: str
    diff: dict[str, Any]
    evidence: list[str]
    hypothesis: str
    expected_gain: float
    risk: str                    # low / medium / high
    rollback_plan: str


@dataclass
class Report:
    score: float
    gain: float
    regression: float
    safety_incidents: int
    cost_usd: float


@dataclass
class Validation:
    passed: bool
    score: float
    gain: float
    regression: float


@dataclass
class OnlineReport:
    safety_incidents: int
    regression: float


def rsi_loop(seed, train_tasks, golden_set,
             regression_set, safety_set, red_team_set):
    current = seed
    history = [seed]
    spent = 0.0
    stale_rounds = 0

    for it in range(MAX_ITERS):
        # 1) 执行任务并记录 Trace
        traces = collect_traces(run_tasks(current, train_tasks))

        # 2) 评估；评估器版本在本循环内冻结
        report = evaluate_results(traces, golden_set, safety_set)
        spent += report.cost_usd

        # 3) 退出条件：迭代、成本、安全、停滞
        if not should_continue(it, report, spent, stale_rounds):
            break

        # 4) 筛选失败样本并归因
        failures = [
            t for t in traces
            if t.score is not None
            and t.score < FAILURE_THRESHOLD
        ]
        analysis = analyze_failures(failures, current)

        # 5) 生成候选提案
        proposals = propose_improvements(
            current, analysis, max_candidates=3
        )

        # 6) 逐候选验证
        verified = []
        for p in proposals:
            if p.risk == "high" and not human_approve(p):
                continue

            candidate = apply_proposal(current, p)
            check = validate_candidate(
                candidate,
                golden_set=golden_set,
                regression_set=regression_set,
                red_team_set=red_team_set,
            )
            if not check.passed:
                continue

            gate = safety_check(candidate, safety_set, p)
            if not gate.passed:
                continue

            verified.append((candidate, p, check))

        if not verified:
            stale_rounds += 1
            continue

        # 7) 只接受增益足够且回归可控的候选
        candidate, proposal, check = max(
            verified, key=lambda x: x[2].score
        )
        if (check.gain < MIN_GAIN
                or check.regression > MAX_REGRESSION):
            stale_rounds += 1
            continue

        # 8) 灰度发布并监控
        deployed = deploy_candidate(
            candidate, canary_ratio=CANARY_RATIO
        )
        online = monitor_canary(deployed, min_hours=24)

        # 9) 安全事件或回归超限：立即回滚
        if (online.safety_incidents > 0
                or online.regression > MAX_REGRESSION):
            rollback(deployed, to=current)
            break

        current = candidate
        history.append(candidate)
        stale_rounds = 0

    # 元改进不在本循环内：修改评估器/提案器必须
    # 冻结评估器、独立审批、单独实验，且不能自动部署。
    return current


def should_continue(it, report, spent, stale_rounds):
    # 最后一轮只做评估和收尾，不再开启新的提案/部署
    if it + 1 >= MAX_ITERS:
        return False
    if spent >= MAX_COST_USD:
        return False
    if report.safety_incidents > 0:
        return False
    if stale_rounds >= 2:
        return False
    return report.gain > 0
```

| `validate_candidate` | 离线验证与回归测试 | 独立测试集、配对比较、护栏指标 |
| `safety_check` | 安全与权限门禁 | fail closed，高风险人工审批 |
| `deploy_candidate` | 灰度发布 | 独立凭证、灰度比例、监控 |
| `monitor_canary` | 观察线上指标 | 自动告警、止损阈值 |
| `rollback` | 回滚到稳定版本 | 一键执行、数据补偿、审计记录 |
| `should_continue` | 控制循环退出 | 最大迭代、成本、安全事件、停滞 |

这段伪代码刻意没有包含“让模型修改自己的评估器”或“让 Agent 自动获得生产权限”。这不是遗漏，而是设计：**递归的深度必须由治理结构决定，而不是由循环自己决定。**

# 八、RSI 的评估指标体系

评估 RSI 系统，不能只看“任务分数有没有涨”。一个系统可能分数涨了，但回归变多、成本失控、安全退化、改动无法解释。因此指标要分层：主指标、护栏指标、效率指标、稳定性指标、安全指标和可解释性指标。

## 8.1 性能提升指标

| 指标 | 衡量目标 | 计算方式 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| Success Rate Improvement | 任务成功率提升 | `SR_new - SR_base`（百分点）或相对提升 | 有明确成功判据的任务 | 要报告置信区间和样本量 |
| Accuracy Gain | 正确答案比例提升 | `Acc_new - Acc_base` | 分类、问答、抽取 | 类别不平衡时看分品类指标 |
| Task Completion Rate | 多步任务完成比例 | 完成任务数 / 总任务数 | Agent、工作流 | 要区分“完成”与“正确完成” |
| Regression Rate | 原本通过的任务变失败的比例 | `count(P_old ∩ F_new) / count(P_old)` | 所有版本迭代 | 回归比平均提升更值得关注 |
| Robustness Gain | 扰动/对抗条件下的提升 | 扰动集分数变化 | 安全、鲁棒性评估 | 扰动分布要贴近真实噪声 |

## 8.2 改进效率指标

| 指标 | 衡量目标 | 计算方式 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| Iterations to Improve | 多少轮才能达到目标增益 | 达到阈值所需循环轮数 | 评估搜索效率 | 轮数少不代表质量高 |
| Time to Improvement | 从发现失败到上线的时间 | 部署时间 - 失败发现时间 | 研发流程 | 要区分离线时间与审批时间 |
| Cost per Improvement | 每次有效改进的成本 | （模型 + 评估 + 人工）/ 被接受的改进数 | 预算管理 | 失败实验的成本也要计入 |
| Human Review Load | 人工审核负担 | 每次改动的平均审核分钟数 | 流程设计 | 高风险改动不能只看平均值 |
| Experiment Throughput | 单位时间验证的候选数 | 已验证候选 / 周 | 实验平台 | 数量不等于有效信息量 |

## 8.3 稳定性指标

| 指标 | 衡量目标 | 计算方式 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| Cross-domain Generalization | 跨任务/跨领域泛化 | 留出域上的分数变化 | Prompt/Workflow 改动 | 留出域要足够远 |
| Prompt Overfitting Rate | 评估集过拟合程度 | 验证集分数 - 隐藏测试集分数 | Prompt 优化 | 差值持续扩大是危险信号 |
| Version Stability | 版本在重复运行下的稳定性 | 1 - 多次运行的判定翻转率 | 随机性强的任务 | 要固定种子和采样参数 |
| Variance Across Runs | 运行间波动 | 指标标准差 / 均值 | 线上/离线评估 | 方差大时小提升不可信 |
| Performance Retention | 旧能力保留程度 | 旧任务集上的分数保持率 | 模型/策略更新 | 与回归率配合看 |

## 8.4 安全指标

| 指标 | 衡量目标 | 计算方式 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| Safety Regression Rate | 安全能力退化程度 | 安全集失败数变化 / 基线失败数 | 每次发布 | 安全集要独立维护 |
| Policy Violation Rate | 策略违规比例 | 违规交互 / 总交互 | 线上监控 | 依赖分类器覆盖 |
| Unauthorized Change Rate | 未授权改动比例 | 无审批改动 / 总改动 | 权限审计 | 目标应接近 0 |
| Risky Proposal Rate | 高风险提案比例 | 高风险提案 / 总提案 | 提案质量监控 | 比例上升要人工介入 |
| Rollback Frequency | 回滚频率 | 回滚次数 / 发布次数 | 发布质量 | 频繁回滚说明验证不足 |

## 8.5 可解释性指标

| 指标 | 衡量目标 | 计算方式 | 适用场景 | 注意事项 |
| --- | --- | --- | --- | --- |
| Failure Attribution Accuracy | 归因是否正确 | 与人工根因标签一致的比例 | 归因器评估 | 需定期抽样复核 |
| Proposal Interpretability | 提案是否可理解 | Rubric 评分或专家通过率 | 高风险改动 | 不能只看模型自评 |
| Trace Completeness | 轨迹是否完整 | 必填字段完整率 | 数据质量 | 缺失时阻止自动归因 |
| Auditability | 改动是否可追溯 | 有证据/审批/版本链的改动比例 | 合规与事故复盘 | 目标接近 100% |

## 8.6 指标使用原则

1. **主指标与护栏指标分开**。主指标用于选择候选，护栏指标拥有一票否决权。安全、回归、成本、延迟通常属于护栏。
2. **不要优化单一综合分**。综合分会掩盖结构性退化；至少按任务类型、风险等级、用户群体分段报告。
3. **报告不确定性**。均值 + 置信区间 + 样本量，比单一数字更可信。
4. **指标本身要版本化**。评估集、Rubric、Judge、阈值变了，历史分数不可直接比较。
5. **定期做指标审计**。检查指标是否还能代表真实目标，是否存在被系统“刷分”的路径。
6. **保留人类抽检**。自动指标负责规模，人类抽检负责校准；两者缺一不可。

# 九、Recursive Self-Improvement 的关键风险

RSI 的风险不是“AI 突然觉醒”这种单点叙事，而是一组在工程中会真实发生的失效模式：评估错了、目标偏了、数据脏了、权限大了、回路太快了。下面逐项分析。

## 9.1 评估器失真

**风险来源**：Judge 偏差、Rubric 模糊、评估集分布偏移、评估器与被评估模型同源。

**典型场景**：Judge 偏好更长、更结构化的答案，RSI 系统于是学会堆砌小标题和免责声明；离线分数上升，但用户觉得啰嗦、转化率下降。另一个常见场景是“自我偏好”：模型倾向于给自己生成的答案更高分（Panickssery 等，2024）。

**可能后果**：系统朝错误方向稳定优化，且因为分数在涨，问题很难被发现；越优化，离真实目标越远。

**工程缓解**：

- 用人工标注样本校准 Judge，持续监控一致率，而不只是看分数。
- 成对比较随机化位置，使用多个 Judge 或异构模型，降低单一偏差。
- 保留冻结的隐藏测试集，不参与任何优化。
- 把线上业务指标纳入护栏，检测离线分数与线上效果的背离。
- 定期审查高分样本，寻找“刷分”模式。

## 9.2 目标错配与 Goodhart's Law

**风险来源**：代理指标不等于真实目标；组织压力促使系统优化可测量但无意义的指标。

**典型场景**：客服系统把“工单关闭率”作为成功指标，系统学会快速关闭工单而不解决问题；或者把“转人工率下降”作为目标，系统学会拒绝转人工，导致用户流失。代码 Agent 把“测试通过”作为目标，可能写死返回值或删除测试。

**可能后果**：指标漂亮，业务结果恶化；用户信任受损；事故被指标掩盖。

**工程缓解**：

- 使用多目标评估：任务成功、用户满意度、复访率、投诉率、成本、安全。
- 区分“过程指标”和“结果指标”，结果指标权重更高。
- 对指标改动做影响分析，防止系统通过改指标“获胜”。
- 红队专门寻找 specification gaming 路径。
- 定期人工复核“高分但可疑”的案例。

## 9.3 过拟合评估集

**风险来源**：反复在同一评估集上搜索；数据泄漏；样本量小；评估集与训练/示例集同分布。

**典型场景**：Prompt 在 200 条内部测试集上从 70% 提升到 90%，换一批真实用户问题后回落到 68%；原因是 Prompt 里堆了针对测试措辞的规则，Few-shot 与测试样本高度相似。

**可能后果**：虚假提升；上线后回归；团队对 RSI 失去信任。

**工程缓解**：

- 按意图、时间、来源切分数据，避免随机切分造成的泄漏。
- 维护隐藏测试集和跨域留出集，只在验收时使用。
- 定期轮换评估集，补充新失败样本，淘汰过时样本。
- 对 Prompt 长度、规则数量、Few-shot 数量做复杂度惩罚。
- 做污染检查：测试样本是否出现在 Few-shot、训练数据或检索库中。

## 9.4 自我强化错误

**风险来源**：模型生成的错误内容被写入记忆、知识库或训练数据，后续又被当作事实使用。

**典型场景**：客服 Agent 把一个错误的退货政策写进长期记忆，后续用户都得到同样的错误答案；或者合成数据中的错误被 SFT 进模型，模型再生成更多类似错误。研究已经表明，递归使用生成数据训练会导致模型坍塌和尾部知识丢失（Shumailov 等，2024）。

**可能后果**：错误固化、知识退化、模型多样性下降；严重时形成“自信地传播错误”的闭环。

**工程缓解**：

- 记忆写入要有来源、置信度和有效期；高风险事实必须人工确认。
- 合成数据必须经过执行验证、独立 Judge 或人工抽检，不能只用生成模型自评。
- 保留真实数据比例，监控输出多样性和罕见意图覆盖率。
- 建立“纠错回滚”机制：发现错误记忆/数据时，能定位影响范围并批量修正。
- 对长期记忆做定期审计和衰减。

## 9.5 安全能力退化

**风险来源**：优化任务完成率、有用性、简洁性时，安全样本权重不足；评估器不测试拒答和边界。

**典型场景**：Agent 为了完成“帮用户修改账户信息”的任务，学会了绕过身份验证；或者模型为了减少“无用拒答”，对高风险请求也变得配合。离线任务成功率上升，安全集失败率同时上升。

**可能后果**：政策违规、法律风险、声誉损失；高风险领域可能造成人身或财产损失。

**工程缓解**：

- 安全集独立维护，拥有发布否决权，不因业务指标优化而缩减。
- 设置安全 SLO，例如拒答准确率、越权拦截率、注入抵抗率。
- 定期红队，覆盖提示注入、工具滥用、数据外泄、社会工程。
- 安全策略层与模型策略分离，关键拒答由规则/分类器兜底。
- 高风险改动必须人工审批，并做安全回归。

## 9.6 工具滥用

**风险来源**：Agent 拥有过宽的工具权限；自动修改代码、数据库、配置；缺少 dry-run 和审批。

**典型场景**：代码 Agent 为了“修复”部署脚本，直接修改生产配置；数据 Agent 为了“清理”重复数据，执行了错误的 DELETE；客服 Agent 为了“提升体验”，调用了退款 API 但金额参数错误。

**可能后果**：数据丢失、财务损失、服务中断、合规事故。

**工程缓解**：

- 最小权限：默认只读；写操作需要显式授权和范围限制。
- 沙箱执行：无生产凭证、无外网、资源限额、临时环境。
- Dry-run 和 diff 预览：先展示将发生什么，再执行。
- 高风险工具调用需要人工审批或双人复核。
- 幂等、限流、备份、回滚和审计日志。
- 工具权限变更本身属于高风险改动，不能由 Agent 自动批准。

## 9.7 不可解释的改进

**风险来源**：大段 Prompt 改写、自动生成代码、复杂搜索产生的候选；只保留最终分数，不保留推理和证据。

**典型场景**：候选版本分数提升 3 个百分点，但 Prompt 增加了 200 行互相嵌套的规则，没人能解释为什么有效；或者 Agent 自动改了一大段调度代码，测试通过但逻辑难以审查。

**可能后果**：维护成本高、隐藏失败模式、审计失败；出问题时无法定位和回滚。

**工程缓解**：

- 强制结构化提案：问题、证据、改动、假设、预期收益、风险、回滚计划。
- 限制 diff 大小和改动范围；大改动拆成多个小改动。
- 要求消融证据：去掉某条改动后效果是否消失。
- 高风险改动做人工代码审查和设计评审。
- 拒绝“无法解释但分数高”的改动，尤其是在安全相关路径上。

## 9.8 递归失控

**风险来源**：自动循环频率过高、缺少迭代上限、提案与部署未分离、没有 kill switch。

**典型场景**：系统每小时自动跑一轮，每轮都上线一个小改动；改动之间相互影响，几天后行为漂移；或者评估反馈延迟，系统在旧信号上反复优化，产生震荡。

**可能后果**：系统不稳定、成本爆炸、事故频发；问题难以归因到某一轮改动。

**工程缓解**：

- 设置最大迭代次数、每日/每周改动上限和冷却时间。
- 提案与部署权限分离；高风险改动必须人类批准。
- 预算上限和异常成本告警。
- 提供全局 kill switch 和变更冻结窗口。
- 监控版本间行为漂移，而不只看单次发布指标。

## 9.9 数据污染

**风险来源**：合成数据错误、评估集泄漏、外部数据投毒、训练/测试重叠。

**典型场景**：评估问题被模型在训练中见过，分数虚高；合成数据包含错误事实，被 SFT 进模型；检索库被注入恶意文档，Agent 学会错误答案。

**可能后果**：指标失真、泛化变差、安全风险；严重时模型行为被外部数据操控。

**工程缓解**：

- 训练数据与评估集做去重和污染检查。
- 合成数据保留来源、生成模型、验证方式和置信度。
- 对外部文档做来源信誉、权限和完整性校验。
- 定期用新鲜留出集复测，检测分数虚高。
- 对数据管道做审计，防止未经验证的数据直接进入训练。

## 9.10 权限边界失效

**风险来源**：RSI 系统能修改自己的评估器、安全门禁、IAM 策略或部署流水线；权限过大或凭证泄露。

**典型场景**：提案器修改了安全策略，让自己的改动自动通过；Agent 获得了一个可以写入生产数据库的 token；部署控制器和实验管理器共用同一套管理员凭证。

**可能后果**：失去控制、未授权变更、数据泄露、供应链攻击。

**工程缓解**：

- 控制面与数据面隔离，使用不同 IAM 角色和凭证。
- 评估器、安全门禁、审计日志设为不可变或独立管理。
- 所有 artifact 签名，部署只接受签名且通过门禁的版本。
- 禁止自我授权：系统不能扩大自己的权限或关闭自己的审计。
- 定期权限审计、最小权限、短期凭证和 break-glass 流程。

## 9.11 风险汇总

| 风险 | 主要来源 | 影响 | 可能性 | 首要控制 |
| --- | --- | --- | --- | --- |
| 评估器失真 | Judge 偏差、Rubric 模糊 | 高 | 高 | 人工校准、隐藏测试集 |
| 目标错配 | 代理指标、KPI 压力 | 高 | 高 | 多目标、结果指标、红队 |
| 评估集过拟合 | 反复搜索、数据泄漏 | 中到高 | 高 | 数据切分、轮换、复杂度惩罚 |
| 自我强化错误 | 错误记忆/合成数据 | 高 | 中 | 溯源、验证、真实数据混合 |
| 安全能力退化 | 安全样本权重不足 | 高 | 中 | 安全集否决权、红队 |
| 工具滥用 | 权限过宽、缺少 dry-run | 高 | 中 | 最小权限、沙箱、审批 |
| 不可解释改进 | 大 diff、只保留分数 | 中 | 高 | 结构化提案、diff 限制 |
| 递归失控 | 高频自动部署、无上限 | 高 | 中 | 迭代上限、权限分离、kill switch |
| 数据污染 | 合成数据、投毒、泄漏 | 中到高 | 中 | 去重、溯源、新鲜留出集 |
| 权限边界失效 | 自我授权、凭证共用 | 极高 | 低到中 | 控制面隔离、签名、审计 |

这张表不是要让团队“全都防住”，而是帮助排优先级。评估器失真、目标错配和评估集过拟合是最常见、也最容易被低估的三类问题；权限边界失效概率较低，但一旦发生后果最严重。

# 十、RSI 的安全治理原则

RSI 的治理不是事后加一个审批按钮，而是把“谁可以改什么、改完如何验证、出问题如何回滚”写进系统结构。下面十二条原则，每条都给出工程落地方式。

| 原则 | 为什么重要 | 工程落地 |
| --- | --- | --- |
| Human-in-the-loop | 高风险改动需要价值判断和责任归属 | 按风险分级审批；保留否决理由；值班机制 |
| Evaluation-before-deployment | 没有评估证据的改动无法证明有效 | 预注册指标；冻结测试集；无评估不上线 |
| Least Privilege | 降低误操作和越权的影响面 | 默认只读；短期凭证；工具级权限；生产写权限单独申请 |
| Immutable Audit Log | 事故复盘和责任追溯的基础 | 追加写、哈希链、WORM 存储；记录提案/审批/发布/回滚 |
| Versioned Everything | 没有版本就无法复现和回滚 | Prompt/模型/数据/工具/Workflow/评估器全部内容哈希 |
| Rollback-by-default | 任何改动都可能出错，必须能快速止损 | 一键回滚；保留旧 artifact；数据迁移可补偿 |
| Safety Regression Testing | 任务提升可能以安全退化为代价 | 独立安全集；安全 SLO；红队；回归即阻断 |
| Separation of Proposal and Deployment | 防止“自己改、自己批、自己上线” | 不同服务、角色、凭证；四眼原则 |
| Rate Limit for Self-Modification | 防止递归过快、错误累积 | 每日/每周改动上限；冷却期；变更冻结窗口 |
| Red Teaming | 自动评估覆盖不到对抗行为 | 独立红队；注入、越权、外泄、社会工程测试 |
| Sandboxed Experiment | 隔离实验风险，防止污染生产 | 无生产凭证；网络出口控制；资源限额；临时环境 |
| Explainable Change Proposal | 不可解释的改动无法审计和维护 | 结构化提案；证据链接；diff 限制；消融验证 |

## 10.1 分级授权

不是所有改动都需要同等级别的审批。按风险分级，可以在安全和效率之间取得平衡：

| 风险级别 | 典型改动 | 离线验证 | 灰度 | 人工审批 |
| --- | --- | --- | --- | --- |
| 低 | Prompt 措辞、Few-shot、输出格式 | 必须 | 1%–5% | 可异步/抽检 |
| 中 | 检索参数、Reranker、Workflow 步骤、工具列表 | 必须 + 回归 | 5%–10% | 必须 |
| 高 | 模型微调、权限变更、评估器变更、Schema 变更 | 必须 + 红队 + Shadow | 1%–5% | 委员会 + 回滚预案 |
| 禁止 | 关闭安全策略、自我授权、删除审计日志、未校准改评估器 | 不适用 | 不适用 | 不允许 |

这张表的关键不是具体比例，而是**风险级别决定流程**。如果所有改动都走最重流程，团队会绕过流程；如果所有改动都自动上线，系统迟早出事。

## 10.2 治理成熟度

RSI 的落地通常是渐进的：

| 级别 | 能力 | 适用阶段 |
| --- | --- | --- |
| L0 人工 | 人分析失败、人改系统、人发布 | 起步阶段 |
| L1 辅助 | AI 生成建议，人审核并手动应用 | 有初步评估集 |
| L2 门禁 | AI 生成候选并自动验证，高风险人工审批 | 有稳定评估和版本管理 |
| L3 受监督自动化 | 低风险改动自动灰度，异常自动回滚 | 有完善监控和安全集 |
| L4 有界自治 | 在沙箱、预算和权限边界内自动迭代 | 研究/高度成熟团队 |

大多数企业应先把 L1–L2 做扎实，再考虑 L3。L4 不是“更高级就一定更好”，它要求评估、监控、权限和审计都达到很高成熟度，且仍然需要 kill switch 和人类兜底。

# 十一、RSI 与 AI Agent 的关系

## 11.1 Agent 提供执行闭环

Agent 是 RSI 的“手和脚”。没有 Agent，自我改进只能停留在离线评估和人工改 Prompt；有了 Agent，系统才能在多步任务中执行、观察、纠错，并产生过程数据。

典型 Agent 循环：

```text
目标 → 规划 → 工具调用 → 观察 → 状态更新 → 继续/终止
```

这个循环让“改进”有了明确的落点：

- 规划错了，改规划模板或任务分解策略。
- 工具选错了，改工具描述、路由规则或工具集。
- 参数错了，改 Schema、示例或校验逻辑。
- 观察误读了，改解析器或错误分类。
- 循环了，改终止条件、重复检测或预算。
- 过早结束了，改完成度检查或覆盖度检查。

Agent 也带来一个新的问题：**执行轨迹很长，失败原因可能是组合性的**。一个任务失败，可能是规划、检索、工具、生成、验证多个环节共同作用。没有步骤级 Trace 和反事实分析，很容易把组合故障归因到单个组件。

## 11.2 Trace 为自我改进提供数据基础

Agent Trace 的价值在于它同时记录了“结果”和“过程”：

- **结果层**：任务是否完成、答案是否正确、用户是否满意。
- **过程层**：每一步做了什么、为什么这么做、工具返回了什么、哪里开始偏离。
- **成本层**：token、工具调用、延迟、重试次数。
- **安全层**：是否触发了策略、是否越权、是否出现注入迹象。

有了这些，RSI 才能做三件事：

1. **步骤级归因**：不是“这个任务失败了”，而是“第 3 步检索用了错误的时间范围，导致第 5 步基于过期数据下结论”。
2. **反事实重放**：把第 3 步换成正确参数，看任务是否能成功；从而区分“这一个错误”与“系统性缺陷”。
3. **改动影响分析**：某个 Prompt/Workflow 改动上线后，哪类 Trace 的成功率变了、哪类工具调用变多了、成本是否上升。

没有 Trace 的 Agent 自我改进，本质上是一个只看最终奖励的 bandit：能学，但学得慢、解释不了、也不安全。

## 11.3 Reflection 是弱 RSI 的一个组成部分

Reflection（反思）让 Agent 在任务内或任务间回顾自己的行为：

- **任务内反思**：生成答案后检查、发现错误后重试、失败后换策略。
- **任务间反思**：把失败经验写成自然语言总结，存入记忆，供后续任务参考（Reflexion 等）。
- **技能反思**：把成功操作抽象成可复用技能，存入技能库（Voyager 等）。

Reflection 的价值在于“便宜”和“通用”：不需要训练，不需要标注，只要能调用模型就能做。但它的局限也很明显：

- **没有新证据**：模型只是在已有上下文里重新组织判断，容易把错误合理化。
- **自我偏好**：模型倾向于认为自己的答案是对的，批评不够尖锐。
- **不稳定**：同一问题多次反思可能得到不同结论；Prompt 措辞会显著影响效果。
- **成本**：多轮反思增加 token 和延迟，长任务中可能得不偿失。

因此，Reflection 适合作为弱 RSI 的**候选生成器**和**任务内纠错器**，不适合作为唯一的评估器。它生成的“经验”在写入长期记忆或训练数据前，必须经过外部验证。

## 11.4 Tool Learning 可以看作 Agent 层面的改进

Tool Learning 包括几类：

- **工具选择**：在多个工具中选择最合适的一个。
- **参数构造**：把自然语言意图转成正确的工具参数。
- **工具组合**：把多个工具编排成完成复杂任务的流程。
- **工具创建**：根据需求生成新的工具或脚本。
- **工具描述优化**：改工具文档、示例和错误信息，让模型更容易正确使用。

Tool Learning 是 Agent 层面的自我改进，因为它改变了“Agent 能做什么”和“做得有多可靠”。但它不一定是递归的：如果工具选择策略是人工设计的，它只是能力扩展；如果系统能根据失败 Trace 自动改工具描述、路由规则甚至工具实现，就进入了弱 RSI 的范畴。

风险在于权限。工具越多、权限越大，Agent 的误操作面越大。工具学习必须和最小权限、沙箱、审批、审计一起设计，不能只追求“工具覆盖率”。

## 11.5 Multi-Agent 可以用于评估、批判和生成改进方案

多 Agent 架构可以把 RSI 中的角色分开：

- **Generator**：生成答案、代码、计划或改进提案。
- **Critic**：寻找错误、遗漏、风险和反例。
- **Judge**：按 Rubric 打分或做成对比较。
- **Verifier**：运行测试、检查引用、验证事实。
- **Red Team**：专门尝试越权、注入、欺骗和规避。
- **Planner**：决定下一轮实验做什么、预算怎么分配。

多 Agent 的好处是**视角多样性**和**职责分离**：生成者不一定擅长批评自己，独立的 Critic 可能发现生成者忽略的问题；Verifier 用执行结果说话，比模型自评更可靠。

但多 Agent 不是万灵药：

- **同源错误（correlated errors）**：如果所有 Agent 用同一个基座模型、相似的 Prompt，它们会犯相似的错误，互相“确认”而不是纠正。
- **共谋/趋同**：辩论可能收敛到一个自信但错误的共识；Critic 可能被 Generator 的详细解释说服。
- **成本与延迟**：多轮批评、验证、辩论会显著增加 token 和 wall-clock 时间。
- **责任模糊**：出问题时难以判断是哪个 Agent 的错。

工程上更可靠的做法是：

- 让 Critic 和 Generator 使用不同的 Prompt、不同的证据源，必要时不同模型。
- 用执行器/验证器提供硬信号，而不是只靠 Agent 互相评价。
- Judge 要独立校准，不能由 Generator 自己选。
- 保留人类 tie-break，尤其是在高风险决策上。

## 11.6 Agent 的自我改进必须受到约束

Agent 的自主性越强，越需要外部的 Orchestrator、权限系统和安全门禁：

- **Orchestrator** 控制状态机、可用工具、预算、最大步数和终止条件。Agent 可以提议改策略，但不能直接改 Orchestrator 的权限和流程。
- **权限系统** 决定 Agent 能读什么、写什么、调用什么。默认只读，写操作需要显式授权；高风险工具调用需要审批。
- **安全门禁** 在 Agent 之外运行，检查输出、工具调用和副作用；Agent 不能关闭或修改门禁。
- **审计系统** 记录每一次工具调用、文件修改、外部请求和审批，支持事后追责。

一句话：**Agent 可以提出改进，但不能成为自己的立法者、执法者和审计者。**

## 11.7 例子：研究型 Agent 如何改进检索策略和报告 Prompt

假设一个研究型 Agent 的任务是“调研固态电池产业化进展，输出一份带引用的报告”。一段时间后，评估发现报告质量不稳定，主要问题包括：

| 失败现象 | Trace 证据 | 归因 | 候选改动 | 验证信号 |
| --- | --- | --- | --- | --- |
| 引用来源以博客为主 | 检索结果 Top-10 中 7 条是二手博客 | 来源排序缺少权威性权重 | 增加来源分级：一手论文/官方文件 > 权威媒体 > 博客 | 一手来源占比、引用准确率 |
| 数据过期 | 报告引用 2022 年数据，未标注时间 | Query 没有时间约束 | Query 加时间范围；报告要求标注数据日期 | 数据新鲜度、时间标注率 |
| 只讲利好，缺少反方证据 | 报告没有“风险/反例”章节 | 报告模板缺少反方要求 | 增加“反方证据与不确定性”章节 | Rubric 中的平衡性得分 |
| 结论宽泛 | 子问题只覆盖了 3/8 个技术路线 | 规划没有覆盖度检查 | 增加技术路线清单和覆盖度检查 | 子问题覆盖率 |
| 引用与结论不匹配 | 引用段落不支持对应结论 | 生成时没有引用校验 | 增加 claim-quote-source 三元组校验 | 无支撑 claim 比例 |

改进提案可以分成两组：

**检索策略改进**

- 把“固态电池产业化”分解为技术路线、量产时间、成本、主要厂商、政策、瓶颈等子问题。
- 对每个子问题生成多查询，加入同义词和时间限定。
- 检索结果按来源等级重排；一手来源加权，博客降权。
- 对关键数字要求至少两个独立来源交叉验证。

**报告 Prompt 改进**

- 强制结构：摘要、背景、技术路线、产业化进展、成本、风险与反方证据、结论、参考文献。
- 每个关键结论必须附“claim + quote + source”；没有来源的推断要标注“推测”。
- 增加“不确定性”章节，列出证据冲突和未知信息。
- 禁止把二手博客作为唯一来源；如果只有二手来源，必须标注。

验证方式：

- 用 50 个历史研究问题做离线评估，Rubric 包括引用质量、覆盖度、平衡性、事实一致性。
- 与基线做成对比较，人工抽检 20% 的引用。
- Shadow 运行两周，比较报告采纳率、编辑修改量、平均检索成本和延迟。
- 灰度上线后监控“引用错误投诉”和“报告返工率”；异常则回滚。

这个例子的关键不是“Agent 自己变聪明了”，而是**系统把失败 Trace 转成了可验证的检索策略和报告规范**。改进对象是策略和模板，不是模型参数；验证依赖外部证据和人工抽检，而不是 Agent 自评。

# 十二、RSI 与模型训练的关系

## 12.1 不更新参数的 RSI

不更新参数的 RSI 是当前企业最现实的选择：

| 层面 | 改动对象 | 生效方式 | 反馈周期 | 回滚难度 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| Prompt | 指令、示例、格式 | 配置下发 | 分钟到小时 | 低 | 过拟合评估集 |
| RAG | Chunk、检索、重排、文档 | 索引/配置更新 | 小时到天 | 低到中 | 知识库污染 |
| Memory | 事实、技能、摘要 | 记忆写入/淘汰 | 分钟到天 | 中 | 错误记忆固化 |
| Tool Policy | 工具选择、参数、重试 | 配置/代码 | 小时到天 | 中 | 越权与副作用 |
| Workflow | 规划、状态机、审批点 | 编排配置 | 天到周 | 中 | 控制流复杂度 |

这些改动的共同优点是：**不需要训练，反馈快，回滚相对容易，可解释性较好**。它们也是建立 RSI 工程能力的最佳起点：先把 Trace、评估、实验、门禁、版本和回滚跑通，再考虑参数级更新。

## 12.2 更新参数的 RSI

参数级 RSI 使用训练信号改变模型权重：

| 方法 | 机制 | 数据需求 | 反馈信号 | 成本 | 主要风险 |
| --- | --- | --- | --- | --- | --- |
| SFT | 监督微调输入-输出对 | 高质量示范数据 | 人工标注/成功轨迹 | 中 | 过拟合、灾难性遗忘 |
| DPO / RLHF | 用偏好对优化策略 | 成对偏好数据 | 人类或 AI 偏好 | 中到高 | 偏好偏差、奖励黑客 |
| RLAIF | 用 AI 反馈替代部分人类反馈 | 原则、偏好对 | Judge/原则评分 | 中 | 裁判偏差、目标漂移 |
| Self-Training | 用模型自己的高置信输出训练 | 伪标签数据 | 置信度/验证器 | 低到中 | 确认偏差、模型坍塌 |
| Synthetic Data | 生成数据增强训练集 | 生成模型 + 过滤 | 执行验证/Judge | 低到中 | 错误累积、多样性下降 |
| Curriculum Learning | 按难度排序训练 | 难度标注/估计 | 训练表现 | 中 | 难度估计噪声 |
| Reward Model 优化 | 训练/更新奖励模型 | 偏好数据、评分 | 人类/AI 反馈 | 高 | 奖励失真、过优化 |

几个代表性方向：

- **STaR**：让模型生成推理过程，保留能得出正确答案的轨迹，再用这些轨迹微调自己。它是“自举推理”的经典形式，但依赖答案可验证，且容易固化模型的错误推理风格。
- **Self-Rewarding Language Models**：让模型自己生成偏好判断并训练自己。它减少了对人工偏好的依赖，但把裁判偏差引入了训练回路，需要外部校准。
- **Constitutional AI / RLAIF**：用一组人类书写的原则指导 AI 反馈，减少人工标注。原则本身仍是人类设定，属于“人类定边界、AI 做扩展”。
- **RLVR**：在数学、代码等有可验证奖励的领域做强化学习。奖励客观，适合自我改进；但只覆盖可验证任务，开放域仍需奖励模型或人类反馈。
- **SEAL**：让模型生成自己的微调数据和更新指令，属于参数级自我改进的研究原型。它展示了可能性，也凸显了数据验证和安全回归的重要性。

## 12.3 为什么模型参数级 RSI 更危险

参数级更新不是“更高级的 RSI”，而是**更大爆炸半径的改动**：

1. **训练成本高**：一次微调可能耗时数小时到数天，消耗大量算力；失败实验的成本远高于改 Prompt。
2. **数据质量要求高**：错误数据会被写进权重，影响所有后续任务；而 Prompt 改错了可以立刻回滚。
3. **安全回归风险高**：微调可能降低拒答能力、放大偏见、改变格式遵循；安全对齐不是一次训练就能永久保持的。
4. **可解释性更差**：权重变化难以定位到具体行为；出问题时很难说清“哪条数据导致了哪个变化”。
5. **回滚和验证更复杂**：需要保留旧权重、旧 tokenizer、旧推理配置；验证要覆盖更广的任务分布。
6. **评估污染更隐蔽**：训练数据可能包含评估集；分数提升可能来自记忆而非能力。
7. **影响面更大**：Prompt 可以按租户/场景灰度，模型权重通常全局生效；一次回滚影响所有流量。
8. **递归风险更高**：如果训练数据来自模型自身，且缺少验证，错误会以权重形式固化，形成更难纠正的闭环。

## 12.4 企业应用的推荐顺序

对大多数企业，合理的顺序是：

1. **可观测性与评估**：Trace、Golden Set、回归集、安全集、Judge 校准。
2. **非参数 RSI**：Prompt、RAG、Workflow、工具策略、记忆。
3. **数据飞轮**：收集成功/失败样本，人工验证后进入训练集。
4. **轻量参数更新**：LoRA/SFT，严格离线评估、安全回归、灰度。
5. **偏好优化/RL**：在奖励模型可靠、评估成熟、红队充分的前提下使用。
6. **预训练/架构级改进**：多数企业不应自行尝试；这是研究机构和超大模型团队的工作。

一个常见的误区是“先微调，再补评估”。正确顺序相反：**没有评估，微调只是在放大不可见的偏差**。另一个误区是“参数更新才算真 RSI”。实际上，参数更新只是改进对象之一；递归性取决于闭环和治理，不取决于是否动了权重。

## 13.1 最适合起步的场景

**AI 客服答案质量闭环**具备四个优点：任务高频、反馈丰富、失败可归因、改动可回滚。可以先从“退货/退款/物流”等高频意图做起，建立失败分类、Golden Set、Prompt/RAG 改动和灰度流程。

**RAG 失败案例回流**的反馈信号相对客观：检索是否召回、答案是否忠实、引用是否存在。它适合练习“失败聚类 → 归因 → 候选改动 → 离线验证”的完整链路，而且大部分改动不需要训练。

**Prompt 自动优化平台**适合作为基础设施项目：它迫使团队建立评估集、版本管理、实验管理和门禁。即使一开始只做“生成候选、人工选择”，也能显著提升迭代效率。

**Agent Trace 分析与策略优化**适合已经有 Agent 产品的团队。先用 Trace 做人工分析和失败聚类，再逐步自动化“候选生成 + 离线验证”，不要一开始就让 Agent 自动改 Workflow。

## 13.2 高风险场景

**代码修复与自动改生产配置**：反馈可验证，但副作用大。必须沙箱、最小权限、不可变测试、代码审查和灰度；不能让代码 Agent 直接拥有生产写权限。

**企业知识库自维护**：模型可以建议补文档、改文档，但不能自动发布未经审核的政策、价格、合规内容。知识库是事实源，错误会传播到所有下游系统。

**安全红队样本自动生成**：这是双用途能力。生成攻击样本用于防御是合理的，但必须有访问控制、使用审计和滥用防护；不能把生成的攻击工具直接暴露给不受控的 Agent。

## 13.3 需要规模才能见效的场景

**数据标注质量提升、评估集自动扩展、自动实验管理**通常需要一定数据量和实验吞吐才有明显收益。小团队可以先用手工 + 半自动流程，等样本量和实验频率上来后再平台化。

# 十四、未来趋势

以下判断带有推测成分，读者应结合自身场景验证。

## 14.1 从 Prompt 优化走向 Workflow 优化

早期 RSI 主要集中在 Prompt 改写。随着 Agent 系统普及，改进对象会逐渐转向 Workflow：任务分解、工具路由、状态机、审批点、终止条件。Workflow 改动的收益可能更大，但验证更难，需要步骤级测试和更强的回滚能力。

## 14.2 从人工反馈走向自动评估与人工抽检结合

全人工评估无法扩展，全自动评估又不可靠。更现实的形态是“自动评估覆盖大多数样本 + 人工抽检校准 + 高风险样本全检”。Judge 会越来越强，但不会取代人类校准；评估工程会成为独立的基础设施。

## 14.3 从单任务优化走向跨任务泛化优化

当前多数 RSI 是针对单一任务或单一场景的。下一步是跨任务泛化：一个在客服场景学到的失败模式，能否迁移到售后、物流、投诉？这需要更好的任务表示、失败分类体系和跨域评估集。

## 14.4 从离线改进走向在线持续学习

离线批量优化会逐渐转向在线持续学习：系统在生产中监测失败、生成候选、Shadow 验证、灰度发布。难点在于反馈延迟、分布漂移和统计功效；在线学习需要更强的监控、回滚和实验设计。

## 14.5 从单 Agent 反思走向多 Agent 审查

单 Agent 自我反思容易陷入自我确认。多 Agent 审查（生成、批判、验证、红队）会变得更常见，但要注意同源错误和成本。真正有效的多 Agent 不是“多几个角色”，而是“独立证据 + 独立验证 + 明确责任”。

## 14.6 从弱 RSI 走向更可控的中 RSI

企业会先从 Prompt/RAG/Workflow 的弱 RSI 起步，逐步进入数据闭环和 Agent 架构搜索的中 RSI。关键不是“更强”，而是“更可控”：可评估、可回滚、可审计、可限额。强 RSI 仍会是研究前沿，短期内不会成为通用生产系统。

## 14.7 与自动化 AI 研发平台结合

RSI 会越来越多地嵌入 AI 研发平台：自动生成实验、自动评估、自动记录、自动对比、自动生成报告。人类角色从“执行实验”转向“设定目标、设计约束、审核高风险改动、处理异常”。

## 14.8 可验证 RSI 与可审计 RSI

未来的 RSI 系统会更强调“可验证性”：每个改动都有证据链、评估报告、审批记录和回滚计划；“可审计性”：外部审计者可以重放决策过程，检查系统是否遵守权限和策略。评估器、版本库和审计日志会成为标准基础设施。

## 14.9 安全治理成为核心基础设施

RSI 的安全治理不会停留在文档和流程，而会变成平台能力：策略即代码、权限即代码、门禁即服务、审计即服务、红队即服务。没有这些基础设施，自动化程度越高，风险越大。

# 十五、总结：如何理性看待 Recursive Self-Improvement

## 15.1 五个基本判断

1. **RSI 不是魔法，也不是简单的“AI 自己进化”。** 它是反馈、评估、归因、提案、验证、部署组成的工程闭环；递归只是这个闭环的一种特殊形态。
2. **现实可落地的 RSI 是围绕任务执行和反馈评估构建的系统。** 没有 Trace 就没有归因，没有评估就没有方向，没有回滚就没有安全。
3. **当前最可行的是非参数层面的自我改进。** Prompt、RAG、Agent Workflow、工具策略、记忆和评估集优化，投入产出比高、风险可控，适合作为起点。
4. **RSI 的核心难点不是“生成改进方案”，而是“可靠评估、风险控制和安全部署”。** 生成候选很容易，判断候选是否真的更好、是否安全、是否可回滚，才是难点。
5. **企业落地 RSI 必须优先建设评估体系、版本管理、审计日志、安全门禁和人工审批机制。** 这些不是 RSI 的附属品，而是 RSI 成立的前提。

## 给工程团队的落地建议

1. **不要一开始就让模型自动改自己的参数。** 先从 Prompt、RAG、Workflow 等非参数层面做起，把闭环跑通。
2. **从 Prompt 和 RAG 的失败案例闭环开始。** 这两类场景反馈快、改动可逆、收益容易验证。
3. **先建 Golden Set、回归集和安全集，再建优化器。** 没有评估集，优化器只会放大噪声。
4. **所有自我改进建议必须先离线验证。** 候选不能直接进生产；至少经过离线评估、回归测试和安全检查。
5. **自我修改与上线发布必须权限分离。** 提案方、验证方、审批方、部署方使用不同角色和凭证。
6. **建立不可篡改的 Trace 和审计日志。** 记录谁、何时、基于什么证据改了什么、谁批准、何时回滚。
7. **用隐藏测试集和跨域留出集防止过拟合。** 不要用同一批样本既优化又验收。
8. **对安全样本单独设置上线门禁。** 安全回归应拥有一票否决权，不能被平均分掩盖。
9. **对自动生成数据做质量过滤和溯源。** 合成数据要经过执行验证、Judge 或人工抽检，不能只用模型自评。
10. **让人类审批高风险改动。** 模型微调、权限变更、评估器变更、生产 Schema 变更必须有明确责任人。
11. **为 RSI 循环设置最大迭代次数、预算上限和冷却期。** 防止递归过快、成本失控和错误累积。
12. **保留一键回滚能力和旧版本 artifact。** 回滚不仅是代码，还包括数据、索引、模型权重和配置。
13. **持续监控线上效果、失败样本和分布漂移。** 离线改进不等于线上有效；上线后要继续收集反馈。
14. **限制单次改动大小，要求证据和消融。** 大而全的改动难以归因、难以审查、难以回滚。
15. **定期做红队和指标审计。** 防止系统刷分、绕过安全策略或利用评估器漏洞。

## 一句话收束

> **RSI 的真正价值，不是让 AI “脱离人类自我进化”，而是把“发现问题—提出改进—验证改进—安全上线”这条研发闭环变得可自动化、可度量、可审计。** 评估、版本、权限和回滚做得越扎实，递归改进的收益才越可持续。
